## 2. 关键改动详解

### 2.1 §8 服务管理（生产 + 容器双分支，修复 v2-#1/#2/#3）

**生产分支**（零修改，原 systemd unit 完全保留）。
**容器分支**（关键修复）：
- 生成 `run-myblog.sh` heredoc，包含 `set -a; . $ENV_FILE; set +a; exec java ...`（env 注入 + 替代 systemd EnvironmentFile）
- 写 `/etc/supervisor/conf.d/myblog.conf`
- `supervisorctl reread/update/restart myblog`

### 2.2 §7.5 ENV 文件路径三元 + chown 守卫

```bash
if [ "$LOCAL_SIM" = "1" ]; then
    mkdir -p "$INSTALL_DIR"
    ENV_FILE="$INSTALL_DIR/myblog.env"           # 容器内
else
    mkdir -p /etc/myblog
    ENV_FILE="/etc/myblog/myblog.env"            # 生产
fi
...
chmod 600 "$ENV_FILE"                            # 永远保留（含 JWT_SECRET 必须 600）
if [ "$LOCAL_SIM" != "1" ]; then
    chown myblog:myblog "$ENV_FILE"              # 仅生产模式（容器内没 myblog 用户）
fi
```

**设计取舍**：chmod 600 永远跑，chown 仅生产模式——env 文件在容器里也是 600（只有 root 可读，安全等价于生产模式的"只有 myblog 可读"）。

### 2.3 §5/§6/§7 chown 守卫统一模式

```bash
cp .../blog-app.jar .../blog-app.jar
if [ "$LOCAL_SIM" != "1" ]; then
    chown myblog:myblog .../blog-app.jar
fi
```

6 处 chown 全部用同样模式：`if not sim then chown`。**关键风险**：原版 set -e 下，§5 第一个 chown 执行（用户不存在）就会 exit 1，连 §7.5 写 env 都到不了——意味着 JWT_SECRET 没生成、即使绕过 chown，run-myblog.sh 也会因 env 文件缺失失败。

### 2.4 §2 / §3 / §8.6 / §12 守卫模式

```bash
if [ "$LOCAL_SIM" = "1" ]; then
    info "LOCAL_SIM=1, skipping §X (reason)"
elif <原条件>; then
    <原代码>
fi
```

### 2.5 §9 / §10 systemd → supervisorctl

```bash
if [ "$LOCAL_SIM" = "1" ]; then
    supervisorctl restart nginx        # §9
    supervisorctl restart redis        # §10
else
    systemctl enable nginx && systemctl restart nginx
    systemctl enable redis-server ...
fi
```

### 2.6 Dockerfile 拆花括号（修复 v3-#9）

```dockerfile
# 原版（dash 不展开花括号）：
# RUN mkdir -p /opt/myblog/{logs,frontend,db,db/backups,uploads,scripts,releases}
# 
# 修复：拆成显式多目录
RUN mkdir -p \
    /opt/myblog/logs \
    /opt/myblog/frontend \
    /opt/myblog/db \
    /opt/myblog/db/backups \
    /opt/myblog/uploads \
    /opt/myblog/scripts \
    /opt/myblog/releases
```

**根因**：Dockerfile 的 `RUN <cmd>` 走 `/bin/sh -c`，ubuntu:22.04 的 `/bin/sh` 是 dash，不支持 brace expansion。原版会创建一个名字字面 `{...}` 的目录，导致 supervisord 的 `stdout_logfile=/opt/myblog/logs/*.log` 写不出来 → redis/nginx FATAL 起不来。

**为什么 deploy-server.sh §3 那行同样的 `{...}` 没问题**：脚本 shebang 是 `#!/bin/bash`，走 bash 展开。问题只在 Dockerfile 这一层 RUN。

### 2.7 supervisord.conf 配套改动（修复 v2-#4）

```diff
+[include]
+files = /etc/supervisor/conf.d/*.conf
+
 [program:redis]
 [program:nginx]
-[program:myblog]    ← 删除（避免和 §8 写的 conf.d 重复 + 失效）
```

## 4. 已知限制

1. **`run-myblog.sh` 时序依赖**：必须在 §8 之前生成 `myblog.env`（§7.5）。已验证 deploy-server.sh 执行顺序：§5 部署 jar → §7 写 application.yml → §7.5 写 env 文件 → §8 写 unit/run-myblog.sh → §8.5 数据导入（可选）→ §9-§13。顺序正确。

2. **supervisord 不支持 `EnvironmentFile=`**：本质差异，必须用 `run-myblog.sh` 中转。已在 heredoc 里加注释说明此设计。

3. **supervisord 不支持 `After=` 依赖**：靠 priority 隐式表达。当前 baked redis=10, nginx=20，conf.d myblog=30，启动顺序正确。

4. **`User=myblog` 没了**：容器内用 root 跑 jar，生产安全模型本地不模拟。

5. **`LimitNOFILE=65536` 没了**：容器内默认 65536，不需要设。

6. **`Stop_app()` 在 §5 调用 supervisorctl 不可行**：supervisord 此时还没读到 myblog 配置（§8 才写），stop 不到。已改为容器内 §5 跳过 stop（§8 restart 会自然重启）。

## 5. 同步策略

- 本地模式代码在 `deploy-server.sh` 里，生产脚本更新时本地模式自动 sync
- **有 1 处需要手动同步**：如果生产 §8 的 systemd unit 内容改了（比如加 JVM 参数），本地模式 `run-myblog.sh` heredoc 也要同步改
- **Dockerfile 是容器专属**，与生产无关
- 建议：每次改 §8 后跑 `bash docs/scripts/verify-sqlite.sh` + `docker exec myblog-sim bash -c "deploy-server.sh --dry-run"` 验证（dry-run 后续可加）
