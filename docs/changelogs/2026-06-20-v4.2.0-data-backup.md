## 背景

生产服务器上的数据（SQLite db + uploads）目前没有任何自动备份机制。
故障 / 误操作 / 部署事故一旦发生，数据无法回滚。

需要 admin 后台一键触发 → 自动加密 → 上传到独立 GitHub 仓库 Release 的能力，
便于随时下载恢复。

## 新增

### 后端

- `BackupRecord` 实体 + `BackupRecordMapper`（CRUD + countRunning 并发控制）
- `BackupService`（核心）
  - `triggerBackup(HttpServletRequest)` — 创建 PENDING 记录 → @Async 启脚本
  - 同步等待脚本退出（1h 兜底超时）
  - 解析 `.result.json` → 更新 record（SUCCESS / FAILED）
  - 状态机：`PENDING → RUNNING → SUCCESS / FAILED`
  - 并发保护：已有 RUNNING 任务时抛 `BACKUP_CONFLICT(3001)`
  - 失败信息自动脱敏：截断到 500 字符
- `BackupController` — 3 个 admin API：
  - `POST /api/v1/admin/backup/run` — 触发（异步，立即返回 record id）
  - `GET  /api/v1/admin/backup/list` — 历史分页
  - `GET  /api/v1/admin/backup/{id}` — 详情 + 状态（前端轮询用）
- `BackupResponse` DTO（覆盖 run / list / get 三种响应）
- `ResultCode.BACKUP_CONFLICT(3001, "已有正在执行的备份任务,请等待完成后再试")`
- `BlogApplication.@EnableAsync` 启用异步支持
- 加密：复用 `sqlite-export.sh` 的 AES-256-CBC + PBKDF2 100k 链路
  - `BACKUP_ENCRYPTION_PASSWORD` env 模式（patch sqlite-export.sh 的 `prompt_password_twice`）
  - 优先 `BACKUP_ENCRYPTION_PASSWORD` > `DB_EXPORT_PASSWORD` > 交互式两次输入
  - 不破坏现有 dev/publish-release 流程

### 前端

- `pages/admin/backup.vue` — 数据备份管理页
  - 顶部「立即备份」按钮（二次确认 + 防误触）
  - 触发后前端轮询 `/admin/backup/{id}`（每 2s）
  - 历史列表（ID / 状态 / Tag / 失败阶段 / 触发时间 / 耗时 / db 大小 / uploads 大小 / 资产数 / 操作人）
  - 失败记录红色高亮 + errorStage + errorMessage tooltip
  - 成功记录显示 SHA256SUMS / asset URL
- `layouts/admin.vue` 菜单调整
  - 「系统」分组新增「数据备份」入口，**放在「设置」上方**（用户原话）

### 数据库

新增 `backup_record` 表（SQLite / MySQL schema 都加）：

- `id` / `tag` / `status` / `started_at` / `finished_at` / `db_size` / `uploads_size`
- `asset_count` / `asset_urls` (JSON) / `manifest_json` (原文)
- `error_stage` (DUMP/PACK/UPLOAD/SCRIPT) / `error_message` (脱敏)
- `operator_id` / `operator_name`
- 索引：`started_at DESC`、`status`

### 脚本

- `scripts/blog-backup.sh` — 服务器端核心执行脚本（v4.2.0 新增）
  - 8 步流程：预检 → 准备 stage → 加密 db → 加密 uploads → manifest → SHA256 → 上传 → 完成
  - 加密：调 `sqlite-export.sh`（db）+ `tar | openssl enc`（uploads）
  - 上传：优先 `gh release create`，fallback `curl + GitHub REST API`
  - trap EXIT/INT/TERM 清理明文中转（`/tmp/blog-backup-stage`）
  - `DRY_RUN=1` 模式可调试
  - `SKIP_DB=1` / `SKIP_UPLOADS=1` 单独备份
  - 退出码 0=成功 / 10=预检 / 11=db dump / 12=uploads / 13=manifest / 14=sha / 15=release / 16=upload
- `sqlite-export.sh` 补丁（向后兼容）：
  - `prompt_password_twice` 顶部加 `BACKUP_ENCRYPTION_PASSWORD` / `DB_EXPORT_PASSWORD` env 模式
  - 优先级：env > 交互式

### 部署集成

- `publish-release.sh`：把 `blog-backup.sh` 拷到 release assets + 加入 ZIP + 加入 SHA256SUMS
- `deploy-server.sh`：下载 `blog-backup.sh` → 装到 `$INSTALL_DIR/scripts/blog-backup.sh`
- `deploy-server.env.example`：加 `BACKUP_ENCRYPTION_PASSWORD` / `GITHUB_BACKUP_REPO` / `BACKUP_GITHUB_TOKEN` 模板
- `deploy-server.sh` 首次自动生成 `/etc/myblog/myblog.env` 时加这 3 个 KEY（默认 `REPLACE_ME_` 占位）
- `BackupService` 走 `@Value` 从 `application-prod.yml` / env 读 env
  - `BACKUP_ENCRYPTION_PASSWORD` / `BACKUP_GITHUB_TOKEN` / `GITHUB_BACKUP_REPO`
  - `SQLITE_PATH` / `UPLOAD_DIR` / `INSTALL_DIR`
  - `blog.backup.script.path`（默认 `/opt/myblog/scripts/blog-backup.sh`）
  - `blog.backup.timeout.sec`（默认 3600）
  - `blog.backup.keep.records`（默认 30）

## v4.2.0 修复合并（2026-06-20 同日 PR review 后）

**5 个 bug 在同日 review 阶段发现并修完**：

1. **P0-1** `.result.json` 竞争条件：原写到 `$STAGE_DIR/.result.json` → trap `rm -rf $STAGE_DIR` 误删 → Java 永远读不到 → SUCCESS 备份被标 FAILED
   - 修：result 写到 `$STAGE_DIR_PARENT/.blog-backup-result.$recordId.json`（STAGE_DIR 之外）
   - 配合：Java 侧通过 `@Value` 注入 `BACKUP_STAGE_DIR`，两遍路径对齐
2. **P0-2** `destroyForcibly()` (SIGKILL) 不可被 bash trap 捕获 → 明文 tar 残留磁盘
   - 修：先 `process.destroy()` (SIGTERM) → 等 5s → 才 `destroyForcibly()` 兜底
   - 配合：Java 侧 `forceCleanStageDir()` 兜底清理
3. **P1-1** Java 侧 `Paths.get(java.io.tmpdir, "blog-backup-stage", ".result.json")` 硬编码 → 跟 shell 走 `BACKUP_STAGE_DIR` env 完全错位
   - 修：`@Value("${BACKUP_STAGE_DIR:/tmp/blog-backup-stage}")`，env 透传给脚本
4. **P1-2** `ProcessBuilder(backupScriptPath)` 直接执行脚本，依赖 `chmod +x`
   - 修：`new ProcessBuilder("bash", backupScriptPath)`，不依赖文件权限位
5. **P2** `BACKUP_KEEP_RECORDS` 配置项是死代码——Service 里 `keepRecords` 字段从未被调过
   - 修：实现 `trimOldRecords()`，每次备份完成后异步调一次，db + GitHub Release 双清
   - 优先用 `gh release delete`，fallback `curl + REST API`
   - 设为 0 表示"不清理"（向后兼容默认值 30）

## 升级 / 部署步骤

```bash
# 0. 初始化备份仓库（必须有 main 分支, 否则 gh release create --target main 失败）
#    全新空仓第一步: push 一个空 commit 到 main
mkdir my-blog-backup && cd my-blog-backup
git init && git checkout -b main
echo "# my-blog-backup (private)" > README.md
git add . && git commit -m "init"
gh repo create yourname/my-blog-backup --private --source=. --remote=origin --push
#    或网页端: GitHub → New repo → 勾 "Add a README file" → 直接创建（自动建 main）

# 1. 首次部署前：Settings → 生成 PAT（repo 权限）
#    仓库名: yourname/my-blog-backup

# 2. publish release（带 blog-backup.sh）
export GITHUB_TOKEN=ghp_xxx
export GITHUB_REPO=yourname/my-blog-prov
bash scripts/publish-release.sh

# 3. 服务器端首次部署：跑 deploy-server.sh
sudo bash /opt/myblog/scripts/deploy-server.sh v4.2.0

# 4. ssh 上服务器填 3 个 env
sudo vim /etc/myblog/myblog.env
#   BACKUP_ENCRYPTION_PASSWORD=...  (openssl rand -base64 24)
#   GITHUB_BACKUP_REPO=yourname/my-blog-backup
#   BACKUP_GITHUB_TOKEN=ghp_xxx  (注意是 BACKUP_GITHUB_TOKEN, 不是发布用的 GITHUB_TOKEN)

# 5. 重启
sudo systemctl restart myblog

# 6. 登录 admin → 侧边栏「数据备份」→ 点「立即备份」→ 等 30-60s
#    去 GitHub https://github.com/yourname/my-blog-backup/releases 看 release
```

## 安全考虑

按 AGENTS.md §4.8 P0 安全类：

| 事件 | 级别 | 字段 |
|---|---|---|
| 备份启动 | INFO | operator_id, request_ip |
| 备份成功 | INFO | record_id, tag, size, duration_sec |
| 备份失败 | WARN | record_id, error_stage, error_message (脱敏) |
| 非 admin 触发 | WARN | request_ip, uid |
| 已有 RUNNING 任务 | WARN | record_id |
| 脚本被 kill | WARN | record_id, signal |

**禁打**（4 类硬线）：

- 密码明文 / `BACKUP_ENCRYPTION_PASSWORD` 值
- GitHub token
- 上传文件内容
- 解密后的 db 内容

**实现**：

- 密码/token 走 env / ProcessBuilder 内存，**不进命令行 → 不进 ps**
- `.progress` 文件只记阶段标识（`DB_DUMP_OK:5242880`），不记数据
- `error_message` 字段只取脚本 stdout/stderr 最后 500 字符
- 备份明文中转目录 trap EXIT/INT/TERM 清理，shred 优先

## 已知限制

1. **GitHub release 单 asset 2GB 上限**：uploads 接近 1.5GB 时 WARN（不让用户卡死）。后续 OPT 项：分卷 + 自动拆包
2. **首次部署必填 env**：`BACKUP_ENCRYPTION_PASSWORD` / `GITHUB_BACKUP_REPO` / `BACKUP_GITHUB_TOKEN` 在 `myblog.env` 默认占位，未填时 admin 点"立即备份"会报错
3. **单并发**：同时只允许 1 个备份任务（防 SQLite 锁 + uploads 拉两遍）。已有 RUNNING 时返回 3001
4. **不内置 cron**：本期只做"点击菜单触发"。cron / systemd timer 留作后续 OPT 项
5. **不内置恢复**：本期只做"备份"，恢复走现有 `sqlite-import.sh` + 手动 `openssl enc -d`，命令在 release notes 里
6. **gh CLI 优先**：服务器没装 gh CLI 时 fallback 到 curl + REST API（多 30% 代码量但覆盖更广）
