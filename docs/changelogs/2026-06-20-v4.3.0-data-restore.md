## v4.2.0-restore.2 补丁（2026-06-21）

### 严重-2 修复：TOCTOU 竞态

countRunning() → insert() 之间存在并发窗口，两个请求同时通过检查后会同时建 PENDING → 同时跑脚本 → 同时 stop myblog + 覆盖 db。

**修复**：用 SQLite partial unique index 在数据库层强保证。

```sql
CREATE UNIQUE INDEX uk_backup_record_running
  ON backup_record(status) WHERE status = 'RUNNING';
CREATE UNIQUE INDEX uk_restore_record_running
  ON restore_record(status) WHERE status = 'RUNNING';
```

Java 侧捕获 `UNIQUE constraint failed` 转 `BACKUP_CONFLICT`（应用层 countRunning 还在，作为快速路径）。

### 中-1 修复：sudoers 通配符精确化

原 `chown -R myblog:myblog /opt/myblog/*` 通配符过宽，理论上可被路径穿越（如 `/opt/myblog/../../etc/shadow`）。

**修复**：精确到 4 条路径：
- `/opt/myblog/blog.db`
- `/opt/myblog/blog.db.bak.*`
- `/opt/myblog/uploads`
- `/opt/myblog/uploads/*`

### 中-2 修复：cp 改 sqlite3 .backup

SQLite WAL 模式下 `cp blog.db blog.db.bak.*` 只复制主文件，`-wal` 和 `-shm` 里未 checkpoint 的数据丢失，.bak 可能不完整。

**修复**：用 `sqlite3 .backup` (online safe backup)，包含完整一致状态。

### 中-3 修复：前端轮询超时阈值 + 注释

注释写 "5 分钟"，实际 backoff 序列 [2,4,8,16,30...] 60 次累计 ~28 分钟。

**修复**：阈值改 30 次（5-15 分钟），注释同步更新。

### 中-4 修复：ACTUAL_COUNTS 空表防护

空 db 没有业务表时，`paste -sd ','` 空输入 → 输出 `{\n}` → 与 EXPECTED 差异导致虚假 verify_diff。

**修复**：用 `awk 'BEGIN{print "{"} ... END{print "}\n"}'` 兜底 + jq 校验失败时 fallback 到 `{}`。

### 小-4 修复：前端轮询首 tick 重复

`tick()` 立刻调用一次 + `schedule()` 2s 后再调一次 → 0s + 2s 两次请求。

**修复**：去掉直接 `tick()` 调用，让 schedule 自然调度（首次 2s 后）。

## v4.2.0-restore.3 补丁（2026-06-21）

### 严重修复：chown sudoers 与脚本命令不匹配

v4.3.2 拆 sudoers 时自留的 bug：

```bash
# 脚本原写法 (line 379): 一条 sudo chown 传两个路径
sudo -n chown -R myblog:myblog "$SQLITE_PATH" "${UPLOAD_DIR}"   # 命令行 2 个参数

# sudoers 写法: 4 条独立规则, 每条 1 个路径
myblog ALL=(root) NOPASSWD: /usr/bin/chown -R myblog\:myblog /opt/myblog/blog.db
myblog ALL=(root) NOPASSWD: /usr/bin/chown -R myblog\:myblog /opt/myblog/blog.db.bak.*
myblog ALL=(root) NOPASSWD: /usr/bin/chown -R myblog\:myblog /opt/myblog/uploads
myblog ALL=(root) NOPASSWD: /usr/bin/chown -R myblog\:myblog /opt/myblog/uploads/*
```

sudoers 按完整命令行精确匹配，脚本这条 `chown db uploads` 跟 4 条都对不上 → 100% 被拒 → write_result FAILED + exit 25 → 永远到不了 step 11 启服 → 恢复永远失败。

**修复**：脚本里拆成两条独立 `sudo -n chown`：
```bash
sudo -n chown -R myblog:myblog "$SQLITE_PATH"               # 对应 sudoers 第 1 条
sudo -n chown -R myblog:myblog "$UPLOAD_PATH"               # 对应 sudoers 第 3 条
```

`UPLOAD_DIR` 不存在时优雅降级（warn + 跳过），不阻断恢复。

## 背景

v4.2.0 实现了"数据备份 → GitHub Release"（`blog-backup.sh`），但没有"从 GitHub Release 恢复"的链路。
本版本补齐最后一块：用户在 admin 的「数据备份」页面单选一条 SUCCESS 备份 → 点「数据恢复」→ 服务停 1-5 分钟覆盖式恢复 → 启服 + 健康检查 + 数据校验。

## 关键设计要点

### 进程模型：systemd-run --scope 进独立 cgroup

```
JVM (myblog.service cgroup)
  └─ sudo systemd-run --scope --slice=myblog-restore --unit=blog-restore-<id>
       --uid=myblog --gid=myblog /bin/bash blog-restore.sh
                            │
                            ▼
                  新 cgroup: myblog-restore.slice/blog-restore-<id>.scope
                  (跟 myblog.service 不在同一 cgroup)
                            │
                            └─ 脚本 systemctl stop myblog ← 只杀 myblog.service cgroup, 杀不到这里
```

- **setsid 不行**（只改 session/process-group，不迁移 cgroup）
- **sudoers 必须精确到脚本路径**（末尾不能 `*` 通配符 → myblog 可 `sudo ... bash -i` 拿 root shell）
- **--uid=myblog 必加**（否则 scope 内进程是 root，写出的 db/uploads 属主不对）

### 状态回填：双轨

1. **ApplicationReadyEvent** 启动时跑一次
2. **@Scheduled(fixedDelay = 5min)** 定时巡检

回填逻辑：
- 无条件扫所有 RUNNING（不带 started_at < now - 30min 过滤 —— 这个过滤让 v2 永远捞不到正常完成的 RUNNING）
- 有 `.result.json` → 按它标 SUCCESS/FAILED，删 result 文件
- 没 result + 超 30min → 标 UNKNOWN（孤儿）
- 没 result + 时间不到 → 还在跑，跳过

### 双向并发互斥

`BackupService.triggerBackup` 和 `RestoreService.triggerRestore` 都查两个表的 RUNNING，避免：
- 恢复期间触发备份 → 备份读半截 db
- 备份期间触发恢复 → 两边争资源

## 部署步骤（生产首次上线）

1. 部署 jar（deploy-server.sh, DEPLOY_MODE=code）
2. 部署新脚本：手 copy 到 `/opt/myblog/scripts/blog-restore.sh`
3. 安装 sudoers：`install -m 0440 sudoers-myblog-restore.example /etc/sudoers.d/myblog-restore`
4. 创建 result 目录：`mkdir -p /var/lib/myblog/restore-results && chown myblog:myblog && chmod 700`
5. 应用 schema 更新（deploy-server.sh §7 会跑 schema-sqlite.sql，新表 restore_record 自动建）
6. 重启 JVM（让 RestoreStartupReconciler 注册 @EventListener 和 @Scheduled）
7. 进 admin /backup 页面，选一条 SUCCESS 备份测试恢复
