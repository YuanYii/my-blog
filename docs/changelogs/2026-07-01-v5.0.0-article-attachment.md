## 关键决策

### D-01 一文一附件
`article_id UNIQUE` 约束（DB 层兜底）+ `try-insert + catch UNIQUE`（业务层跨方言一致）。不引入 SELECT-then-INSERT 的 TOCTOU 竞态。

### D-02 流式响应
公开下载走 `ResponseEntity<InputStreamResource>` + `FileInputStream`，**不**读 `byte[]` 中转（避 OOM，大文件友好）。

### D-03 路径防穿越
`Paths.get(attachmentDir).resolve(filePath).normalize()` + `startsWith(attachmentDir.normalize())` 双层校验，防 `../etc/passwd`。

### D-04 中文文件名 RFC 5987
`URLEncoder.encode(fileName, "UTF-8").replace("+", "%20")` + Content-Disposition 双字段，浏览器按 RFC 5987 优先解析 UTF-8。

### D-05 attachments 独立打包
`blog-backup.sh` 与 uploads 并列独立 asset，attachments 失败不连带 uploads；接近 2GB 警告而非 fail。

### D-06 防多点击下载
组件级 `downloadLock` ref + `setTimeout` 30s 解锁，不依赖全局 store。

### D-07 useFileSize 自实现
B/KB/MB 三档格式化，不引 npm 包。

## 本轮 4 个开发期修复（autodev Stage 5 实测发现，本轮一并修复）

### 修复 1 — MyBatis-Plus 全局 logic-delete 绕过

**症状**：`list(deleted=1/all)` 返 0 条；`getById` 找不到软删记录（restore/hardDelete 走 `selectById` 必返 1001）

**根因**：`application.yml` 全局配置 `mybatis-plus.global-config.db-config.logic-delete-field: deleted` 让带 `deleted` 字段的实体自动加 `AND deleted=0` 过滤

**修复**：`AttachmentService.list` / `getById` / `getByArticleIdIncludeDeleted` 改用 `JdbcTemplate` 直查直读，绕过框架自动过滤

**未来优化**：可考虑全局 logic-delete 改为**显式 `@TableLogic` 注解**（更明确），但当前项目沿用全局默认，绕开是最小改动

### 修复 2 — SQLite UNIQUE 异常翻译

**症状**：重复上传返 500 而非 400

**根因**：Spring `JdbcTemplate` 把 SQLite 的 UNIQUE 冲突包成 `UncategorizedSQLException`（嵌套 `SQLiteException`），原 try-catch `DataIntegrityViolationException` 没接住

**修复**：catch `Exception` + 字符串匹配 `UNIQUE constraint failed` / `SQLITE_CONSTRAINT_UNIQUE`，是则翻译为 `BusinessException(400, "请先删除旧附件")`

**参考**：`ArticleService.insertArticleTagIfNotExists` 同模式（catch 嵌套检查）

### 修复 3 — getByArticleId 软删过滤导致 1001 而非 410

**症状**：软删下载返 1001「附件不存在」（应该是 410）

**根因**：原 `getByArticleId` 用 `qw.eq("deleted", 0)` 过滤，软删记录查不到 → resolveFile(null) 抛 1001

**修复**：新增 `getByArticleIdIncludeDeleted(articleId)` 方法（走 JdbcTemplate 不过滤），公开下载控制器调用此方法；`resolveFile` 内部仍按 deleted 状态判 410

### 修复 4 — SQLite JDBC 时间戳解析

**症状**：JdbcTemplate 查询抛 `ParseException: Unparseable date "2026-07-01T10:37:09.968"`

**根因**：项目历史数据混存 ISO 8601（MyBatis-Plus 写入）与 `yyyy-MM-dd HH:mm:ss`（早期手写）两种格式；SQLite JDBC 的 `getTimestamp` 只支持后者

**修复**：抽 `parseTimestamp(String)` 工具方法先尝试 `LocalDateTime.parse` (ISO 8601)，失败再回退 `replace("T", " ")`（`yyyy-MM-dd HH:mm:ss`）

## API 设计

| 方法 | 路径 | 鉴权 | 说明 |
|------|------|------|------|
| GET | `/api/v1/articles/{id}/attachment` | 公开 | 流式下载；软删/不存在返 410 |
| POST | `/api/v1/admin/articles/{id}/attachment` | admin | 上传（multipart）|
| DELETE | `/api/v1/admin/articles/{id}/attachment` | admin | 软删（文章维度入口）|
| GET | `/api/v1/admin/attachments?deleted=0\|1\|all&page=N` | admin | 后台列表 |
| DELETE | `/api/v1/admin/attachments/{id}` | admin | 硬删（文件 + DB）|
| PUT | `/api/v1/admin/attachments/{id}/restore` | admin | 恢复 |

**业务码**：
- `400` 文件超过 5MB / 仅允许 zip / 请先删除旧附件（竞态）
- `410` 附件已删除 / 附件文件已丢失
- `1001` 文章不存在 / 附件不存在（已硬删）

## 反思

1. **Stage 5 集成测试必须有端到端实测**：本轮发现 4 个开发期修复，全部靠 myblog-sim 容器实测发现（光看代码 + 静态审计看不出 SQLite UNIQUE 异常翻译问题、SQLite JDBC 时间戳解析问题）

3. **跨方言兼容性测试不可省略**：SQLite 与 MySQL 在异常翻译、UNIQUE 约束、ISO 8601 时间戳解析上有差异——单测一种方言会漏掉另一种方言的 bug
4. **autodev 流水线对开发期修复有很好的"自纠错"机制**：本轮 4 个修复全部在 Stage 5 集成测试时发现 + 立即修复 + 立即回归，符合"无人值守闭环"设计意图
