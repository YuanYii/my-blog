## 一、PageView 异步写库（性能：首页 /articles 等公开接口响应不再等 SELECT+INSERT）

### 新增文件

- `backend/blog-article/src/main/java/com/blog/article/config/AsyncConfig.java`（39 行）— `@EnableAsync` + `pageViewExecutor` 线程池（core=2 / max=4 / queue=500 / `DiscardPolicy`）

### 改动

- `PageViewService.recordVisit(...)` → `recordVisitAsync(...)`
  - 加 `@Async("pageViewExecutor")` 注解
  - 签名去掉 `HttpServletRequest` 形参，改收 `ip / userAgent / referer` 三个 String（filter 在请求线程内同步取出后传入）
- `PageViewFilter.recordPageView(...)`
  - 同步调用 `pageViewService.recordVisit(...)` → 异步调用 `pageViewService.recordVisitAsync(sub, articleId, visitor, ip, userAgent, referer)`
  - 在调用前同步取 `ip / userAgent / referer`（异步执行时 `HttpServletRequest` 可能已被容器回收）

### 设计取舍

- 队列满走 `DiscardPolicy`：PV 统计是 best-effort，绝不能反压业务线程
- 核心池故意小（core=2 max=4）：SQLite 仍是单写者，过多写线程无益

## 二、SQLite WAL + 连接池优化（性能：首页 7 个公开接口不再串行排队）

### 改动

- `application-dev.yml` / `application-prod.yml`
  - URL 加 `?journal_mode=WAL&busy_timeout=10000&synchronous=NORMAL`
    - WAL 让"多读 + 单写"可并发（读不再被写阻塞）
    - `busy_timeout=10000` 让偶发写竞争等待而非立刻抛 `SQLITE_BUSY`
    - `synchronous=NORMAL` 在 WAL 下兼顾安全与吞吐
  - Hikari 池：`maximum-pool-size: 1` → `8`，`minimum-idle: 1` → `2`（WAL + busy_timeout 下连接池才可安全 >1）
- `application-prod.yml` — CORS 默认域从 `https://yourname.com` 改成 `https://blog.croeyai.cn`（已确认的唯一生产域名）

### 顺手修复

- `application-prod.yml` — `blog.jwt.expiration-ms` → `blog.jwt.expiration`
  - 原 key 跟 `JwtUtil.@Value("blog.jwt.expiration:86400000")` 不匹配 → prod yml 改的 24h 永远不生效，实际用的是代码默认 86400000（值刚好都是 24h，没造成实际 bug，但配置无效是隐患）
  - 改 key 后 yml 真正生效

## 三、slug 负缓存修复（健壮性：防爬虫狂打随机 slug 导致 map 无界增长）

### 改动

- `PageViewFilter.resolveArticleId(...)`
  - 原写法对不存在的 slug（`findArticleIdBySlug` 返回 `null`）执行 `bucket.put("id", null)` → `ConcurrentHashMap` 抛 NPE 被外层 try/catch 吞掉，缓存形同虚设
  - 改用 `-1L` 哨兵值（`NEG_CACHE_SENTINEL`）表示"slug 不存在"，TTL 缩到 1 分钟（正缓存仍 5 分钟）
  - 命中负缓存时 `resolveArticleId` 返回 `null`，`page_view` 表仍会写一行（无 articleId），但 DB 不再反复查 + SLUG_CACHE 不再无界膨胀

## 四、前端 composable 修复

### `frontend/composables/useAdminApi.ts`

- `onResponse` 钩子之前对所有响应都执行业务 code 检查，导致真正的 HTTP 401/403 错误被这里截胡 → `onResponseError` 里"清空 token + 跳转 /admin/login"永远执行不到（会话失效后页面停留在原地，只看见 toast）
- 两处 `onResponse` 都加 `if (!response.ok) return` 守卫：只在 HTTP 本身成功（2xx）时才识别"业务错误码"，真正的 HTTP 错误交给 `onResponseError` 处理

### `frontend/composables/useApi.ts`

- 删掉 `import { useAdminApi } from './useAdminApi'`，改靠 Nuxt auto-import
- Nuxt 3 的 composables 必须自包含（不互相 import），互相 import 会破坏 auto-import 扫描顺序，导致 Vite 编译出的 setup 函数里部分 composable（比如 `usePublicApi`）没被注入，运行时 `ReferenceError`
