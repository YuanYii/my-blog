# v4.4.0 (2026-06-23) — 部署模式重构

> 需求 ID: REQ-DEPLOY-MODE-REFACTOR-2026-06-23
> 设计依据: `docs/项目部署操作手册.md` §1.3 速查表
> 实现方式: 模式集合从 7 精简到 4，本地容器从手工流程升级为 deploy-server.sh 一行命令

## 背景

原 `DEPLOY_MODE` 有 7 种（`init` / `full` / `code` / `frontend` / `backend` / `sql` / `data`），过度细分导致：

- 手册 §1.3 速查表 5 列信息冗余（`code` ≡ `full`，`data` 等价 `full + IMPORT_DB=1`）
- 用户决策成本高（"该用 `frontend` 还是 `full`"）
- 脚本里 7 个 case 分支维护成本高

重构后精简为 **4 种模式**：

| 旧模式 | 新模式 | 行为差异 |
|---|---|---|
| `init` | `init`（保留）| 不变 |
| `full` | `full`（保留）| 不变，吸收 `code` 等价语义 |
| `code` | `full` | 零差异（`code` 等价 `full`，删除）|
| `data` | `full + IMPORT_DB=1` | 显式开环境变量 |
| `frontend` | `full` | 升级前端必须连带 jar 重 build（~30s vs 60s）|
| `backend` | `full` | 升级后端必须连带前端重 build（~60s 差异不大）|
| `sql` | `full` | 删手册 §6 增量 SQL 场景章节，纯 SQL 升级必须跑全量 |
| —— | `docker-create`（新增）| 本地容器创建（build + run myblog-sim）|
| —— | `docker-init`（新增）| 本地容器业务初始化（docker cp + exec 跑部署）|

## 兼容性 & 迁移路径

### 5.1 老用户从 7 模式切到 4 模式

**已在用的功能**（行为不变）：

- 用 `code` → 改 `full`（零差异）
- 用 `data` → 改 `full` + 加 `IMPORT_DB=1`
- 用 `frontend` / `backend` / `sql` → 改 `full`（接受变慢，但功能完整）

**已删除的功能**（功能仍在，只是粒度退化）：

- `frontend` 的"只刷前端 30s"→ 现在必须跑全量 60s
- `backend` 的"只刷后端 60s"→ 现在必须跑全量 60s（差异不大）
- `sql` 的"只跑 SQL migration"→ 现在必须跑全量（删手册 §6 章节）

**触发报错信息**（不静默忽略）：

```
DEPLOY_MODE must be init / full / docker-create / docker-init, got: frontend
Note: code/frontend/backend/sql/data were removed in v4.4.0, use 'full' instead
```

### 5.2 老 release 上的 deploy-server.sh 仍支持 7 模式

`publish-release.sh` 把每个 tag 的 deploy-server.sh 都封进 release assets。**回滚到老 release 等于回滚到老 7 模式**——这是天然的回滚机制。

## 风险与回滚

**风险点**：

1. 删 `frontend` 模式后，升级前端会触发后端重 build——前端改动很小但 jar 依赖大时，会拖慢升级
2. 删 `sql` 模式后，纯增量 SQL 升级必须跑全量——对纯 DBA 场景不友好
3. 新增 `docker-create` / `docker-init` 是全新代码路径——bug 概率高，需要先在小环境验证

**回滚步骤**：

```bash
# 1. 服务器端:拉老 release 的 deploy-server.sh
curl 老-release 的 deploy-server.sh + 跑老版本

# 2. 本地:git revert 这次重构 commit + 重新 publish-release
```
