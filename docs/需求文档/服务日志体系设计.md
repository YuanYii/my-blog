## 1. 背景

my-blog 当前部署在 VPS 1C2G 单机（Spring Boot 2.7 + Nuxt 3 全静态 + SQLite + Redis 7.x），单一 owner 线上排查问题使用。

当前日志体系现状（基于代码摸底）：

- **日志框架**：Spring Boot 2.7 默认 Logback + SLF4J 已生效，6 个类已声明 `@Slf4j`（PageViewFilter、PageViewService、GlobalExceptionHandler、ApiWhitelistService、CommentController、SiteSettingsService）。
- **缺失项 A**：无自定义 `logback-spring.xml`，仅有控制台输出；部署到 ECS 后日志无法落盘，进程重启即丢失。
- **缺失项 B**：admin 鉴权核心链路（AdminAuthFilter、AuthController 登录、DeviceService、JwtUtil）**完全无日志**，无 `traceId`，线上出现"被踢回登录页""设备被吊销"等问题时无法溯源。
- **缺失项 C**：前端报错无可读关联 ID，用户反馈"我刚才操作失败了"时无法对日志定位。

## 2. 目标与范围

### 2.1 业务目标

1. **可追溯**：任何 admin 鉴权拒绝、登录失败、设备白名单事件均能在落盘日志中找到完整链路（含 IP、username、deviceId）。
2. **可关联**：前端报错时能拿到一个 traceId，owner 据此在日志中 grep 出该请求从 filter → controller → service 的全部上下文。
3. **可回溯**：部署期间产生的关键事件至少保留 30 天，便于事后复盘。

### 2.2 非目标（本期不做）

- 分布式追踪 / Zipkin 上报
- 日志聚合 / ELK 接入
- 结构化 JSON 日志
- 业务层 `@Async` / `CompletableFuture` 的 MDC 透传
- 慢 SQL 专项监控（MyBatis-Plus 自带 SQL 日志已开）
- 日志告警（邮件 / 钉钉 / webhook）

### 2.3 用户故事

| 编号 | 角色 | 故事 | 验收 |
|---|---|---|---|
| US-1 | Owner | 我作为 owner 排查"为什么某次 admin 操作被踢"，能在 `/opt/myblog/logs/` 找到该请求的 WARN 级日志，包含 traceId、path、IP、拒绝原因 | 日志存在 + 包含以上四要素 |
| US-2 | Owner | 我作为 owner 排查"某 IP 是否在暴力破解登录"，能 grep 出该 IP 在登录失败时的所有 WARN 日志 | 日志存在 + 含 IP + username |
| US-3 | Owner | 用户报告"管理后台某按钮报错"，用户从浏览器 devtools 复制 X-Trace-Id 给我，我能用这个 ID grep 出完整请求链路 | traceId 在响应头 + 日志中均可见 |
| US-4 | Owner | 我部署后 30 天内的日志可查询，超过 30 天的日志自动清理 | `du -sh /opt/myblog/logs` 不超过 3GB（**注**：systemd 重定向的 app.log / app-error.log 由 logrotate 单独管理，保留 7 天，不计入 30 天 Logback 滚动周期） |
| US-5 | Owner | dev 模式开发时日志同时输出到控制台和 `/tmp/blog-dev-logs/`，方便本地调试 | 两处都能看到日志 |

## 3. 需求详述

### 3.1 功能需求

#### FR-1 日志落盘 + 滚动 + 自动清理

**描述**：服务运行产生的日志必须落盘，按天滚动，单文件超过阈值自动切割，自动清理过期文件。

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-1.1 | 配置文件独立于 jar 外的部署路径 | P0 |
| FR-1.2 | 按天滚动（每天 0 点切分） | P0 |
| FR-1.3 | 单文件大小超过阈值自动切割（防单天异常暴涨） | P0 |
| FR-1.4 | 超过保留天数的日志自动清理 | P0 |
| FR-1.5 | 总磁盘占用设上限，超过时优先删最老的 | P0 |
| FR-1.6 | dev / prod profile 路径分离（dev 临时，prod 长期） | P1 |
| FR-1.7 | 异步写日志，不阻塞业务线程 | P0 |

#### FR-2 鉴权链路日志

**描述**：admin 鉴权链路必须能在日志中完整还原"谁、什么时候、从哪个 IP、用哪个设备、访问了什么、为什么被拒或通过"。

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-2.1 | AdminAuthFilter 在每个拒绝点输出 WARN，包含 path / method / IP / 拒绝原因 | P0 |
| FR-2.2 | AdminAuthFilter 在放行时输出 INFO（含 uid / deviceId / path） | P1 |
| FR-2.3 | AuthController.login 在登录成功 / 失败 / 限流触发 时输出日志 | P0 |
| FR-2.4 | 登录日志必须包含 username 和 IP | P0 |
| FR-2.5 | 登录日志禁止输出 password / passwordHash / token 全文 | P0（合规硬线） |
| FR-2.6 | DeviceService 在设备注册 / 授权 / 吊销时输出 INFO | P0 |
| FR-2.7 | DeviceService 在拒绝访问时输出 WARN（含 deviceId 状态） | P0 |
| FR-2.8 | JwtUtil 解析失败时分类输出 WARN（过期 / 签名错 / 格式错）。**实现位置**：try/catch 落在 `JwtUtil.parse()` 内部，分类打 WARN 后**重新抛出**原异常；调用方（如 `AdminAuthFilter`）保持现有 `catch (Exception e)` 简化写法不变 | P1 |

#### FR-3 业务关键节点日志

**描述**：文章 / 评论 / 上传 / 设置修改等核心业务操作的关键路径可追溯。

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-3.1 | 文章 CRUD 在创建 / 更新 / 删除 时输出 INFO（含 slug、操作人） | P1 |
| FR-3.2 | 文章业务校验失败（slug 重复、标签不存在、status 非法）输出 WARN | P1 |
| FR-3.3 | 访客评论提交输出 INFO（含 IP、UA、文章 slug） | P1 |
| FR-3.4 | admin 评论审核 / 拒绝输出 INFO（含操作人 uid） | P1 |
| FR-3.5 | 文件上传成功输出 INFO（路径、大小） | P1 |
| FR-3.6 | 文件上传失败输出 WARN/ERROR（超限 / 类型不符 / IO 异常） | P1 |
| FR-3.7 | 配置修改输出 INFO（key 名、操作人） | P2 |
| FR-3.8 | **view_count 自增等高频操作不输出 INFO**（防日志爆炸） | P0 |

#### FR-4 异常处理

**描述**：业务异常与未预期异常有明确分级，便于过滤。

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-4.1 | 已知业务异常（BusinessException）输出 WARN | P0 |
| FR-4.2 | 未预期异常（Exception）输出 ERROR（含完整 stacktrace） | P0 |
| FR-4.3 | 异常日志必须含 traceId | P0 |

#### FR-5 请求级 traceId

**描述**：每个 HTTP 请求自动获得一个 traceId，从 filter 一直贯穿到 controller / service，日志中可见，响应头回写。

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-5.1 | 入口 filter 自动生成 traceId（或读请求头 X-Trace-Id） | P0 |
| FR-5.2 | traceId 通过 SLF4J MDC 注入，所有日志自动携带 | P0 |
| FR-5.3 | 响应头回写 X-Trace-Id，前端可读 | P0 |
| FR-5.4 | 请求结束后清理 MDC，防线程复用泄漏 | P0 |
| FR-5.5 | traceId 顺序优先于业务 filter，保证鉴权拒绝也能带 traceId。**实现手段**：`@Component` + `@Order(Ordered.HIGHEST_PRECEDENCE)` 显式声明；**不要依赖 Spring Boot 默认 bean 名字母序**（当前项目无 `FilterRegistrationBean`，未来扩展必须显式标注） | P0 |

#### FR-6 日志分层与降噪

**描述**：控制日志量，避免噪声压过信号。

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-6.1 | 业务包 `com.blog` 默认 INFO 级 | P0 |
| FR-6.2 | Spring 框架包 `org.springframework` 默认 WARN 级 | P0 |
| FR-6.3 | PageViewFilter / PageViewService 单独设 WARN（访问量大） | P0 |
| FR-6.4 | dev profile 控制台输出 + 文件双写 | P0 |
| FR-6.5 | prod profile **必须关闭** CONSOLE appender（控制台 stdout 经 systemd 重定向到 `/opt/myblog/logs/app.log` —— 不断写会绕过 NFR-3 的 3GB 容量预算） | P0 |

## 4. 非功能需求

### NFR-1 性能

- 日志写入异步化，业务 P99 延迟受日志影响 < 1ms（VPS 单核敏感）
- 单次请求产生的日志行数上限：5 行（防失控）

### NFR-2 安全

- 任何日志禁止包含：明文密码、passwordHash、token 全文、JWT secret
- 登录失败日志允许包含 username（业务决策，已与设备白名单安全模型配合，详见 AGENTS.md §9.1）
- 日志文件权限 0644，目录 0755，仅 owner 可读

### NFR-3 容量

- 单机磁盘预算：Logback 管理的日志文件总占用 ≤ 3GB
- 30 天保留 + 100MB/文件大小上限 + 总容量上限，三层保险
- systemd 重定向的 `app.log` / `app-error.log` 由 logrotate 单独管（按天切，保留 7 天），**不计入** 3GB Logback 预算

### NFR-4 可运维

- 部署脚本必须确保日志目录存在且权限正确
- 服务异常退出后日志仍能落盘（异步 appender 关闭时 flush）
- 部署脚本必须安装 `/etc/logrotate.d/myblog` 配置，覆盖 Logback 文件 + systemd 重定向文件

## 5. 验收标准

### 5.1 功能验收（每条 US 对应一个验证用例）

| US | 验收步骤 | 预期 |
|---|---|---|
| US-1 | curl 模拟 `/admin/*` 无 token 请求 | 日志含 WARN + traceId + path + IP + "无 token" |
| US-2 | curl 模拟同 IP 6 次错误密码登录 | 日志含 5 条该 IP 的 WARN 登录失败 + 1 条 429 限流 |
| US-3 | 浏览器触发任意错误，从 devtools 复制 X-Trace-Id，grep 日志 | 至少一条匹配，且该请求从 filter 到 controller 完整 |
| US-4 | 部署后查看日志目录 | 文件按天滚动，30 天前的文件不存在 |
| US-5 | dev 模式启动服务 | 控制台 + `/tmp/blog-dev-logs/` 均有输出 |

### 5.2 性能验收

- `bash scripts/verify-sqlite.sh` 跑完后，所有端点 P99 延迟与改动前相比差异 < 5%
- 模拟 1000 次 `/articles/{slug}` 阅读请求后，view_count 自增路径的日志行数 ≤ 5（默认未打 INFO）

### 5.3 安全验收

- `grep -r "passwordHash" /opt/myblog/logs/` 返回空
- `grep -r "Bearer eyJ" /opt/myblog/logs/` 返回空（token 全文不入日志）
- `grep -r "JWT_SECRET" /opt/myblog/logs/` 返回空

### 5.4 容量验收

- 服务运行 7 天后，`du -sh /opt/myblog/logs/` ≤ 1GB（按 100MB/天 估算）

## 7. 风险与缓解

| 编号 | 风险 | 影响 | 缓解措施 |
|---|---|---|---|
| RISK-1 | 日志盘满 1C2G 磁盘 | 服务不可用 | totalSizeCap=3GB + 100MB 单文件 + 30 天清理 |
| RISK-2 | 异步日志线程挂掉丢日志 | 排查时缺数据 | neverBlock=true，丢日志不阻塞业务 |
| RISK-3 | traceId 在异步线程丢失 | 多线程场景关联失败 | 本期不引入 @Async；上分布式追踪时再处理 |
| RISK-4 | view_count 等高频路径误打 INFO | 日志爆炸 | logback 里单独设 WARN + 单请求日志行数上限 |
| RISK-5 | 密码误打日志 | 合规事故 | code review + grep 校验（验收项 5.3） |
| RISK-6 | 部署时未建日志目录 | 服务启动失败 | 部署脚本兜底 `mkdir -p` + Java 启动钩子 |

## 9. 决策记录（关键决策一览）

| 决策点 | 选择 | 理由 |
|---|---|---|
| 日志门面 | SLF4J + Logback（沿用） | Spring Boot 默认，无需新依赖 |
| traceId 长度 | **32 字符**（UUID 去横线） | 唯一性更强，未来对接 Micrometer Tracing 无冲突 |
| MDC key | `traceId` | 兼容未来 Micrometer Tracing |
| 登录日志是否打 username | ✅ 打 | 用户已确认；安全模型有设备白名单兜底 |
| 密码类字段入日志 | ❌ 禁 | 合规硬线 |
| view_count 自增入日志 | ❌ 不打 INFO | 1k PV/天 → 86k 行日志会爆 |
| 日志保留期 | **统一 30 天**（不区分 INFO/WARN/ERROR） | 30 天对单人排查够用；磁盘预算简单可控 |
| systemd 重定向的 app.log / app-error.log | 由 logrotate 单独管，按天切，保留 7 天 | 这两个文件超出 Logback 控制范围，必须单独配 |
| prod CONSOLE appender | **必须关闭** | 防 stdout → app.log 与 Logback 文件双写，绕过 3GB 预算 |
| dev 日志路径 | `/tmp/blog-dev-logs/` | 本地临时 |
| prod 日志路径 | `/opt/myblog/logs/` | 与部署目录一致 |
| 文档落盘 | `docs/需求文档/REQ-LOG-2026-06-18.md` | 与 `docs/设计文档/` 平级 |
| 是否写变更日志 | ❌ 不写（用户决策） | 本期范围明确，无需 v2.x changelog |
| AGENTS.md 是否同步增加 | ✅ 简化增加（一节"日志体系"） | 供未来 agent 启动时自动加载 |
