## 问题 1：路径错误 — 备份脚本找不到数据库

**会话**：`mvs_e2d2fa3ff4a1410e`（Docker备份数据库缺失）

| 项 | 内容 |
|---|---|
| **报错** | `[STEP-DB_DUMP] Database file not found: /opt/backend/blog.db` |
| **根因** | `blog-backup.sh:223` 调 `sqlite-export.sh` 时漏传 db 路径作为位置参数；`sqlite-export.sh:122` `DB_PATH` 默认值是 `backend/blog.db`（v2.6.0 旧的项目相对路径），容器/生产都不存在；实际路径应为 `$INSTALL_DIR/db/blog.db` |
| **解决方案** | ① `blog-backup.sh:223` 调 `sqlite-export.sh` 时显式传 `"$SQLITE_PATH"`；② `sqlite-export.sh:122` `DB_PATH` 默认改为 `$INSTALL_DIR/db/blog.db`；③ 同步到容器（`docker cp`） |
| **状态** | ✅ 已合 `46b09dc`（v4.2.0 commit） |

## 问题 2：依赖缺失 — 容器内 `jq` 未装

**会话**：`mvs_a66fc0d497844fd0`（Docker备份jq命令缺失）

| 项 | 内容 |
|---|---|
| **报错** | `blog-backup.sh: line 476: jq: command not found` → GitHub API 返回 HTTP 422 `"links/0/schema", nil is not an object` |
| **根因** | `blog-backup.sh` line 475/483/484 用 `jq` 解析 GitHub Release API JSON；容器内没装 `jq`；`jq -n` 失败 → `-d` 后的 payload 为空 → API 收到空 body → 422 |

| **状态** | ✅ 已合 `46b09dc`（v4.2.0 commit）；Dockerfile 未动（按用户指示避免牵连） |

## 问题 3：锁竞争 — prod SQLite 没启用 WAL（核心一仗）

**会话**：`mvs_127914a50efd4ac2`（本地Docker数据备份失败）

| 项 | 内容 |
|---|---|
| **报错** | `BackupService` 报 `record_id=20 exit_code=11` + `sqlite-export.sh` 内 `[!] .schema api_whitelist 失败: Error: database is locked` |
| **直接触发** | 用户 19:45–19:55 手点 4 次备份（id=17/18/19/20），全部 exit_code=11 |
| **根因链** | ① 容器内 `PRAGMA journal_mode = delete`、`busy_timeout = 0`（不是 AGENTS.md §4.5 写的 v4.0.0 WAL）；② jar 内 `application-prod.yml` 有 WAL + `busy_timeout=10000`，但 Spring 启动参数 `--spring.config.additional-location=/opt/myblog/application.yml` 让外置 yml 完全覆盖 jar 内 yml；③ `deploy-server.sh:330-348` 第 7 步硬编码写裸 URL `jdbc:sqlite:$DB_FILE`（无 PRAGMA + `pool-size=1`），v2.6.0 配置没跟着 v4.0.0 升级；④ `page_view` 异步写持 PENDING 锁时，dump 进程的 `sqlite3 .schema` 拿新 SHARED 锁被拒秒炸 |
| **错误定位的修正过程** | 第 1 误判"WAL 没生效"→ 第 2 纠正"yml 是有的，但没被加载"→ 真相"deploy 脚本硬编码错 + changelog 漏写 deploy 改动" |
| **解决方案（治本）** | `deploy-server.sh` step 7：URL 改为 `jdbc:sqlite:$DB_FILE?journal_mode=WAL&busy_timeout=10000&synchronous=NORMAL`；`pool-size: 1 → 8`；step 5 全量部署改为"备份旧 DB → 删 → 重建"，避免残留空壳 DB 误判 |
| **解决方案（治标）** | `sqlite-export.sh`：封装 `sqlite3_with_timeout`（统一 `.timeout 30000`）；schema dump 加 4 次退避重试（0/1/2/4s）；Python `sqlite3.connect` 加 `timeout=30`；失败时保留 `TMP_SQL.failed` 现场 |
| **状态** | ✅ 已合 `46b09dc`（v4.2.0 commit，commit message 明确写"治本 + 治标"） |

## 问题 5：设计 bug — 备份时强制清空 `admin_device` 和 `page_view`

**会话**：`mvs_4bc5c08965aa4652`（Docker数据备份恢复测试，用户原话纠正）

| 项 | 内容 |
|---|---|
| **报错** | 备份恢复后 `admin_device=0`、`page_view=0`，但基线分别是 1 和 6 |
| **根因** | `sqlite-export.sh:135` 硬编码 `CLEAR_DATA_TABLES=("admin_device" "page_view")` — 每次导出都清空这两张表的数据（"安全清空"被误用为"备份时清空"） |
| **用户原话** | "系统全量部署的时候才会清空 admin_device 和 page_view，数据备份的时候这两个表的数据不能清空" |
| **方案对比** | A. `export.sh` 默认不清空 + 新增 `--clear-tables=admin_device,page_view` CLI（用户拍板） ｜ B. 保留硬编码（被否） |
| **解决方案** | ① `sqlite-export.sh`：`CLEAR_DATA_TABLES` 默认改空数组；新增 `--clear-tables=` CLI（`${1#*=}` + `tr ',' ' '`）；报告段 conditional `Cleared: ...`；② `publish-release.sh:246`：`EXPORT_DB=1` 路径显式传 `--clear-tables=admin_device,page_view`（全量部署场景）；③ `blog-backup.sh` 不动（本来就没传 CLEAR 字段，新行为下默认不清空正好符合） |
| **验证结果** | 默认导出：14 表全保留（`admin_device=1, page_view=6`）；显式 `--clear-tables=`：schema 保留 + 无 INSERT，其他 12 表正常；恢复链路 diff 完全为空 |
| **状态** | 🔧 工作区未提交（22 个文件改动一起待 commit） |
