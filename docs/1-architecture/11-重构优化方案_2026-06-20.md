## A. 低风险快修

### A1 — SQL 字符串拼接改参数化绑定

**问题**
- `ArticleController.java:61`：`qw.exists("...at.tag_id = " + tagId)` 拼接 tagId。
- `ArticleController.java:179-181`：`fillTagIds` 把 articleIds 拼成 `IN (1,2,3)` 字符串。

**为何要改（即便当前不可注入）**
二者当前均为 `Long`，运行时不可注入。但这是「侥幸安全」——依赖调用方永远传 Long、依赖 MyBatis-Plus 内部不对该字符串做二次处理。一旦参数来源变化或 MP 行为变化即破防。参数化是根除而非缓解。

**方案（已按 MyBatis-Plus 3.4.3.4 实际 API 核验，见附录核验记录⑤）**
- tagId：用 **`qw.exists(true, "SELECT 1 FROM article_tag at WHERE at.article_id = article.id AND at.tag_id = {0}", tagId)`**。
  - 注意：3.4.3.4 **只有** `exists(boolean, String, Object...)` 签名，**没有** `exists(String, Object...)` 两参便捷版；首参 `boolean condition` 必传 `true`。
  - `inSql` 在 3.4.3.4 **不支持参数占位**（仅 `inSql(R, String)`），故不可用于参数化。
- `fillTagIds`：改为生成 `?` 占位符 + 变长 `Object[]` 参数传入 `jdbc.queryForList`，不再手拼字面量。

**涉及文件**：`backend/blog-article/.../ArticleController.java`
**风险**：极低
**落地前**：用最小代码片段编译验证 `exists(true, sql, params)` 签名（核验记录⑤已确认存在，落地时再编译确认）。
**空集合边界**：`fillTagIds` 开头 `if (records == null || records.isEmpty()) return;` 已守卫；`articleIds` 派生自非空 records → 至少 1 个 `?` 占位符 → SQL 必合法，**空集合不可能进 SQL**。改造时加注释点明此守卫关系，防未来误删。
**回归验证**：按标签筛选文章列表正确；列表页 / 归档页 `tagIds` 回填正确。

## B. 后端重构

### B1 — 抽取 Service 层

**现状**：`ArticleController`（563 行）/ `CommentController`（263 行）把校验 + SQL + tag 关联 + 日志全堆在 controller，文章模块无 Service。

**方案（拆两阶段，避免"物理搬迁"与"逻辑改造"混在一起，核验记录第四轮①）**

**B1a — 纯物理搬迁（零逻辑改动）**
- 新建 `ArticleService`（blog-article）、`CommentService`（blog-comment）。
- Service 方法与 Controller 方法 **1:1 对应**（同名同签名），把校验/SQL/tag 关联/日志原样搬入，**保留 `return Result.error(...)` 风格**（Service 方法返回 `Result`）。
- 这一步**不改任何控制流**，纯位置移动，用 D1 测试逐方法兜回归。
- 边界优化（按下方 checklist）也放在 B1a 之后单独评审，不在搬迁同提交里做。

**B1b — 错误风格改造（独立阶段，逻辑改动）**
- 把 Service 内 `return Result.error(code,msg)` 改为 **`throw new BusinessException(code,msg)`**，由已有 `GlobalExceptionHandler.handleBusiness` 统一转 `Result.error`（HTTP 200，返回结构等价）。
- **注意**：① 这是控制流改动（return→throw），**不属于 B1a 的"物理搬迁"承诺**，故独立成阶段；② 现有校验失败的业务 WARN（FR-3.2：slug 重复 / status 非法 / tag 不存在）必须保留——在抛异常前打 WARN；③ 核验确认 controller 无 try-catch 包裹业务校验，无需删 catch。
- B1b 可选——若觉得收益不抵风险，可只做 B1a 停在 `Result.error` 风格。

**边界划分 checklist（评审用）**
| 关注点 | 归属 | 说明 |
|--------|------|------|
| 参数边界校验（page/size/排序白名单） | Controller | 与 HTTP 协议相关 |
| 业务校验（slug 唯一、status 白名单、发布时补 publishedAt） | Service | 与业务规则相关 |
| `view_count` 自增 | Service | 业务行为 |
| `article_tag` 关联增删（含 `fillTagIds`） | ArticleService | article 为聚合根，关联归其管理（接受轻度耦合，**评审确认点**） |
| 业务日志（创建/更新/删除 INFO、校验失败 WARN） | Service | 记录业务事件 |
| `Result` 包装 | Controller | 表现层 |

**涉及文件**：新增 2 个 Service；改 2 个 Controller
**前置依赖**：**先完成 D1**
**风险**：中（搬迁易漏分支）
**回归验证**：文章/评论全部 CRUD + 分类 + 标签端到端；业务日志输出不变。

### B2 — 鉴权模型重构（方案 b）

**现状风险点（核验后确认全部真实）**
1. **默认放行**（最致命）：`AdminAuthFilter.java:82` 白名单未命中即匿名放行 → 新增端点漏登记裸奔。
2. **DB / 代码双源**：结论同时取决于代码特征规则 + `api_whitelist` 表 `type`，改 DB 即可掀边界（历史 CVE 来源）。
3. **特征匹配脆弱无法证明完整性**：`isAdminSubpath` 用 `contains("/admin/")` / 正则 `/id/\d+` / `endsWith("/admin")`。**全量路由核验确认**：`GET /articles/admin/all`、`GET /articles/id/{id}` 这两个 **admin GET** 端点完全依赖特征命中，新表漏枚举 → 匿名可读草稿/按 id 读，信息泄露。
4. **前缀匹配无边界**：`ApiWhitelistService.java:74` 用 `startsWith`，`/articles` 会匹配 `/articlesXXX`。

**方案 b（不改前端、不改 DB）**
- 散落特征判断收敛成**一张显式 admin 路由表**（精确 path + method，覆盖附录 C 中所有 admin 端点）。
- 基调改为「**写操作默认拒绝，仅显式 public 白名单放行**」：
  - 显式 public（公开 GET、`POST /auth/login`、`POST /comments`）→ 放行。
  - 命中 admin 路由表 → 强制鉴权。
  - 其余写操作（POST/PUT/DELETE/PATCH）→ 默认要求鉴权（消灭风险①③）。
- `matchPath` 前缀匹配补路径边界（消灭风险④）。
- **防遗漏机制**（采纳评审建议 2a）：filter 对「未在 admin 表 / 未在 public 白名单」命中的请求打 WARN（含 path/method/IP），便于发现漏登记端点。

**防遗漏 WARN 策略（采纳评审建议 2，遵守 §4.8 防日志放大）**
- **打点位置**：filter 内「既不命中 admin 表、又不命中 public 白名单」的写请求 → WARN（path/method/IP），提示疑似漏登记端点。
- **去重**：key = `method + path`，用进程内 `ConcurrentHashMap.newKeySet()` 记录已告警 key，**同一 key 进程生命周期内只打一次**（每日 cron 重建静态站会重启进程，自然 reset）。
- **频次上限（防日志放大攻击）**：同一 IP 每分钟最多打 **N（初值 5，可配置 `blog.security.unregistered-warn.per-min`，待运维按实际误报率调）** 条此类 WARN；**第 N+1 条起降为 DEBUG**（不静默丢弃——保留信息、只降量级，避免攻击时丢线索又不爆盘）。
  - 窗口实现：复用 `CommentController` 的**固定窗口**（核验确认是 fixed window 非滑动）——`ConcurrentHashMap<ip, long[]{count, windowStartSec}>` + `compute` 原子段，`now - windowStartSec > 60` 则重置 `{1, now}`。单实例够用；多实例窗口各自独立（不影响正确性，仅各实例各算各的）。
  - 不引入熔断（封禁交既有 `IpRateLimitFilter`，不在鉴权层耦合）。

**#14 配套（categories 泄露收口）**
- `GET /articles/categories/all`、`GET /articles/categories/with-count` 在新 admin 路由表中标 admin。
- 核验：前端仅 `posts.vue`/`categories.vue`/`edit.vue`（均 admin 页、走 useAdminApi 带 token）调用 → **收 admin 零前端改动**。公开页用的是带 `visible=1` 过滤的 `GET /articles/categories`，不受影响。

**落地前置（采纳评审建议 2b/2c）**
1. 先产出「**原特征规则判定 ↔ 新路由表判定**」对照清单（基础数据见附录 C），确保每个端点判定一致，无端点从"碰巧鉴权"变"碰巧放行"（#14 是**预期内的判定变化**：从误放行 → 鉴权）。
2. `AdminAuthFilterTest` 用 **`@SpringBootTest` + `MockMvc` 真实路由**（非 mock filter），遍历附录 C 每个端点跑匿名访问，**B2 改动前先跑一次建立基线，改动后再跑对比**。

**涉及文件**：`AdminAuthFilter.java`、`ApiWhitelistService.java`
**前置依赖**：**先完成 D1 的 `AdminAuthFilterTest`**
**风险**：高（鉴权是安全边界）
**回归验证**：匿名访问附录 C 全部 admin 端点 → 401；登录后 admin 端点可用；匿名 `POST /auth/login`、`POST /comments`、公开 GET 可用；设备校验链路（2001/2002/不匹配）不受影响。

## D. 补自动化测试

**现状**：后端 0 测试类（无任何 `src/test`）；前端 `tests/` 空。

### D1 — 后端集成测试（B1/B2 的安全网）
- **模块归属**：放 **blog-app**（核验：唯一 `@SpringBootApplication` 模块，能加载全 context + 所有 controller；放业务模块起不来）。blog-app 引 `spring-boot-starter-test`。
- **测试库：只用内存 SQLite**。**不用 H2**——项目业务 SQL 已为 SQLite 方言统一（§4.5，38 处），H2 方言不一致会致测试要么跑不起来、要么"通过"不可信。（注：项目用 MyBatis-Plus + JDBC，**无 Hibernate/JPA**，故不存在 Hibernate 方言问题。）
- **关键坑：内存 SQLite 多连接不共享**（核验记录第四轮③）。`:memory:` 每个连接是独立库；`file::memory:?cache=shared` 虽共享但写仍要锁。配合 prod 的 Hikari `pool-size=8`，测试会**间歇性失败**（不同连接看到不同库 / 写锁竞争）。
- **解法：独立 `application-test.yml`，强制单连接**，与 dev/prod 完全隔离。最小片段：
  ```yaml
  spring:
    datasource:
      driver-class-name: org.sqlite.JDBC
      url: jdbc:sqlite:file::memory:?cache=shared
      hikari:
        maximum-pool-size: 1   # 单连接，避免内存库不共享 / 写锁竞争
        minimum-idle: 1
  ```
  测试类用 `@ActiveProfiles("test")`；schema 在 `@BeforeAll` / `schema-test.sql` 初始化。
- 用例：
  - `ArticleControllerTest`：CRUD + 校验分支 + tag 关联。
  - `AdminAuthFilterTest`（**B2 安全网**）：`@SpringBootTest`+`MockMvc`，遍历附录 C 每端点匿名访问，验证 401/放行符合预期。
  - `CommentControllerTest`：限流 + 校验。

### D2 — 前端 e2e（C 的安全网，按 C 拆分维度配对）
- `edit.spec.ts`：登录 → 发文章（覆盖 `<MarkdownEditor>` + `useImageUpload`）。
- `dashboard.spec.ts`：仪表盘加载 + 图表渲染（覆盖 chart 子组件）。
- `settings.spec.ts`：改设置 + 改密（覆盖 settings 子组件）。

**风险**：低（只加不改）
