# my-blog 项目部署操作手册

> **本文档定位**：my-blog 项目部署**操作手册** —— 升级时一步步怎么操作（"how"）。
> 设计决策 / 成本预算 / 架构演进 / ADR 见姐妹文档 [`项目部署解决方案.md`](项目部署解决方案.md)。

> 适用：my-blog **v5.0.0+**（SQLite + 全静态 + systemd + GitHub Release + 日志体系 + IP 限流封禁 + 增量 SQL migration）

- **读者**：负责 my-blog 日常升级 / 故障排查 / 数据迁移的开发者（单 owner）
- **目标环境**：阿里云 ECS 1C2G + 阿里云域名 + Let's Encrypt HTTPS

## 1. 脚本与场景速查

### 1.1 5 个主脚本

| 脚本 | 触发位置 | 用途 |
|---|---|---|
| [`publish-release.sh`](../scripts/publish-release.sh) | 本地 | 清理 + 重新构建后端/前端 + 打资源 + 创建 GitHub Release |
| [`deploy-server.sh`](../scripts/deploy-server.sh) | 服务器 | 从 release 拉资源 + 部署 + 重启服务 + 验收 |
| [`sqlite-export.sh`](../scripts/sqlite-export.sh) | dev 本地 | 把 dev SQLite 加密导出为 `.sql.gz.enc` |
| [`sqlite-import.sh`](../scripts/sqlite-import.sh) | 服务器 | 解密 `.enc` + 备份目标 db + 导入 + 完整性校验 |

### 1.2 6 个升级场景

| 场景 | 涉及脚本 | 文档位置 |
|---|---|---|
| 项目初始化（从零部署）| deploy-server + schema-sqlite.sql | [§2](#2-场景一项目初始化) |
| 全量代码升级（最常用，含前端/后端/SQL）| publish-release + deploy-server | [§3](#3-场景二全量代码升级) |
| 增量 SQL 脚本升级（应急，不走 deploy-server）| 手动 sqlite3 | [§4](#4-场景三增量-sql-脚本升级) |
| 本地 Docker 构建 | docker build + deploy-server | [§5](#5-场景四本地-docker-构建) |
| 本地 Docker 升级 | docker exec + deploy-server | [§6](#6-场景五本地-docker-升级) |

### 1.3 DEPLOY_MODE 速查表

> v4.4.0 起：`code/frontend/backend/sql/data` 5 种模式已删除，统一为 `full`。

| `DEPLOY_MODE` | jar | schema | 前端 | 增量 SQL | 数据导入 | 典型场景 |
|---|---|---|---|---|---|---|
| `init` | ✅ | ✅ | ✅ | ✅ | ❌ | 首次初始化 |
| `full`（默认）| ✅ | 保留 | ✅ | ✅ | ❌ | 全量代码升级（前端+后端+SQL）|
| `full` + `IMPORT_DB=1` | ✅ | 保留 | ✅ | ✅ | ✅ | 代码+数据一起升级 |
| `docker-create` | ✅ | ✅ | ✅ | ✅ | ❌ | 本地 Docker 首次构建 |
| `docker-init` | ✅ | ✅ | ✅ | ✅ | ❌ | 本地 Docker 业务初始化 |

## 2. 场景一：项目初始化

首次从零部署，建立完整的运行环境。

### 2.1 前提条件

- [ ] 开发机已安装 JDK 8+、Node.js 20+、Maven
- [ ] `backend/pom.xml` 的 `<revision>` 已设置正确版本号
- [ ] `scripts/deploy.env` 的 `GITHUB_TOKEN` 已配置
- [ ] ECS 已购买，SSH 可达
- [ ] 域名已解析到 ECS IP

### 2.2 本地：打包发布

```bash
# 1. 确认版本号（publish-release.sh 会自动从 pom.xml 读取并计算 tag，无需手动指定）
grep "<revision>" backend/pom.xml
# 期望: <revision>4.3.0</revision>（脚本会自动计算 patch 版本号）

# 2. 跑发布脚本（构建 jar + 前端静态 + 打 GitHub Release）
#    注意：只需 export GITHUB_REPO，TAG 由脚本自动计算，不要手动指定
export GITHUB_REPO=YuanYii/my-blog-prov
./scripts/publish-release.sh
# 脚本会:
#   - 从 pom.xml 读 <revision> 前两位（如 4.3）
#   - 查询 GitHub 已有 tag，自动递增 patch（如 v5.0.0 → v5.0.1）
#   - mvn clean package（构建后端 jar）
#   - npm run generate（构建前端全静态）
#   - 打 GitHub Release（含 jar/前端/schema/deploy-server.sh/增量 SQL）
```

**验收**：

```bash
# 确认 release assets 完整（TAG 由脚本自动计算，从脚本输出中获取实际 tag）
# 脚本执行完会输出: Release: https://github.com/$GITHUB_REPO/releases/tag/$TAG
open "https://github.com/$GITHUB_REPO/releases/tag/<实际tag>"
# 必有: blog-app.jar / frontend-static.tar.gz / schema-sqlite.sql /
#       deploy-server.sh / sqlite-import.sh / sqlite-export.sh / blog-backup.sh / SHA256SUMS / deploy-bundle-*.zip
```

### 2.3 服务器：初始化部署

```bash
# 1. SSH 到服务器
ssh myblog@<ecs-ip>

# 2. 拉 deploy-server.sh
TAG=v5.0.2
GITHUB_REPO=YuanYii/my-blog-prov
curl -L "https://github.com/$GITHUB_REPO/releases/download/$TAG/deploy-server.sh" \
    -o "deploy-server-$TAG.sh"
chmod +x "deploy-server-$TAG.sh"

# 3. 初始化部署（DEPLOY_MODE=init：schema 建库 + 种子数据 + 不导入业务数据）
export GITHUB_REPO=$GITHUB_REPO
sudo -E "./deploy-server-$TAG.sh" "$TAG"
# 脚本会:
#   - 装依赖（Java/redis/nginx/sqlite3）
#   - 创建 /opt/myblog/ 目录结构
#   - 下载 jar + 前端静态 + schema
#   - 按 schema-sqlite.sql 建库（仅种子数据：admin 账号 + 默认设置）
#   - 写 application.yml / myblog.env / systemd unit / nginx conf
#   - 启动服务 + 健康检查
```

### 2.4 初始化后验收

```bash
# 1. 服务正常
curl -s http://127.0.0.1/api/v1/health
# 期望: {"code":200,"data":{"status":"UP",...}}

# 2. 前端可访问
curl -sI http://127.0.0.1/
# 期望: 200 OK

# 3. admin 可登录（默认账号 admin / 123456，**生产必须改密码**）
curl -s http://127.0.0.1/api/v1/admin/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"123456"}'
# 期望: 返回 token

# 4. 数据库只有种子数据
curl -s http://127.0.0.1/api/v1/articles | jq '.data.total'
# 期望: 0（无业务数据）
```

### 2.5 初始化后的必要操作

- [ ] 修改 admin 密码（admin 后台 → 设置 → 修改密码）
- [ ] 配置 CORS_ORIGINS（`/etc/myblog/myblog.env`）
- [ ] 配置设备授权（admin 后台 → 设备授权）
- [ ] 配置备份（`/etc/myblog/myblog.env` 中的 BACKUP_* 变量）

### 2.6 关键环境变量表（v5.0.0 补全）

完整模板见 `scripts/deploy-server.env.example`。`deploy-server.sh` 首次部署时会自动生成 `/etc/myblog/myblog.env` 默认值，但下列 6 项**手册原本未说明**，运维拿到 `.example` 时容易一脸懵——这里集中说明：

| 变量 | 用途 | 默认值 | 必填？ |
|------|------|--------|--------|
| `SQLITE_PATH` | SQLite 数据库文件绝对路径 | `/opt/myblog/db/blog.db` | 建议改（dev 可用 `/tmp/blog.db`） |
| `JWT_SECRET` | JWT 签名密钥（≥32 位强随机 hex） | 首次自动生成 | **必填**——生成后**绝对不要覆盖**，会踢所有用户下线 |
| `CORS_ORIGINS` | 允许跨域的源（逗号分隔） | `https://yourname.com` | **必填**——必须含真实域名 |
| `UPLOAD_DIR` | 文件上传存储目录（绝对路径） | `/opt/myblog/uploads` | 建议改（容器内可能要 `/data/uploads`） |
| `BACKUP_ENCRYPTION_PASSWORD` | 备份加密密码（`openssl rand -base64 24`） | 首次自动生成 | **必填**——丢失则历史备份无法解密 |
| `GITHUB_BACKUP_REPO` | 备份推送的 GitHub repo（建议私有） | 空 | 必填（若启用 GitHub 备份功能） |
| `BACKUP_GITHUB_TOKEN` | Fine-grained PAT（只勾备份 repo 写权限） | 空 | 必填（若启用 GitHub 备份功能） |
| `REDIS_HOST` | Redis 服务地址 | `127.0.0.1` | 建议（apt 装本地默认即可） |
| `REDIS_PORT` | Redis 端口 | `6379` | 建议（apt 装本地默认即可） |
| `REDIS_PASSWORD` | Redis 密码（本地无密码可空） | 空 | 可选（生产建议设） |
| `REDIS_DB` | Redis db index（0-15） | `0` | 可选 |

**强约束**：
- 部署后**只手动改** `JWT_SECRET` / `CORS_ORIGINS` / `BACKUP_ENCRYPTION_PASSWORD` / `REDIS_PASSWORD` 这 4 个敏感项；其他项用 `.example` 默认即可
- `BACKUP_GITHUB_TOKEN` **不要跟发布 token 复用**——命名带 BACKUP 前缀就是为避免混淆
- `UPLOAD_DIR` 必须在 jar 启动前存在，否则上传会失败——`deploy-server.sh` 首次部署会自动 `mkdir -p`

## 3. 场景二：全量代码升级

最常用的升级方式。改了代码后，`publish-release.sh` 打包 → `deploy-server.sh` 部署。

### 3.1 本地

```bash
# 1. 改代码（前端 or 后端 or 两者都改）
# 2. 改 backend/pom.xml <revision>
# 3. 跑发布（只需 export GITHUB_REPO，TAG 由脚本自动计算）
export GITHUB_REPO=YuanYii/my-blog-prov
./scripts/publish-release.sh
# 脚本会重新构建前端静态文件 + 后端 jar
```

### 3.2 服务器

```bash
ssh myblog@<ecs-ip>

# 拉新版 deploy-server.sh
TAG=v5.0.0
GITHUB_REPO=YuanYii/my-blog-prov
curl -L "https://github.com/$GITHUB_REPO/releases/download/$TAG/deploy-server.sh" \
    -o "deploy-server-$TAG.sh"
chmod +x "deploy-server-$TAG.sh"

# 全量升级（DEPLOY_MODE=full，含前端+后端+增量SQL）
export GITHUB_REPO=$GITHUB_REPO
sudo -E "./deploy-server-$TAG.sh" "$TAG"
# 脚本会:
#   - 下载 jar + 前端静态文件 + 增量 SQL
#   - 停服务 → 替换 jar
#   - 替换前端静态文件
#   - 执行增量 SQL（若有）
#   - 重启服务 → 健康检查
```

**验收**：

```bash
# 确认 release assets 完整（TAG 由脚本自动计算，从脚本输出中获取实际 tag）
open "https://github.com/$GITHUB_REPO/releases/tag/<实际tag>"
# 必有: blog-app.jar / frontend-static.tar.gz / schema-sqlite.sql /
#       deploy-server.sh / sqlite-import.sh / sqlite-export.sh / blog-backup.sh / SHA256SUMS / deploy-bundle-*.zip
```

### 3.3 服务器：跑 deploy-server

```bash
ssh myblog@<ecs-ip>

# 拉新版 deploy-server.sh
TAG=v5.0.2
GITHUB_REPO=YuanYii/my-blog-prov
curl -L "https://github.com/$GITHUB_REPO/releases/download/$TAG/deploy-server.sh" \
    -o "deploy-server-$TAG.sh"
chmod +x "deploy-server-$TAG.sh"

# 全量升级（DEPLOY_MODE=full，默认保留 DB + 跑增量 SQL）
export GITHUB_REPO=$GITHUB_REPO
sudo -E "./deploy-server-$TAG.sh" "$TAG"
# 脚本会:
#   - 下载 jar + 前端静态 + 增量 SQL
#   - 停服务 → 替换 jar → 替换前端静态
#   - 扫描并执行 docs/sql/migrations/ 下未执行的增量 SQL
#   - 重启服务 → 健康检查
#   - **不删除 DB**（业务数据完整保留）
```

### 3.4 升级后验收

```bash
# 1. 服务正常
curl -s http://127.0.0.1/api/v1/health

# 2. 业务数据还在
curl -s http://127.0.0.1/api/v1/articles | jq '.data.total'
# 期望: > 0（文章数据保留）

# 3. 增量 SQL 已执行
sqlite3 /opt/myblog/db/blog.db "SELECT * FROM _migration_history ORDER BY executed_at DESC LIMIT 5;"
# 期望: 显示最近执行的 migration 记录

# 4. 版本号正确
journalctl -u myblog -n 10 | grep -i "version"
```

### 3.5 带数据迁移的全量升级

如果需要把 dev 的业务数据灌到生产：

```bash
# 方式 A：dev 导出 + 上传 + 生产导入
bash scripts/sqlite-export.sh --exclude page_view -o /tmp/migration.sql.gz.enc
scp /tmp/migration.sql.gz.enc myblog@<ecs-ip>:/tmp/
ssh -t myblog@<ecs-ip> "sudo bash /opt/myblog/scripts/sqlite-import.sh /opt/myblog/db/blog.db /tmp/migration.sql.gz.enc"

# 方式 B：发布时一起打包（EXPORT_DB=1）
# publish-release.sh 会自动计算 TAG，无需手动指定
export GITHUB_REPO=YuanYii/my-blog-prov
EXPORT_DB=1 ./scripts/publish-release.sh
# 生产端（TAG 从脚本输出中获取）
IMPORT_DB=1 sudo -E "./deploy-server-<实际tag>.sh" "<实际tag>"
```

### 3.6 升级的 3 个不变量

| 不变量 | 实现 | 出问题会怎样 |
|---|---|---|
| **业务数据不丢** | DB 不删除，增量 SQL 补丁 | 数据完整保留 |
| **JWT secret 不变** | `/etc/myblog/myblog.env` 首次生成后不覆盖 | token 仍然有效 |
| **服务平滑重启** | systemctl restart + 健康检查 | 启动失败打日志退出 |

## 4. 场景三：增量 SQL 脚本升级（应急）

只补表结构/数据，不动代码。适用于紧急修复 DB schema 或手动执行数据迁移。
v4.4.0 起不再有 `DEPLOY_MODE=sql`，如需只跑 SQL 不动代码，手动执行即可。

### 4.1 增量 SQL 规范

- **目录**：`docs/sql/migrations/`
- **命名**：`{YYYYMMDD}_{description}.sql`（如 `20260623_add_device_lock.sql`）
- **幂等**：使用 `CREATE TABLE IF NOT EXISTS` / `ALTER TABLE ... ADD COLUMN` 等安全语法
- **执行记录**：写入 `_migration_history` 表（由 deploy-server.sh 自动管理）

### 4.2 服务器操作

```bash
ssh myblog@<ecs-ip>

# 直接在服务器上执行单个 SQL 文件
sqlite3 /opt/myblog/db/blog.db < /path/to/migration.sql

# 手动记录到 migration history
sqlite3 /opt/myblog/db/blog.db \
  "INSERT INTO _migration_history (script_name, executed_at) VALUES ('20260623_add_device_lock.sql', datetime('now'));"
```

### 4.3 查看已执行的 migration

```bash
sqlite3 /opt/myblog/db/blog.db "SELECT script_name, executed_at FROM _migration_history ORDER BY executed_at DESC;"
```

### 4.4 失败处理

增量 SQL 执行失败时：
1. 脚本输出**失败的脚本名称**
2. 已成功执行的 migration **已写入** `_migration_history`，不会重复执行
3. 失败的脚本需要人工修复后重跑（或手动执行修正后的 SQL）

## 7. 场景六：本地 Docker 构建

首次构建本地模拟容器 + 项目初始化。

### 7.1 构建镜像

```bash
# 进入 Docker 目录
cd docs/deployment/docker/local-sim

# 构建镜像
docker build -t myblog-local-sim:latest .
```

### 7.2 启动容器 + 初始化

```bash
# 启动容器（端口映射）
docker run -d \
  -p 28080:8080 \
  -p 28000:80 \
  --name myblog-sim \
  myblog-local-sim:latest

# 进入容器跑部署
docker exec -it myblog-sim bash
cd /opt/myblog
TAG=v5.0.0
bash deploy-server.sh $TAG
# 脚本会自动检测 /.dockerenv → LOCAL_SIM=1
# 初始化：schema 建库 + 种子数据 + supervisord 启动服务
```

### 7.3 验收

```bash
# 浏览器访问
# http://localhost:28000/        ← 前端
```

## 8. 场景七：本地 Docker 升级

已有容器，模拟生产环境升级流程。**不销毁容器**，直接在容器内运行 deploy-server.sh。

### 8.1 前提条件

- [ ] 容器 `myblog-sim` 已运行（通过场景六构建）
- [ ] 本地代码已修改并 commit

### 8.2 本地：打包发布

```bash

# 跑发布脚本（只需 export GITHUB_REPO，TAG 由脚本自动计算）
export GITHUB_REPO=YuanYii/my-blog-prov
./scripts/publish-release.sh
# 脚本会:
#   - 从 pom.xml 读 <revision> 前两位（如 4.3）
#   - 查询 GitHub 已有 tag，自动递增 patch（如 v5.0.0 → v5.0.1）
#   - mvn clean package（后端）
#   - npm run generate（前端全静态）
#   - 打 GitHub Release
```

### 8.3 容器内：执行升级

```bash
# 进入容器
docker exec -it myblog-sim bash

# 在容器内拉新版 deploy-server.sh 并执行（模拟生产流程）
cd /opt/myblog
TAG=v4.4.7
GITHUB_REPO=YuanYii/my-blog-prov
curl -L "https://github.com/$GITHUB_REPO/releases/download/$TAG/deploy-server.sh" \
    -o "deploy-server-$TAG.sh"
chmod +x "deploy-server-$TAG.sh"

# 执行升级（DEPLOY_MODE=full：保留 DB + 增量 SQL）
export GITHUB_REPO=$GITHUB_REPO
bash "./deploy-server-$TAG.sh" "$TAG"
# 脚本会自动检测 /.dockerenv → LOCAL_SIM=1
# 升级行为与生产完全一致：
#   - 下载 jar + 前端静态 + 增量 SQL
#   - 停服务 → 替换 jar → 替换前端静态
#   - 扫描并执行未执行的增量 SQL
#   - 重启 supervisord 管理的服务
#   - 健康检查
```

## 10. 紧急回滚

升级出问题 → 拉老版本的 deploy-server.sh + 跑：

```bash
TAG=<上一版本 tag>
GITHUB_REPO=owner/repo
ssh myblog@<ecs-ip>
curl -L "https://github.com/$GITHUB_REPO/releases/download/$TAG/deploy-server.sh" \
    -o "deploy-server-$TAG.sh"
chmod +x "deploy-server-$TAG.sh"
export GITHUB_REPO=$GITHUB_REPO
sudo -E "./deploy-server-$TAG.sh" "$TAG"
```

### 10.1 回滚的不变量

| 项 | 行为 |
|---|---|
| **DB** | 不回滚（schema 兼容新版本，老 jar 也能读新 DB）|
| **静态文件** | 替换为上一版本的 |
| **JWT secret** | 保留（所有已签发 token 仍然有效）|

## 13. 决策记录（ADR 摘要）

### ADR-001：境外免备案
- **影响**：省去 ICP 备案；代价是国内访问 +20-50ms 延迟

### ADR-005：v2.6.0 改用 SQLite
- **影响**：JVM heap 256MB → 512MB；月成本 ¥60 → ¥30

### ADR-006：v2.7.0 前端全静态
- **影响**：前端内存 150-250MB → 10-20MB；新文章 0-24h 延迟

### ADR-007（v4.3.0）：增量 SQL migration
- **影响**：升级时不再删除 DB，通过 `_migration_history` 表追踪已执行的脚本
- **决策**：方案 A（_migration_history 表）+ 失败时输出脚本名
