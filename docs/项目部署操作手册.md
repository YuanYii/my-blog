# my-blog 项目部署操作手册

> **本文档定位**：my-blog 项目部署**操作手册** —— 升级时一步步怎么操作（"how"）。
> 设计决策 / 成本预算 / 架构演进 / ADR 见姐妹文档 [`项目部署解决方案.md`](项目部署解决方案.md)。

> my-blog 服务升级端到端操作手册：把代码仓的改动变成生产服务器上跑的新版本。
> 串联 [`publish-release.sh`](../scripts/publish-release.sh)（本地发版）+ [`deploy-server.sh`](../scripts/deploy-server.sh)（服务器部署）+ 验收 + 回滚。
>
> 适用：my-blog **v4.0.0+**（SQLite + 全静态 + systemd + GitHub Release + 日志体系 + IP 限流封禁）

## 1. 脚本与场景速查

### 1.1 4 个主脚本

| 脚本 | 触发位置 | 用途 | 典型调用方 |
|---|---|---|---|
| [`publish-release.sh`](../scripts/publish-release.sh) | 本地 | 清理 + 重新构建后端/前端 + 打资源 + 创建/更新 GitHub Release + 上传 assets | 开发者 |
| [`deploy-server.sh`](../scripts/deploy-server.sh) | 服务器 | 从 release 拉资源 + 装依赖（首次）+ 部署 jar/前端/配置 + 调 import + 重启服务 + 验收 | 服务器（root） |
| [`sqlite-export.sh`](../scripts/sqlite-export.sh) | dev 本地 | 把 dev SQLite 加密导出为 `.sql.gz.enc`（AES-256-CBC + PBKDF2 100k）| 开发者（手动 / 被 publish 调）|
| [`sqlite-import.sh`](../scripts/sqlite-import.sh) | 服务器 | 解密 `.enc` + gunzip + 备份目标 db + 重建 + 导入 + 完整性校验 | 服务器（手动 / 被 deploy 调）|
| [`blog-restore.sh`](../scripts/blog-restore.sh) | 服务器 | 从 GitHub Release 拉加密 dump → 解密 → 停服 → 导入 db → （可选）恢复 uploads → 启服 → 健康检查 + 数据校验 | RestoreService（systemd-run）|

## 2. 场景一：纯代码发版

最常用的升级流程：**只发代码 + 静态文件，但 DB 会被删除并重建（仅种子数据）**。JWT secret 也保留，所有已签发 token 仍然有效。

⚠️ **重要警告**：每次 `DEPLOY_MODE=full` 部署都会**删除旧 DB 并按 `schema-sqlite.sql` 重建（仅种子数据）**，文章/评论/设置全部丢失。恢复办法：先跑 `sqlite-import.sh` 从备份恢复，或用 `IMPORT_DB=1` 带数据一起发版。

### 2.1 本地：跑 publish-release

**前置检查**（跑脚本前逐项过一遍）：

- [ ] 代码已 commit & push 到 main
- [ ] `backend/pom.xml` 里 `<properties>` 块的 `<revision>4.0.0</revision>`（约第 32 行）已改成新版本号
  - ⚠️ 别动第 10 行 spring-boot-starter-parent 的 `<version>2.7.18</version>`（Spring Boot 父 POM）
  - 第 16 行 `<version>${revision}</version>` 是占位符引用，**不是可编辑的版本号**
  - 改完后 `cd backend && mvn validate` 验证
  - 这条**仅作开发期标记**，不影响发布 tag（tag 由脚本自动推导 +1）
- [ ] `scripts/deploy.env` 里的 `GITHUB_TOKEN` 还有效（Fine-grained PAT 经常自动过期）
- [ ] 知道下一个 tag = GitHub 上最大 release 的 patch +1（脚本自动推导，**不接受手动指定**）

**跑发布**：

```bash
# 标准姿势（tag 完全自动推导，不接受手动指定）
./scripts/publish-release.sh
# 传参数会被脚本拒绝:err "本脚本版本号完全自动...,不接受手动指定"
```

**脚本步骤**：

| 步骤 | 动作 | 耗时 |
|---|---|---|
| 1 | 清理 `blog-app.jar` / `.output/` | 秒级 |
| 2 | `mvn -f backend clean package -DskipTests` | 30-60s（首次 2-3min）|
| 3 | `npm run generate`（Nuxt 全静态） | 30-60s（首次 2-3min）|
| 4 | 打 staging + 算 sha256 + 打 zip 冷部署包 | 秒级 |
| 4.5 | 空仓自愈：补 README 解锁 release 创建 | 只首次触发 |
| 5 | 创建/更新 GitHub Release（已存在则删旧 assets 重传）| < 5s |
| 6 | 上传 7-8 个 assets | 5-30s（看带宽）|

**成功输出长这样**：

```
[INFO] === ✅ 全部完成 ===
[INFO] Release:    https://github.com/<owner>/<repo>/releases/tag/v4.0.0
[INFO] 冷部署包:   deploy-bundle-v4.0.0.zip (xxxM)
```

**4 项验收**（跑完必做）：

```bash
# 1. 7 个 assets 都在（不带数据导入时没有 .enc）
#    必有:blog-app.jar / frontend-static.tar.gz / schema-sqlite.sql /
#          deploy-server.sh / sqlite-import.sh / SHA256SUMS / deploy-bundle-*.zip
open "https://github.com/$GITHUB_REPO/releases/tag/$TAG"

# 2. 冷部署包能下
curl -fsSL -I "https://github.com/$GITHUB_REPO/releases/download/$TAG/deploy-bundle-$TAG.zip"

# 3. SHA256SUMS 跟本地一致
curl -fsSL "https://github.com/$GITHUB_REPO/releases/download/$TAG/SHA256SUMS"
# 对比本地 .release-staging/assets/SHA256SUMS

# 4. deploy-server.sh 是最新的（如果这次改过它）
curl -fsSL "https://github.com/$GITHUB_REPO/releases/download/$TAG/deploy-server.sh" | head -20
```

### 2.2 服务器：跑 deploy-server

**前置检查**（ssh 之前）：

- [ ] 知道当前服务器跑的版本（`curl -s http://127.0.0.1/api/v1/health` 看 banner 或 release tag）
- [ ] `/opt/myblog/db/backups/` 目录还有空间（升级会留一份旧 DB 备份）
- [ ] 当前服务器时间是对的（NTP 同步）—— SQLite 热备份对时间戳敏感
- [ ] 升级时间段不在流量高峰（升级过程有 5-10s 不可用窗口）

**最小命令**：

```bash
# 上服务器
ssh myblog@<ecs-ip>

# 拉新 deploy-server.sh（脚本自己会再去 GitHub 拉资源）
curl -L https://github.com/YuanYii/my-blog-prov/releases/download/v4.2.7/deploy-server.sh -o deploy-server-v4.2.7.sh
chmod +x deploy-server-v4.2.7.sh

# 跑（DB 会被删除并重建 → 自动备份到 db/backups/ → 数据会丢失，需 IMPORT_DB=1 或事后恢复）
export GITHUB_REPO=YuanYii/my-blog-prov
sudo -E ./deploy-server-v4.2.7.sh v4.2.7
```

> 升级场景首次跑：3-5 分钟（装依赖占大头）；之后只要 30-60 秒。

### 2.3 升级场景的 3 个"保命"不变量

| 不变量 | 实现 | 出问题会怎样 |
|---|---|---|
| **数据不丢（需配合 IMPORT_DB=1 或事后从备份恢复）** | DB 会被删除并按 `schema-sqlite.sql` 重建（仅种子数据），旧 DB 自动备份到 `db/backups/` | 未导入数据 → 文章/评论/设置全部丢失 |
| **JWT secret 不变** | `/etc/myblog/myblog.env` 已存在 → **保留不动** | secret 改了 → 所有用户 401 被踢下线 |
| **服务平滑重启** | `systemctl restart` + 30 次健康检查轮询 | 启动失败 → 脚本报错退出，**不会自动回滚**（要手动）|

### 2.4 DEPLOY_MODE 部署模式表

通过外置环境变量 `DEPLOY_MODE` + `IMPORT_DB` 控制 3 档模式：

| `DEPLOY_MODE` | `IMPORT_DB` | jar | schema | 前端 | 数据导入 | 典型场景 |
|---|---|---|---|---|---|---|
| `full`（默认）| `0`（默认）| ✅ | ✅ | ✅ | ❌ | 纯代码发版（最常用）|
| `full` | `1` | ✅ | ✅ | ✅ | ✅ | 代码+数据一起升级 |
| `code` | `0` | ✅ | ✅ | ✅ | ❌ | 显式强调只动代码 |
| `code` | `1` | ✅ | ✅ | ✅ | ✅ | **warn** 后仍执行（与 full+1 等价）|
| `data` | `0` | ❌ | ❌ | ❌ | ❌ | **打印错误但继续走 data 跳过逻辑（jar/schema/前端/nginx 全部跳过）；建议二选一：DEPLOY_MODE=full 或 IMPORT_DB=1** |
| `data` | `1` | ❌ | ❌ | ❌ | ✅ | 只灌数据，不重启服务 |

```bash
# 完整代码发版（默认）
TAG=v4.0.0
curl -L "https://github.com/$GITHUB_REPO/releases/download/$TAG/deploy-server.sh" -o "deploy-server-$TAG.sh"
chmod +x "deploy-server-$TAG.sh"
sudo -E "./deploy-server-$TAG.sh" "$TAG"

# 代码 + 数据一起升级（姿势 B）
TAG=v4.0.0
curl -L "https://github.com/$GITHUB_REPO/releases/download/$TAG/deploy-server.sh" -o "deploy-server-$TAG.sh"
chmod +x "deploy-server-$TAG.sh"
IMPORT_DB=1 sudo -E "./deploy-server-$TAG.sh" "$TAG"

# 只装代码，保留 db（显式）
TAG=v4.0.0
curl -L "https://github.com/$GITHUB_REPO/releases/download/$TAG/deploy-server.sh" -o "deploy-server-$TAG.sh"
chmod +x "deploy-server-$TAG.sh"
DEPLOY_MODE=code sudo -E "./deploy-server-$TAG.sh" "$TAG"

# 只灌数据，跳过 jar/schema/前端/systemd/nginx（姿势 C）
TAG=v4.0.0
curl -L "https://github.com/$GITHUB_REPO/releases/download/$TAG/deploy-server.sh" -o "deploy-server-$TAG.sh"
chmod +x "deploy-server-$TAG.sh"
DEPLOY_MODE=data IMPORT_DB=1 sudo -E "./deploy-server-$TAG.sh" "$TAG"
```

**`data` 模式的两个注意点**：
1. **不重启服务**：db 文件已被 `sqlite-import.sh` 重建，但服务进程持有的 fd 仍是旧 db。需要立即生效时手动 `systemctl restart myblog`
2. **`data` + `IMPORT_DB=0` 打印错误但 jar/schema/前端/nginx 全部跳过**（脚本 `err()` 当前只 echo 到 stderr 不 exit，数据不会被导入且其他步骤也跳过——**行为与表格对齐**，但语义矛盾）

### 2.5 deploy-server.sh 步骤表（升级场景）

| 步骤 | 动作 | 升级场景行为 |
|---|---|---|
| 1-2 | 装依赖（Java / sqlite / redis / nginx） | `SKIP_DEPS=1` 跳过（已装过的机器强烈建议）|
| 3 | 建 `/opt/myblog/{logs,frontend,db,uploads}` + `/opt/myblog/db/backups` + myblog 用户 | 目录已存在则不动 |
| 4 | 优先下 `deploy-bundle-vX.Y.Z.zip`，否则下 5-6 个单文件（**含 sqlite-import.sh**）| 校验 sha256（若有）|
| 5 | 停 systemd → 部署 jar → 备份旧 DB → **删除 → schema-sqlite.sql 重建（仅种子数据）** | DB 存在 → 自动备份后删除重建 |
| 6 | `rm -rf frontend/*` + 解压新静态文件 | 整目录重建 |
| 7 | 写 `/opt/myblog/application.yml`（只补端口/数据源）| 覆盖式写（业务配置走 jar 里的 prod.yml）|
| 7.5 | 写 `/etc/myblog/myblog.env` | **首次才生成**，升级保留 |
| 8 | 写 `/etc/systemd/system/myblog.service` + `systemctl restart` | 覆盖式写 service |
| 8.5 | **可选**：`IMPORT_DB=1` 时从 release 下载 `dev-blog-dump.sql.gz.enc`（若存在）→ 调 `sqlite-import.sh` 解密 → 导入 `$DB_FILE`（交互式输一次密码；**部署期自动传 `FORCE_IMPORT=1` 跳过 y/N 确认门**）| DB 存在 → 自动备份再覆盖 |
| 9 | 写 `/etc/nginx/conf.d/myblog.conf` + 处理 default_server 冲突 + `systemctl restart nginx` | 自动处理（DEPLOY_MODE=data 跳过）|
| 10-11 | 启 redis + 轮询 `/api/v1/health` 30 次 | 启动失败打日志路径退出 |
| 12 | 自动 firewalld/ufw 放行 | `OPEN_FIREWALL=0` 可关 |

### 2.7 常见代码改动速查

> **服务器上的 deploy-server.sh 不存在**——`publish-release.sh` 才把它打进 release assets，
> 每次部署都得从 GitHub 拉。下面的所有场景都假设你按下面这套**标准 deploy 流程**操作：

```bash
# 标准 deploy 流程（所有 §2.7 场景都用这个）
TAG=v4.0.0                    # ← 替换成要部署的 tag
GITHUB_REPO=owner/repo         # ← 替换成你的 release 仓库

# 服务器上拉新 deploy-server.sh
ssh myblog@<ecs-ip>
curl -L "https://github.com/$GITHUB_REPO/releases/download/$TAG/deploy-server.sh" \
    -o "deploy-server-$TAG.sh"
chmod +x "deploy-server-$TAG.sh"
export GITHUB_REPO=$GITHUB_REPO
sudo -E "./deploy-server-$TAG.sh" "$TAG"
# 跑完留在服务器上,deploy-server.sh 会自己清理 staging 目录
```

下面的速查只列**本地动作** + **服务器要跑的具体命令**（deploy 流程的变异）。

**只改前端代码**（js/css/页面）：

```bash
# 本地
./scripts/publish-release.sh
# 服务器
TAG=v4.2.5
curl -L "https://github.com/$GITHUB_REPO/releases/download/$TAG/deploy-server.sh" -o "deploy-server-$TAG.sh"
chmod +x "deploy-server-$TAG.sh"

# ⚠️ deploy-server.sh 步骤 6 会 rm -rf $INSTALL_DIR/frontend/* + 解压新静态文件
```

## 3. 场景二：带数据迁移的发版

把 dev 环境的 db 内容灌到生产。**三种姿势**：

### 3.1 姿势 A：dev 手工导出 + scp + 生产手动导入

适合偶尔迁移、量不大、需要精挑细选表的情况。

```bash
# 1. dev 端：导出（交互式输两次密码）
bash scripts/sqlite-export.sh --exclude page_view -o /tmp/migration-$(date +%Y%m%d).sql.gz.enc
# 输出:
#   [✓] 加密导出完成
#   [✓] 文件: /tmp/migration-20260618-152000.sql.gz.enc
#   [!] 🔑 记住这个密码!生产端导入时需要输入同一密码

# 2. 上传到生产（任何介质都行，scp / rsync / OSS 都安全——文件已是加密态）
scp /tmp/migration-*.sql.gz.enc myblog@<ecs-ip>:/tmp/

# 3. 生产端：解密 + 导入（交互式输一次密码）
# ⚠️ 必须用 ssh -t（强制分配远程 pty）——姿势 A 要靠远端 stdin 是 tty 才会弹
#    "请输入解密密码" + "确认导入? [y/N]" 两个交互门。不带 -t 的话，OpenSSH
#    把 ssh host "cmd" 当 non-interactive session，不分配 pty，远端
#    `[[ ! -t 0 ]]` 为真，会触发 sqlite-import.sh 的"非交互拒绝"分支直接 exit 3
ssh -t myblog@<ecs-ip> "sudo bash /opt/myblog/scripts/sqlite-import.sh /opt/myblog/db/blog.db /tmp/migration-*.sql.gz.enc"
# ⚠️ 错密码立即退出，**不碰目标 db**（目标 db 字节不变）
# ⚠️ db 存在会自动备份到 <db 同目录>/blog-*.bak.YYYYMMDD-HHMMSS
#    （例如 /opt/myblog/db/blog.db.bak.YYYYMMDD-HHMMSS，**不**在 db/backups/ 子目录里）
```

### 3.2 姿势 B：发布时一起打包 + 生产 deploy 时自动导入

适合**每次发版都想带新数据**的场景（内容站迁移、内容同步）。

```bash
# dev 端：发布时导出
EXPORT_DB=1 ./scripts/publish-release.sh
# 脚本会:
#   - 调 sqlite-export.sh 加密导出 backend/blog.db
#   - 把 dev-blog-dump.sql.gz.enc 一起进 release assets
#   - 进 SHA256SUMS + 冷部署 zip 包

# 生产端：自动下载 + 解密 + 导入
TAG=v4.2.6
GITHUB_REPO=YuanYii/my-blog-prov
ssh myblog@<ecs-ip>
curl -L "https://github.com/$GITHUB_REPO/releases/download/$TAG/deploy-server.sh" \
    -o "deploy-server-$TAG.sh"
chmod +x "deploy-server-$TAG.sh"
export GITHUB_REPO=$GITHUB_REPO
IMPORT_DB=1 sudo -E "./deploy-server-$TAG.sh" "$TAG"
# 脚本会:
#   - step 4 下载 .enc + sqlite-import.sh
#   - step 8.5 调 sqlite-import.sh 解密 → 导入到 /opt/myblog/db/blog.db
#     （**部署期自动传 FORCE_IMPORT=1 跳过 y/N 确认门** + 用 PIPESTATUS[0] 捕获真实退出码）
#   - 默认 DEPLOY_MODE=full = jar + schema + 前端 + 数据 一起升级
```

**姿势 B 的额外验收**：

```bash
# 确认 .enc 上传且 SHA256 正确
[ -n "$(curl -fsSL "https://github.com/$GITHUB_REPO/releases/download/$TAG/dev-blog-dump.sql.gz.enc" 2>/dev/null | head -c1)" ] && \
    echo "✅ .enc 已上传" || echo "⚠️ .enc 不在 release（EXPORT_DB=0 或导出失败）"
```

### 3.3 姿势 C：只灌数据，不重启服务

适合 db 大、需要服务不中断的场景。

```bash
# dev 端:跟姿势 A 或 B 一样导出（姿势 C 不要求走 release）
# 生产端:用 DEPLOY_MODE=data 跳过 jar/schema/前端
TAG=v4.0.0
GITHUB_REPO=owner/repo
ssh myblog@<ecs-ip>
curl -L "https://github.com/$GITHUB_REPO/releases/download/$TAG/deploy-server.sh" \
    -o "deploy-server-$TAG.sh"
chmod +x "deploy-server-$TAG.sh"
export GITHUB_REPO=$GITHUB_REPO
DEPLOY_MODE=data IMPORT_DB=1 sudo -E "./deploy-server-$TAG.sh" "$TAG"
# 脚本会:
#   - 跳过 jar/schema/前端/systemd/nginx 配置
#   - 只下载 + 解密 + 导入 db
#     （**部署期自动传 FORCE_IMPORT=1 跳过 y/N 确认门**）
#   - 不重启服务（进程持有的 fd 仍是旧 db）
#   - 立即生效:systemctl restart myblog
```

### 3.4 ⚠️ 姿势 B/C 的隐式交互门（容易踩坑）

`sqlite-import.sh` 在目标 db 已存在时会弹 `确认导入? [y/N]` 确认门（防误删），同时也会**交互式**要求输解密密码。两点容易踩：

1. **部署期 stdin 不是终端**（自动化跑 `IMPORT_DB=1`）→ `read` 直接拿空 → 密码不输 + y/N 不答 → 旧版本脚本 `exit 0` 走"已取消"分支，但 `deploy-server.sh` 旧版用 `$?` 拿不到真退出码，会**静默打印"✅ 数据导入完成"——数据其实根本没导入**。
2. 修复后 `deploy-server.sh` 调 import 时**会自动加 `FORCE_IMPORT=1`** 跳过 y/N 门，`PIPESTATUS[0]` 捕获真实退出码；密码必须由操作员**手动输入**（因为密码不能放环境变量/命令行）。

如果手动 ssh 进去跑 `sqlite-import.sh`（姿势 A），保持原样——会正常弹 y/N 让你确认，更安全。

### 3.5 数据迁移的 5 个"保命"不变量

| 不变量 | 实现 | 出问题会怎样 |
|---|---|---|
| **传输安全** | dump 文件本身 `AES-256-CBC + PBKDF2 100k + salt` 加密 | scp/邮件/OSS 泄漏 → 没密码 = 乱码 |
| **目标 db 不被错密码破坏** | `sqlite-import.sh` 解密失败立即 `error` 退出 | 错密码 = 目标 db 字节不变（md5 一致）|
| **目标 db 自动备份** | 导入前 `cp blog.db blog.db.bak.YYYYMMDD-HHMMSS` | 导入失败 → 备份恢复一行命令 |
| **内存/磁盘不残留明文** | 临时 SQL/gz 用 `shred -u` 擦掉，trap 兜底 | dev/prod 磁盘 /tmp 里找不到明文 dump |
| **密码不在 ps 输出** | 走 `openssl -pass env:DUMP_PASSWORD`，不是命令行 | `ps aux` 看不到密码 |

### 3.6 关键约束

| 约束 | 详细 |
|---|---|
| **只支持加密** | `sqlite-export.sh` / `sqlite-import.sh` **不再支持明文**；明文 .sql 会报错 |
| **密码长度 ≥ 8** | 低于 8 位会 warn（不阻断）|
| **同 dev/prod openssl 算法** | 都是 `-aes-256-cbc -pbkdf2 -iter 100000`，跨 macOS/Linux 通用 |
| **`DEPLOY_MODE=data` + `IMPORT_DB=0`** | 立即报错退出（语义矛盾）|
| **`.enc` 不在 release 时 `IMPORT_DB=1`** | warn 后跳过（可能纯代码发版）|
| **跨 sqlite 版本兼容** | export 不用 `sqlite3 .mode insert`（会包成 `unistr()`，SQLite 3.50+ 才有），改用 Python 手工转义；任意版本（≥ 3.0）都能 import |

## 4. 场景三：单独数据备份 / 恢复

### 4.1 dev 本地加密备份

```bash
# 加密导出（默认输出到 ./backups/blog-YYYYMMDD-HHMMSS.sql.gz.enc）
bash scripts/sqlite-export.sh

bash scripts/sqlite-export.sh --no-data -o /tmp/schema-only.sql.gz.enc
```

### 4.2 服务器端手动导入

```bash
# 本地导入（要先把 .enc scp 过来）
scp dev-dump.sql.gz.enc myblog@<ecs-ip>:/tmp/
ssh -t myblog@<ecs-ip> "sudo bash /opt/myblog/scripts/sqlite-import.sh /opt/myblog/db/blog.db /tmp/dev-dump.sql.gz.enc"
```

### 4.3 应急 DB 恢复

如果新版本破坏了 DB 兼容性，从备份恢复：

```bash

# 2. 找最近的备份
ls -lt /opt/myblog/db/backups/ | head -5

# 3. 恢复
sudo cp /opt/myblog/db/backups/blog-YYYYMMDD-HHMMSS.db /opt/myblog/db/blog.db

# 4. 回滚到老版本 jar（老版本 deploy-server.sh 也得拉）

# 5. 启动
sudo systemctl status myblog
```

> `sqlite-import.sh` 导入前的 `.bak.YYYYMMDD-HHMMSS` 也在 db 同目录，可以用作更细粒度的恢复点。

## 5. 场景四：全静态化配套

v2.7.0 起前端改 `ssr: false` + `nuxt generate` 预渲染，**新发布的文章不会立即出现在公开页**——要等下次前端 rebuild。

### 5.1 重建前端的 3 种方式

| 方式 | 谁来跑 | 触发 | 新内容何时出现在公开页 |
|---|---|---|---|
| **本地 rebuild + 发版** | 开发者 | `cd frontend && npm run generate` → publish-release | 立即（随下个 release）|
| **服务器 rebuild** | 服务器 | `rebuild-static.sh` | 立即（需手动部署脚本）|
| **cron rebuild** | 服务器 | 每天 03:00 | 最迟 24h |

`publish-release.sh` 步骤 3 已经会 `npm run generate`，所以**走正常发版天然 rebuild**。

### 5.2 rebuild-static.sh

**当前状态**：默认**不部署到服务器**——`publish-release.sh` 不打它，`deploy-server.sh` 也不装它。在 ECS 上直接跑 `bash /opt/myblog/scripts/rebuild-static.sh` 会因找不到 `package.json` 立即 exit 1。

（路径已统一：`rebuild-static.sh` 和 `deploy-server.sh` 默认 `STATIC_DIR` 均为 `/opt/myblog/frontend`。）

**升级时本地 rebuild**：

```bash
cd frontend && NUXT_PUBLIC_API_BASE=https://yourname.com/api/v1 npm run generate
# 然后照常 ./scripts/publish-release.sh（不带参数）→ 服务器会拿到新静态文件
```

**真正的"服务器上原地 rebuild"目前不支持**（脚本未发布，且需要 node 运行时）。
如果一定要立即生效：本地 rebuild → publish → 部署。

### 5.3 verify-sqlite.sh（端到端 29 端点验证）

**当前状态**：默认**不部署到服务器**。

⚠️ **`verify-sqlite.sh` 第 7 行硬编码 `BASE="http://localhost:8080/api/v1"`**（直接赋值，不是 `${BASE:-...}`），
   **任何 `BASE=...` 环境变量前缀传进去都会被覆盖掉**。所以下面的命令**第一条是无效的**——必须走第二条的 scp 方案。

**正确姿势**（**只能**在 ECS 上跑）：

```bash
# 唯一有效姿势：先把脚本 scp 到 ECS，再 ssh 上去跑
# 脚本硬编码 BASE=http://localhost:8080/api/v1，需要 ECS 上后端监听 8080
scp scripts/verify-sqlite.sh myblog@<ecs-ip>:/tmp/
ssh myblog@<ecs-ip> 'bash /tmp/verify-sqlite.sh'

# 如果 ECS 不在公网暴露 8080，可用 SSH 端口转发把 ECS 8080 映射到本机 8080，
# 然后**在开发机**（不是 ECS）上跑：bash scripts/verify-sqlite.sh
# 这种情况脚本依然打 localhost:8080，但 localhost 已经是 ECS 的 8080 了
ssh -L 8080:127.0.0.1:8080 myblog@<ecs-ip>  # 另开终端
bash scripts/verify-sqlite.sh
```

## 9. 场景五：数据备份与恢复

### 9.1 自动备份（blog-backup.sh）

`blog-backup.sh` 支持手动/自动备份，加密后上传到独立 GitHub 仓库 Release。

**手动备份**：
```bash
# 手动应急（密码走 stdin / 交互式）
BACKUP_ENCRYPTION_PASSWORD=xxx \
BACKUP_GITHUB_TOKEN=ghp_xxx \
GITHUB_BACKUP_REPO=owner/my-blog-backup \
bash /opt/myblog/scripts/blog-backup.sh

# dry-run（只打包加密，不上传）
DRY_RUN=1 bash /opt/myblog/scripts/blog-backup.sh
```

**自动备份**（admin 后台点击"立即备份"）：

后端 `ProcessBuilder` 调 `blog-backup.sh`，已设好全部 env（从 `/etc/myblog/myblog.env` 读取）。

**环境变量**：
- `BACKUP_ENCRYPTION_PASSWORD` - 加密密码（8+ 位，绝不打日志）
- `BACKUP_GITHUB_TOKEN` - GitHub PAT（只给 my-blog-backup 仓库用）
- `GITHUB_BACKUP_REPO` - 备份仓库（私有，`owner/my-blog-backup`）
- `SKIP_UPLOADS=1` - 跳过 uploads（只备份 db）
- `SKIP_DB=1` - 跳过 db（只备份 uploads）
- `DRY_RUN=1` - 不上传 GitHub，只在 stage 目录产出

### 9.2 数据恢复（blog-restore.sh）

`blog-restore.sh` 从 GitHub Release 拉加密 dump → 解密 → 停 myblog → 导入 db → （可选）恢复 uploads → 启服 → 健康检查 + 数据校验。

**手动恢复**：
```bash
# 由 RestoreService 通过 systemd-run 启动（独立 cgroup，不被 systemctl stop 杀到）
# 手动调试：export 全部 env 后 bash 跑
export RESTORE_GITHUB_TOKEN=ghp_xxx
export GITHUB_BACKUP_REPO=owner/my-blog-backup
export RESTORE_TAG=v4.2.0
bash /opt/myblog/scripts/blog-restore.sh
```

**恢复流程**：
1. 从 GitHub Release 下载加密 dump（`dev-blog-dump.sql.gz.enc`）
2. SHA256SUMS 校验
3. openssl 解密（AES-256-CBC + PBKDF2 100k）
4. 停 myblog 服务
5. 备份当前 db
6. 调 `sqlite-import.sh` 导入
7. （可选）恢复 uploads
8. 启 myblog 服务
9. 健康检查（`/api/v1/health`）
10. 数据完整性校验（manifest 行数 vs 实际差异超阈值）
11. 写 `.result.json`

**退出码**：
- 0 - 成功
- 20-28 - 各阶段失败（预检 / 下载 / 校验 / 解密 / 导入 / 启服 / 健康检查 / uploads / 数据校验）

## 10. 场景六：本地 Docker 模拟

`deploy-server.sh` 支持 `LOCAL_SIM=1` 本地 Docker 模拟模式，用于本地验证部署流程。

### 10.1 Dockerfile 构建

```bash
# 构建本地模拟镜像
docker build -t myblog-local-sim .

# 启动容器（端口映射）
docker run -d \
  -p 28080:8080 \
  -p 28000:80 \
  -p 28443:443 \
  --name myblog-local-sim \
  myblog-local-sim
```

### 10.2 LOCAL_SIM=1 行为差异

| 行为 | 生产模式（`LOCAL_SIM=0`）| 本地模拟模式（`LOCAL_SIM=1`）|
|---|---|---|
| 依赖安装 | `apt install` 装 JDK/redis/nginx/sqlite3 | 跳过（Dockerfile 已装）|
| 用户创建 | 创建 `myblog` 用户 | 跳过（容器内默认 root）|
| 服务管理 | systemd（`systemctl start/stop`）| supervisord（容器内）|
| nginx 配置 | `/etc/nginx/conf.d/myblog.conf` | 同理（但 reload 用 supervisord）|
| 防火墙 | `firewalld`/`ufw` 放行 | 跳过（容器端口通过 `-p` 暴露）|
| CORS_ORIGINS | `https://yourname.com` | `http://localhost:28000,http://localhost:28080`（浏览器登录用）|

**自动检测**：容器内 `/.dockerenv` 文件存在 → 自动 `LOCAL_SIM=1`。

### 10.3 本地模拟验证流程

```bash
# 1. 构建镜像
docker build -t myblog-local-sim .

# 2. 启动容器
docker run -d -p 28080:8080 -p 28000:80 --name myblog-local-sim myblog-local-sim

# 3. 进入容器跑部署
docker exec -it myblog-local-sim bash
cd /opt/myblog && bash deploy-server.sh v4.2.0

# 4. 浏览器访问
# http://localhost:28000/
```

## 11. 决策记录（ADR 摘要）

> 完整 ADR 见 [`项目部署解决方案.md`](项目部署解决方案.md) 附录。本节列出对升级操作有影响的 3 条核心决策。

### ADR-001：境外免备案
- **影响**：省去 7-20 天 ICP 备案审核期；代价是国内访问 +20-50ms 延迟
- **升级时操作**：无影响（DNS 已配置好）

### ADR-005（2026-06-17）：v2.6.0 改用 SQLite + 砍 docker
- **影响**：JVM heap 256MB → 512MB；月成本 ¥60 → ¥30
- **升级时操作**：DB 是单文件 `blog.db`；不要用 `mysqldump`；用 SQLite `.backup` 命令或 `sqlite-import.sh`

### ADR-006（2026-06-17）：v2.7.0 改前端全静态
- **影响**：前端内存 150-250MB → 10-20MB；新文章 0-24h 延迟（每日 cron rebuild）
- **升级时操作**：发版时本地 `npm run generate` 跑过即可；服务器 rebuild 见 [§5](#5-场景四全静态化配套)
