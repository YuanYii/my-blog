### 1.2 DEPLOY_MODE

| 模式 | 用途 |
|---|---|
| `init` | 首次初始化（建库 + 种子数据）|
| `full`（默认）| 全量升级（保留 DB + 增量 SQL）|
| `full` + `IMPORT_DB=1` | 代码 + 数据一起升级 |
| `docker-create` | 本地 Docker 首次构建 |
| `docker-init` | 本地 Docker 业务初始化 |

| 场景 | DB 行为 | user | api_whitelist | 其他 17 张表 | _migration_history |

## 2. 场景一：项目初始化

首次从零部署。**风险**：所有业务数据清空。

### 2.1 前提

- [ ] JDK 8+、Node.js 20+、Maven
- [ ] `backend/pom.xml` 的 `<revision>` 正确
- [ ] ECS SSH 可达，域名已解析

### 2.2 本地打包

```bash
export GITHUB_REPO=YuanYii/my-blog-prov
./scripts/publish-release.sh
# 完成后从输出获取 TAG
```

### 2.3 服务器部署

```bash
ssh myblog@<ecs-ip>
GITHUB_REPO=YuanYii/my-blog-prov
curl -L "https://github.com/$GITHUB_REPO/releases/latest/download/deploy-server.sh" \
    -o "deploy-server.sh"
chmod +x "deploy-server.sh"

export GITHUB_REPO=$GITHUB_REPO
export DEPLOY_MODE=init
sudo -E ./deploy-server.sh v6.0.2
```

### 2.4 验收

```bash
curl -s http://127.0.0.1/api/v1/health          # 服务正常
curl -sI http://127.0.0.1/                       # 前端 200
curl -s http://127.0.0.1/api/v1/articles | jq '.data.total'  # 期望 0
```

### 2.5 初始化后必做

- [ ] 改 admin 密码
- [ ] 配 `/etc/myblog/myblog.env` 的 `CORS_ORIGINS`（必填）
- [ ] 配设备授权

### 2.6 关键环境变量

| 变量 | 说明 |
|---|---|
| `JWT_SECRET` | 首次自动生成，**绝对不要覆盖** |
| `CORS_ORIGINS` | **必填**，逗号分隔（首次为占位值，需手动改成真实域名） |
| `BACKUP_ENCRYPTION_PASSWORD` | 首次自动生成，丢失则备份无法解密 |
| `GITHUB_BACKUP_REPO` / `BACKUP_GITHUB_TOKEN` | 启用 GitHub 备份时必填 |

其他部署控制变量（按需设置）：

| 变量 | 默认 | 说明 |
|---|---|---|
| `SKIP_DEPS` | `0` | 设为 1 跳过依赖安装（已装过 JDK/nginx/redis 的服务器） |
| `ENABLE_HTTPS` | `0` | 设为 1 自动申请 Let's Encrypt 证书（需同时设 HTTPS_DOMAIN + HTTPS_EMAIL） |
| `OPEN_FIREWALL` | `1` | 设为 0 跳过自动防火墙放行 |
| `SERVER_PORT` | `8080` | Spring Boot 端口 |
| `PUBLIC_PORT` | `80` | nginx 端口 |

## 3. 场景二：全量代码升级

最常用。DB 保留，跑增量 SQL。

### 3.1 本地打包

```bash
export GITHUB_REPO=YuanYii/my-blog-prov
./scripts/publish-release.sh
```

### 3.2 服务器部署

```bash
ssh myblog@<ecs-ip>
GITHUB_REPO=YuanYii/my-blog-prov
curl -L "https://github.com/$GITHUB_REPO/releases/latest/download/deploy-server.sh" \
    -o "deploy-server.sh"
chmod +x "deploy-server.sh"
export GITHUB_REPO=$GITHUB_REPO
export DEPLOY_MODE=full
sudo -E ./deploy-server.sh v6.0.2
```

### 3.3 验收

```bash
curl -s http://127.0.0.1/api/v1/health
curl -s http://127.0.0.1/api/v1/articles | jq '.data.total'  # 期望 > 0
sqlite3 /opt/myblog/db/blog.db "SELECT * FROM _migration_history ORDER BY executed_at DESC LIMIT 5;"
```

### 3.4 带数据迁移（IMPORT_DB=1）

**风险**：全量覆盖 prod DB，`admin_device` / `page_view` 会清空。

```bash
# 方式 A：手动
bash scripts/sqlite-export.sh --exclude page_view -o /tmp/migration.sql.gz.enc
scp /tmp/migration.sql.gz.enc myblog@<ecs-ip>:/tmp/
ssh -t myblog@<ecs-ip> "sudo bash /opt/myblog/scripts/sqlite-import.sh /opt/myblog/db/blog.db /tmp/migration.sql.gz.enc"

# 方式 B：发布时打包
EXPORT_DB=1 ./scripts/publish-release.sh
IMPORT_DB=1 sudo -E "./deploy-server.sh" v6.0.2
```

## 4. 场景三：系统升级（Web UI 一键升级）

v5.3.0+ 支持从管理后台一键升级到新版本，无需 SSH 登录服务器。

### 4.1 操作步骤

1. 登录管理后台 → 系统升级
2. 查看可用版本列表（从 GitHub Release 获取）
3. 选择目标版本 → 点击「一键升级」
4. **SSE 流式日志**：升级过程实时展示，每行日志即时可见
5. 升级完成后自动刷新状态

### 4.2 升级历史

- 管理后台 → 系统升级 → 升级历史
- 查看每次升级的版本、耗时、状态（成功/失败）
- 升级失败后可查看**完整失败详情**（错误日志）

### 4.3 升级失败回滚

若升级失败，可通过 §9 紧急回滚手动操作。

## 5. 场景四：增量 SQL 升级（应急）

只补表结构/数据，不动代码。deploy-server.sh 在 full 模式下自动执行 `upgrade.sql`，通常无需手动操作。

### 5.1 自动机制

- `docs/sql/upgrade.sql`：通用增量升级脚本（幂等可重复执行）
- full 模式部署时自动执行：先跑 `CREATE TABLE/INDEX IF NOT EXISTS` 幂等部分，再逐条 `PRAGMA table_info` 检查后执行 `ALTER TABLE`

### 5.2 手动执行（应急）

```bash
ssh myblog@<ecs-ip>
sqlite3 /opt/myblog/db/blog.db < docs/sql/upgrade.sql
```

### 5.3 查看迁移历史

```bash
sqlite3 /opt/myblog/db/blog.db "SELECT * FROM _migration_history ORDER BY executed_at DESC LIMIT 10;"
```

## 8. 数据备份与恢复

### 8.1 备份

```bash
BACKUP_ENCRYPTION_PASSWORD=xxx \
BACKUP_GITHUB_TOKEN=ghp_xxx \
GITHUB_BACKUP_REPO=owner/my-blog-backup \
bash /opt/myblog/scripts/blog-backup.sh
```

### 8.2 应急恢复

```bash
sudo systemctl stop myblog
ls -lt /opt/myblog/db/backups/ | head -5
sudo cp /opt/myblog/db/backups/blog-before-*-YYYYMMDD-HHMMSS.db /opt/myblog/db/blog.db
sudo chown myblog:myblog /opt/myblog/db/blog.db
sudo systemctl start myblog
```

## 10. 故障排查

| 症状 | 第一步 |
|---|---|
| 80 端口连不上 / 502 | `journalctl -u myblog -n 100` |
| `Could not resolve placeholder` | 检查 `/etc/myblog/myblog.env` |
| 升级后 401 | 检查 `JWT_SECRET` 是否被改 |
| SQLite locked | 检查 WAL 模式 |
| 跨域报错 | 检查 `CORS_ORIGINS` |
| 增量 SQL 失败 | 看脚本输出的失败文件名 |
| 前端新文章没出现 | 重新跑一次 full 部署 |

### 11.3 历史日志迁移

**背景**：v4.0.0 ~ v4.3.0 期间 Logback 归档文件直接放在 `/opt/myblog/logs/` 根目录，v4.3.0+ 改为 `archive/YYYY-MM/` 子目录，但旧文件不会自动移动。

**迁移脚本**：`/opt/myblog/logs/migrate-logs.sh`

**使用方法**：

```bash
# 预览模式（只看不执行）
sudo bash /opt/myblog/logs/migrate-logs.sh --dry-run

# 执行迁移（将两天前的日志移动到 archive/YYYY-MM/）
sudo bash /opt/myblog/logs/migrate-logs.sh
```

**脚本功能**：
1. 扫描 `/opt/myblog/logs/` 根目录下的日志文件
2. 解析文件名中的日期（如 `blog-2026-06-19.0.log`）
3. 如果文件名无法解析日期，则使用文件修改时间
4. 将两天前的文件移动到 `archive/YYYY-MM/` 子目录
5. 跳过活跃日志文件（`blog.log`、`app.log` 等）

**注意**：
- 建议部署后首次执行 `--dry-run` 预览，确认无误后再执行
- 迁移后文件会保留原文件名，只是位置变化
