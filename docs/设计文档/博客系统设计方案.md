## 1. 项目概述

### 1.1 目标

搭建一个**前后端分离**的个人博客系统，支持 PC 与移动端响应式访问，提供文章发布、分类标签、评论、检索等基础能力。

### 1.2 范围

**包含**（首期交付）：
- 文章发布与管理（Markdown 编辑，前端 marked + DOMPurify 实时预览）
- 分类、标签、归档、热门标签
- 评论（树形嵌套回复，游客可评论）
- 后台管理（单管理员）
- 响应式前端（PC / 平板 / 移动端）
- 基础 SEO + RSS 订阅
- 文件上传（封面图 + Markdown 内嵌图片，本地存储）
- 设置中心：6 个 tab（个人资料 / 站点信息 / 主题外观 / 社交账号 / 偏好设置 / 高级）
  - 注：实际实现 6 tab 内容是 个人资料/站点信息/主题外观/社交账号/偏好设置/高级（与"不包含"中的数据导入/导出、媒体库一起移入 Roadmap）
- 后台仪表盘：KPI 卡片、访问趋势、分类分布、待办清单、站点状态

**不包含**（首期不做，移入 Roadmap）：
- 多用户体系
- 付费阅读 / 会员
- 实时通知 / WebSocket
- 多语言
- 邮件通知（已从偏好设置移除）
- 全文检索（首期用 MySQL `LIKE` 兜底）
- 数据导入 / 导出（首期页面已实现但功能后置）
- 媒体库管理（已从 sidebar 移除，图片直接上传）
- 访问统计埋点（首期**无 page_view 表**，仪表盘访问趋势图是 mock 数据）

**首期简化（已落地，不在 Roadmap）**：
- **无 Service 层**：Controller 直调 Mapper（`blog-article` / `blog-comment` 模块）；仅 `blog-auth`（DeviceService / ApiWhitelistService / JwtUtil）和 `blog-settings`（SiteSettingsService）有 Service 层
- **密码 BCrypt**：用 Hutool `cn.hutool.crypto.digest.BCrypt.checkpw()` 校验，user 表 `password_hash` 字段为 BCrypt hash（**AGENTS.md §4.4 提到的"密码明文比对"是早期计划，实际代码已用 BCrypt**）
- **评论扁平列表**：DB schema 保留 `comment.parent_id` 字段，但接口只返回扁平列表，**未实现树形递归**（后续如需树形，按 parent_id 递归查询即可）
- **仪表盘直接查 DB**：无定时任务 `DashboardAggregationJob`，无 Redis `dashboard:yesterday:*`；KPI 实时查 DB 计算，趋势图 mock 数据
- **缓存仅 site_settings 一项**：文章/列表/分类/标签/阅读数/仪表盘均无 Redis 缓存

### 1.3 非功能性目标

| 指标 | 目标 |
|------|------|
| 首屏加载 | ≤ 2s（4G 网络） |
| 移动端可用性 | 主流机型（iOS 14+ / Android 9+）流畅 |
| SEO | 主要页面被 Google / 百度正常收录 |
| 可维护性 | 新人 1 天内能跑起来 |
| API 文档 | springdoc-openapi 自动生成，无需手写 |

## 2. 技术选型

### 2.1 前端

| 类别 | 选型 | 版本 | 理由 |
|------|------|------|------|
| 框架 | Nuxt 3 | ^3.13 | 基于 Vue 3，原生支持 SSG/SSR，SEO 友好 |
| **包管理** | **npm** | **（注：v2.1 写的是 pnpm ^9，实际项目用 npm）** | 开发机未装 pnpm |
| 样式 | Tailwind CSS | ^3.4 | 响应式类写起来直接，无需 CSS-in-JS |
| **状态管理** | **（未引入 Pinia）** | - | 项目规模小，用 `composables/` + `useState()` 足够 |
| **Markdown 渲染** | **DOMPurify + 自研简易 markdown** | **dompurify ^3.4.8** | **marked/Shiki 未安装**，当前用自研简易 markdown 渲染；DOMPurify 用于 XSS 清洗 |
| **代码高亮** | **（未引入 Shiki）** | - | **当前无代码块高亮**（v2.1 设计用 Shiki 双主题，尚未落地） |
| HTTP | ofetch | ^1.4 | Nuxt 3 内置，无需 axios |
| 类型 | TypeScript | ^5.5 | 全量类型化 |

> **关键决策（v3.0 更新）**：Markdown 渲染放前端，但当前是**自研简易解析**（不是 marked）。后端只存 `content_md` 原文，详情接口返回原文，前端解析 + DOMPurify 清洗 XSS。
> **优点**：后端零渲染开销、CDN 友好、前端可控。
> **缺点**：代码块高亮 / 复杂语法（表格、引用块嵌套）支持有限；marked+Shiki 完整方案是 Roadmap（详见 §9）。

> **备选**：若团队更熟 React，可替换为 Next.js 14（App Router），架构不变。

### 2.2 后端

| 类别 | 选型 | 版本 | 理由 |
|------|------|------|------|
| **构建工具** | **Maven** | 3.6+ | Java 生态主流（开发机 3.6 即可） |
| **框架** | **Spring Boot** | **2.7.18** | **v2.1 写的 3.3.5 受 Java 1.8 限制降级**（MyBatis-Plus 3.5+ / Spring Boot 3.x 都要 JDK 17+） |
| **JDK** | **Java** | **1.8** | **v2.1 写的 21 LTS 因开发机只有 1.8 降级**；详见 README §六.1 环境降级链 |
| **ORM** | **MyBatis-Plus** | **3.4.3.4** | **v2.1 写的 3.5.9 因要 JDK 17 降级** |
| **数据库（默认）** | **SQLite** | **3.45** | **v2.6.0 起 dev/prod 默认**，一文件 0 内存占用，1C2G 友好 |
| 数据库（可选） | MySQL | 8.0 | 备选 profile（`spring.profiles.active=*,mysql` 切回），工具链完善 |
| 缓存 | Redis | 7.x | **仅 site_settings 一项接入 Redis 5min 缓存**；其余缓存为设计目标未落地 |
| **鉴权** | **JJWT** | **0.11.5** | **v2.1 写的 0.12.6 因 Spring Boot 2.7.x 兼容性降级** |
| 工具库 | Hutool | 5.8.x | 减少样板代码（**BCrypt 也来自 Hutool：`cn.hutool.crypto.digest.BCrypt`**） |
| 简化代码 | Lombok | 1.18.x | Getter/Setter/Builder |
| **API 文档** | **springdoc-openapi-ui** | **1.7.0** | **v2.1 写的 2.6.0 因 Spring Boot 2.7.x 兼容性降级**；1.7.0 是 2.6 的 Spring Boot 2.7 兼容版本 |

> **环境降级说明（重要）**：v2.1 文档写的版本是"理想目标"，但开发机环境只有 JDK 1.8，强行升级会破坏所有依赖。降级链：JDK 1.8 → Spring Boot 2.7.x → MyBatis-Plus 3.4.x → JJWT 0.11.x → springdoc 1.7.0。**未来 agent 不要尝试升级这些版本到"原始目标"**。
> 
> **不引入 MapStruct**：项目规模小，MyBatis-Plus 自带的 `BeanUtil` 足够。
> **不引入 Spring Security**：用自实现 `AdminAuthFilter`（位于 `com.blog.common.security`）拦截 + 手动 JWT 解析 + `api_whitelist` 表最长前缀匹配，配置更轻量。

| 类别 | 选型 | 备注 |
|------|------|------|

## 3. 系统架构

### 3.1 总体架构

```
┌─────────────────┐         ┌──────────────────┐
│  浏览器 / 移动端 │ ──HTTP─▶│  Nuxt 3 前端     │
│  (响应式 Web)   │         │  (SSG + ISR)     │
└─────────────────┘         └────────┬─────────┘
                                     │ RESTful API
                                     │ (JSON, /api/v1)
                                     ▼
                            ┌──────────────────┐
                            │  Nginx 反向代理  │
                            └────────┬─────────┘
                                     │
                                     ▼
                            ┌──────────────────┐
                            │  Spring Boot 后端│
                            │  :8080/api/v1    │
                            └────┬──────┬───────┘
                                 │      │
                          ┌──────▼┐   ┌─▼────┐
                          │SQLite │   │Redis │
                          │blog.db│   │:6379 │
                          │v2.6 默认│  └──────┘
                          └───────┘
                                 │
                          ┌──────▼──────┐
                          │  本地磁盘   │
                          │ /uploads/   │
                          └─────────────┘
```

> **v2.6.0 起数据库变更**：默认改为 SQLite 一文件（图中 `SQLite blog.db`），MySQL 降级为可选 profile（`spring.profiles.active=*,mysql` 切回时仍走 MySQL 容器）。v3.1 §3.3 部署架构图为当前权威版本（无 docker + systemd + 全静态前端）。

### 3.2 分层架构（后端）

```
Controller  ── 接收请求、参数校验、返回统一响应
    ↓
Service     ── 业务逻辑、事务控制、缓存策略
    ↓
Mapper      ── 数据库访问（MyBatis-Plus）
    ↓
Database
```

辅助层：
- `common/`：统一响应 `Result`、状态码 `ResultCode`、业务异常 `BusinessException`、全局异常处理 `GlobalExceptionHandler`、分页对象 `PageRequest` / `PageResult`
- `config/`：CORS、MyBatis-Plus 分页插件、springdoc-openapi
- `jwt/`：JWT 工具 `JwtUtil`、过滤器 `JwtAuthenticationFilter`、配置 `JwtConfig`（不引入 Spring Security）
- `entity/`：数据库实体（5 张表）
- `dto/` / `vo/`：入参 / 出参对象
- `schedule/`：定时任务（仪表盘昨日数据聚合）

### 3.3 部署架构

> **2026-06-17 v3.1 更新**：v2.5.0 之前是"5 容器 Docker Compose + Nuxt SSR"；**v2.6.0 起改为"无 docker 1C2G + SQLite"**；**v2.7.0 起前端改为"nuxt generate 全静态 + nginx:alpine serve"**。
> 详细 changelog 见 `docs/changelogs/2026-06-17-v2.6.0-sqlite-migration.md` + `docs/changelogs/2026-06-17-v2.7.0-nuxt-static.md`。

**当前架构（v2.6.0 + v2.7.0）**：

```
                       ┌─────────────────────┐
                       │  浏览器 / 移动端     │
                       └──────────┬──────────┘
                                  │ HTTPS
                                  ▼

                       │  Nginx (apt)        │

       ┌──────────────────┐              ┌─────────────────────┐
```

**关键变化**（对比 v3.0）：

| 维度 | v3.0（v2.5.0 之前） | v3.1（v2.6.0 + v2.7.0） |
|---|---|---|
| 前端进程 | node 20 + Nitro server（150-250MB） | **nginx:alpine** 静态服务（10-20MB） |
| 数据库 | MySQL 8.0 容器 | **SQLite** 文件（MySQL 降级可选） |
| 缓存 | redis:7-alpine 容器 | redis-server 系统服务（apt） |
| 编排 | docker-compose 5 容器 | **systemd**（myblog.service） |
| 构建 | `nuxt build`（SSR） | **`nuxt generate`**（全静态） |
| 公开页 SEO | CSR 空 HTML | **预渲染 13 个静态 HTML** |
| 新文章延迟 | 即时 | 0-24h（每日 cron rebuild） |
| JVM heap 上限 | 256MB（1C2G 极限） | **384MB**（v2.7.0 释放前端内存） |

### 5.3 关键流程

#### 5.3.1 发布文章

```
1. 管理员在后台填写 Markdown → 提交
2. 后端：
   a. @Valid 校验参数
   b. 写入 article 表（status=1, published_at=now）
   c. 写 article_tag 关联
   d. 删除该文章相关 Redis 缓存
3. 返回成功 → 前端提示并跳转
```

> **注意**：后端**不渲染** HTML，只存 `content_md` 原文。前端用 marked 渲染。

#### 5.3.2 获取文章详情

> ⚠️ **计划中（尚未落地）**：以下流程中的「Redis 缓存文章详情」与「`POST /api/v1/articles/{slug}/view` 异步上报阅读量」当前**均未实现**。实际代码中 `GET /articles/{slug}` 直接查库返回，无 Redis 文章缓存，也没有 `/view` 端点（目前仅 `site_settings` 接入了 Redis 5min 缓存）。保留本设计作为后续目标。

```
1. 前端 GET /api/v1/articles/{slug}
2. 后端：
   a. 查 Redis 缓存：key=`article:{slug}`
   b. 命中 → 直接返回 content_md
   c. 未命中 → 查 DB → 写缓存（TTL 1h） → 返回
3. 前端拿到 content_md → marked 解析 + DOMPurify 清洗 → 渲染
4. 异步（POST /api/v1/articles/{slug}/view）：
   a. Redis INCR article:view:{id}
   b. 写 article_view_log（按天聚合）
```

#### 5.3.3 评论提交

```
1. 游客提交评论（昵称、邮箱、URL、内容）
2. 后端：
   a. @Valid 校验内容
   b. 敏感词过滤（首期用简单词表，后期可换 DFA）
   c. 写 comment 表（默认 status=0 待审）
   d. 清除文章评论缓存
3. 管理员后台审核（通过/屏蔽/删除）
4. 已通过的评论对外可见
```

#### 5.3.4 仪表盘数据聚合

```
每日凌晨 02:00 定时任务：
  1. 查询 article_view_log，按 article_id 分组，统计「昨天」的 view_count 增量
  2. 写入 article.view_count（累加）
  3. 计算「昨天」的 KPI：
     - 文章 PV 总数 = SUM(article.view_count 增量)
     - 新发布文章数 = COUNT(article WHERE published_at BETWEEN 昨天 00:00 - 23:59)
     - 待审评论数 = COUNT(comment WHERE status=0)
     - 总字数 = SUM(article.content_md.length)
  4. 写入 Redis dashboard:yesterday:{metric}

仪表盘请求：
  GET /api/v1/admin/dashboard
  1. 读 Redis dashboard:yesterday:* 拿到昨日数据
  2. 查 DB 拿到「总文章数」「已发布」「草稿」（实时）
  3. 查 DB 拿到「近 30 天文章阅读趋势」（按天聚合）
  4. 组装 VO 返回
```

### 5.4 缓存策略

> **实现状态**：当前**仅 `site_settings` 已接入 Redis**（key 前缀 `site_settings:`，TTL 5min，`StringRedisTemplate` 存 JSON 字符串，写操作主动失效）。下表其余条目为**设计目标，尚未落地**。

| 数据 | Key | TTL | 失效时机 | 状态 |
|------|-----|-----|----------|------|
| 站点设置 | `site_settings:{section}` | 5m | 设置更新 | ✅ 已实现 |
| 文章详情 | `article:{slug}` | 1h | 文章更新 / 删除 | 🔜 计划中 |
| 文章列表 | `articles:list:{page}:{filter}` | 10m | 文章发布 / 更新 | 🔜 计划中 |
| 分类列表 | `categories:all` | 24h | 分类变更 | 🔜 计划中 |
| 标签列表 | `tags:all` | 24h | 标签变更 | 🔜 计划中 |

| 仪表盘昨日数据 | `dashboard:yesterday:{metric}` | 26h | 定时任务刷新 | 🔜 计划中 |
| 分类分布 | `dashboard:categories` | 6h | 文章分类变更时失效 | 🔜 计划中 |

### 5.5 鉴权

- **前端门户**：完全匿名，无需登录
- **后台管理**：
  - `POST /api/v1/auth/login` 接收 username + password
  - BCrypt 校验密码（Spring Security Crypto 模块）
  - 校验成功后签发 JWT（有效期 7 天，HS256，secret 256 bit）
  - 后续请求带 `Authorization: Bearer <token>` 与 `X-Device-Id: <设备指纹>`（均放在 Header）
  - 自实现 `AdminAuthFilter`（`com.blog.common.security`）拦截 → 查 `api_whitelist` 最长前缀匹配判定放行/鉴权 → 解析 token（不用 Spring Security）
  - 设备校验：token 的 `deviceId` claim 必须与 `X-Device-Id` 一致，且该设备在 `admin_device` 为 `approved`（待授权 2001 / 已吊销 2002）
  - 角色控制：JWT claims 含 `role`，admin 接口手动校验
- **刷新策略**（首期简化）：Token 7 天有效，过期后重新登录。后期可加 Refresh Token。

**鉴权规则**：
- 放行/鉴权由 `AdminAuthFilter`（`com.blog.common.security`）按 `api_whitelist` 表**最长前缀匹配**判定，不再硬编码路径
- `public` 前缀：GET/HEAD 匿名放行；写方法（POST/PUT/DELETE/PATCH）默认要求 token，仅 `POST /auth/login` 与 `POST /comments` 例外
- `admin` 前缀：一律要求 token + 设备校验（`X-Device-Id` 须为 `approved` 且与 token claim 一致）
- 缺少 / 无效 / 过期 token 返回 401；设备未授权 2001 / 已吊销 2002

**字段命名**：所有响应字段统一 **camelCase**（如 `articleId`/`createdAt`/`userId`），即使数据库列是 `snake_case`，SQL 里用 `AS` 别名映射。

**错误码规范**（与 `com.blog.common.ResultCode` 一致）：

| code | 含义 | code | 含义 |
|------|------|------|------|
| 200 | 成功 | 1000 | 业务异常 |
| 400 | 参数错误 | 1001 | 文章不存在 |
| 401 | 未登录 / token 无效 | 1002 | 分类不存在 |
| 403 | 无权限 | 1003 | 标签不存在 |
| 404 | 资源不存在 | 1004 | 评论不存在 |
| 405 | 请求方法不允许 | 1005 | 用户不存在 |
| 500 | 服务器内部错误 | 1006 | 用户名或密码错误 |
| 2001 | 设备未授权 | 1007 | Token 无效或已过期 |
| 2002 | 设备已吊销 | 2003 | 不能吊销当前登录设备 |

### 8.4 风险与对策

| 风险 | 概率 | 影响 | 对策 |
|------|------|------|------|
| Nuxt 3 生态迭代快，文档不全 | 中 | 中 | 锁版本；遇坑查 GitHub Issues |
| 移动端适配细节多 | 高 | 低 | Tailwind 标准化，先做 PC 再补移动 |
| Markdown XSS | 中 | 高 | 前端 DOMPurify 必装，不依赖后端 |
| MySQL 单表过大影响性能 | 低 | 中 | 早期分页索引足够；后期再分库分表 |
| **SQLite 单写者锁（v2.6.0）** | 中 | 中 | Hikari `maximum-pool-size: 1` 必须保持；公开页 `PageViewFilter` 5 并发会排队（实测 5 次/articles 5 秒），个人博客可接受 |
| **page_view 无分区（v2.6.0）** | 中 | 中 | SQLite 不支持分区，长期数据会很多；按月清理脚本待加 |
| **新文章 0-24h 延迟（v2.7.0）** | 高 | 低 | 个人博客可接受；rebuild 频率提升或改事件触发（v2.7.0 backlog） |
| **构建时短暂吃 200-300MB（v2.7.0）** | 高 | 低 | 选凌晨低峰（cron 已配 3 点），构建 ~60s 完事 |
| 部署成本超预算 | 中 | 低 | 先用 Vercel + Railway 跑通，再迁移 |
| JWT 密钥泄漏 | 低 | 高 | 用 Spring `@Value` 从环境变量注入，不写代码 |
