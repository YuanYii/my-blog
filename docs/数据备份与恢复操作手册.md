# 📘 my-blog 数据备份与恢复操作手册

> **目标读者**：admin（站点管理员）
> **版本**：v5.0
> **设计依据**：`docs/design/博客数据备份方案设计.md` + `docs/design/博客数据恢复方案设计.md`
> **上次更新**：2026-06-24

---

## 1. 一分钟理解

**风险**：硬盘挂了、被恶意 rm、手贱删库、迁移机房——任何一种都会丢东西。

**这套方案做什么**：
- **备份**：admin 后台一键把 `blog.db` + `uploads/` **加密打包** → 上传到 **独立 GitHub 备份仓库** 的 Release
- **恢复**：admin 后台选一条 SUCCESS 备份 → **同 JVM 进程内** 解密 + 替换 db → **不停服 10-60 秒** 完成
- **备份同步**：迁移到新机器时，从 GitHub 备份仓库一键同步最近 3 条 release 元数据到本地，回填 `backup_record` 表后即可走正常恢复流程

**关键不变量**：
- 上传到 GitHub 的 `.enc` 文件 **是加密的**，没有密码拿到也解密不出来
- 加密密码 **只在服务器本地** `/etc/myblog/myblog.env`，不进日志、不进 db、不返回前端
- 备份期间后端 **正常服务**（SQLite WAL online backup）
- 恢复期间后端 **也正常服务**（SQLite Online Backup API 原地替换，v5.0 同进程模式）

**架构概览**：

```
备份链路 (v4.2.0)
  admin UI → POST /admin/backup/run
          → BackupService.runScriptAsync → ProcessBuilder
          → scripts/blog-backup.sh
          → sqlite-export.sh dump + 加密 + tar uploads + 加密
          → gh release create / curl upload → GitHub Release
          → 写 .blog-backup-result.{id}.json
          → BackupStartupReconciler 回填 → SUCCESS

恢复链路 (v5.0)
  admin UI → POST /admin/restore/run
          → RestoreService.runRestoreAsync → @Async, 同 JVM
          → RestoreExecutor.execute (6 步流水线)
            DOWNLOAD → VERIFY → DECRYPT → IMPORT → UPLOADS → POSTCHECK
          → 全程同步推进 record 状态, 无脚本, 无重启
          → SUCCESS / FAILED 立即可见
```

## 2. 前置配置（首次部署必做，一次性）

### 2.1 创建独立的 GitHub 备份仓库

**不要**用你发布代码的 `my-blog-prov` 仓库，单独建一个 `my-blog-backup`（建议 **Private**）：

1. GitHub 网页 → New repository
2. 名字：`my-blog-backup`（或随便起，如 `xxx-blog-backup`）
3. **Private**（必须，否则别人能下载到你的 db + uploads 加密包）
4. **不要**勾 Add README / .gitignore（空仓库即可，gh CLI 需要 default branch）

### 2.2 生成 GitHub Personal Access Token

1. GitHub → Settings → Developer settings → Personal access tokens → Tokens (classic) → **Generate new token**
2. **Expiration**：建议 90 天或自定义（过期前重新生成）
3. **Scopes**：只勾 `repo`（完整仓库访问）
4. **不要**勾 admin / delete_repo
5. 复制生成的 token（`ghp_xxx...`）—— **只显示一次**

> 推荐 Fine-grained PAT 限定到 my-blog-backup 仓库，最小权限。

### 2.3 生成备份加密密码

SSH 到服务器：

```bash
openssl rand -base64 24
# 输出类似：b3JyaGVwZUNyaXN0aW5QYXJyb3QgMjAyNg==
```

**复制这个值**，立即存到密码管理器（1Password / Bitwarden）。

### 2.4 写入服务器环境变量文件

env 文件路径：`/etc/myblog/myblog.env`（`chmod 600`，仅 root 可读）。

首次部署时 `deploy-server.sh` 会自动生成模板，编辑：

```bash
sudo vim /etc/myblog/myblog.env
```

补齐三个变量：

```bash
# === 数据备份与恢复 ===
BACKUP_ENCRYPTION_PASSWORD=<2.3 生成的密码>
GITHUB_BACKUP_REPO=YuanYii/my-blog-backup          # 2.1 的仓库
BACKUP_GITHUB_TOKEN=<2.2 的 token>
```

> ⚠️ token 变量名是 `BACKUP_GITHUB_TOKEN`（**不是** `GITHUB_TOKEN`）。发布用的 `GITHUB_TOKEN` 指向 my-blog-prov 仓库，两个 token 完全隔离、独立轮换。

保存后：

```bash
sudo chmod 600 /etc/myblog/myblog.env
sudo systemctl restart myblog   # 重启让 env 生效
```

### 2.5 验证配置生效

浏览器登录 admin → **系统 → 数据备份**。

**如果配置不对**，点「立即备份」会立刻报具体错：
- "BACKUP_ENCRYPTION_PASSWORD 未配置" → 检查 env 第 1 行
- "BACKUP_GITHUB_TOKEN 未配置" → 检查 env 第 3 行
- "GITHUB_BACKUP_REPO 未配置" → 检查 env 第 2 行

三项都配了，点「立即备份」→ PENDING → RUNNING → SUCCESS（耗时 30s-10min，看 uploads 体积）。

## 3. 日常使用：触发备份

### 3.1 UI 触发（推荐）

1. 登录 admin → **系统 → 数据备份**
2. 顶部点 **「立即备份」**
3. 二次确认弹窗 → **确认**
4. 顶部出现 **当前任务卡片**：
   - `PENDING` → 已加入队列
   - `RUNNING` → 正在打包/加密/上传，**不要刷新页面**
   - `SUCCESS` → ✅ 显示 tag（如 `backup-20260620-153012`）+ asset 链接
   - `FAILED` → ❌ 显示失败阶段 + 错误信息
5. 终态自动 Toast 通知

**轮询**：前端每 2s 拉一次 `/admin/backup/{id}`，到终态自动停。

### 3.2 手动 SSH 触发（应急）

服务器本地应急（UI 坏了 / 跳过 UI 鉴权）：

```bash
# 加载 env
set -a; source /etc/myblog/myblog.env; set +a

# DRY_RUN=1 不上传, 只产本地 stage 目录产物
DRY_RUN=1 sudo -E bash /opt/myblog/scripts/blog-backup.sh

# 真跑（加密 + 上传 GitHub）
sudo -E bash /opt/myblog/scripts/blog-backup.sh
```

`-E` 是 `sudo` 保留当前 shell 的 env（**必须**，否则 env 文件那 3 个变量在 sudo 子进程里都消失了）。

### 3.3 可选环境变量

跑 `blog-backup.sh` 时可覆盖默认值：

| 变量 | 默认 | 用途 |
|---|---|---|
| `SKIP_UPLOADS=1` | 不跳过 | 只备份 db（uploads 太大时） |
| `SKIP_DB=1` | 不跳过 | 只备份 uploads |
| `BACKUP_STAGE_DIR=/tmp/blog-backup-stage` | 默认值 | 明文中转目录（trap 自动清） |
| `SQLITE_PATH=/opt/myblog/blog.db` | 默认值 | db 路径 |
| `UPLOAD_DIR=/opt/myblog/uploads` | 默认值 | 上传目录 |
| `BACKUP_KEEP_RECORDS=30` | 30 | 保留最近 N 条 SUCCESS（超出自动删 GitHub Release + db 行） |
| `DRY_RUN=1` | 0 | 只产本地产物，不上传 GitHub |

## 4. 备份产物

每次 SUCCESS 备份在 GitHub Release 留 4 个文件：

| 文件 | 类型 | 大小 | 加密？ | 作用 |
|---|---|---|---|---|
| `blog-YYYYMMDD-HHMMSS.sql.gz.enc` | 数据库加密包 | db 体积 ~50% | ✅ AES-256-CBC | 完整 SQLite 库 dump |
| `uploads-YYYYMMDD-HHMMSS.tar.gz.enc` | 上传文件加密包 | 压缩后 ~60% | ✅ AES-256-CBC | 全部图片/附件 |
| `manifest.json` | 元数据 | ~5 KB | ❌ 明文 | db 表行数 / uploads 文件数 / 时间 / SHA256 |
| `SHA256SUMS` | 校验和 | <1 KB | ❌ 明文 | 前 3 个文件的 SHA256 |

**Release 命名**：`backup-YYYYMMDD-HHMMSS`（北京时间）。

**加密算法**：AES-256-CBC + PBKDF2-HMAC-SHA256 + 每文件随机 salt（**iter=10**，配合强密码使用；不要使用弱密码）。

GitHub 网页上看到：
```
https://github.com/yourname/my-blog-backup/releases/tag/backup-20260620-153012
├─ blog-20260620-153012.sql.gz.enc
├─ uploads-20260620-153012.tar.gz.enc
├─ manifest.json
└─ SHA256SUMS
```

## 5. 日常使用：触发恢复（v5.0 · 同 JVM 不停服）

> **v5.0 关键变化**：不再调用外部脚本、不重启 myblog 进程、不依赖 sudo / systemd-run / supervisorctl / gh / jq。整个恢复在 JVM 内同步执行，10-60 秒完成。

### 5.1 UI 触发（唯一推荐方式）

1. 登录 admin → **系统 → 数据恢复**（侧栏菜单）
2. 从下拉框选一条状态为 **SUCCESS** 的备份（按时间倒序）
3. 选择 **恢复范围**：
   - `DB_ONLY`（默认）— 仅恢复数据库
   - `DB_UPLOADS` — 数据库 + uploads 文件
4. 点 **「数据恢复」** → 二次确认（红色警示弹窗）
5. 任务卡片显示进度：
   - `PENDING` → 已加入队列
   - `RUNNING` → 正在执行 6 步流水线（DOWNLOAD/VERIFY/DECRYPT/IMPORT/UPLOADS/POSTCHECK）
   - `SUCCESS` → ✅ 成功；如有数据校验差异显示 `verifyDiff`
   - `FAILED` → ❌ 显示失败 stage + errorMessage
   - `UNKNOWN` → ⚠️ JVM 在恢复中崩溃（极罕见，仅在 OOM / kill -9 场景出现）
6. 终态自动 Toast，恢复历史列表实时刷新

**轮询**：每 2s 拉 `/admin/restore/{id}`，退避到最大 30s，到终态自动停。

### 5.2 v5.0 恢复的 6 步流水线

| Step | stage 名称 | 执行内容 | 典型耗时 |
|------|-----------|---------|---------|
| 1 | `DOWNLOAD` | HttpURLConnection 拉 manifest.json / SHA256SUMS / *.enc | 2-5s |
| 2 | `VERIFY` | java.security.MessageDigest 校验每个 .enc 的 SHA256 + 解析 manifest | <1s |
| 3 | `DECRYPT` | AES-256-CBC + PBKDF2 解密 + GZIPInputStream 解压 → 明文 .sql | 1-3s |
| 4 | `IMPORT` | 用 .sql 构建 staged sqlite → SQLite Online Backup API 原地替换 live db | 2-5s |
| 5 | `UPLOADS` | scope=DB_UPLOADS 时：tar 解到 `uploads.new` → 原子切换 → 异步删旧 | 2-10s（视体积） |
| 6 | `POSTCHECK` | 对比 manifest.table_stats_exact 与实际 SQL `COUNT(*)`（仅记录 verifyDiff，不阻断） | <1s |

**核心特性**：
- ✅ 全程 JVM 内执行，无 sudo / systemd-run / supervisorctl / gh CLI 依赖
- ✅ Docker 与宿主机走完全相同代码路径（uploads volume 挂载点兼容，v5.0.1 修正）
- ✅ HikariCP 连接不重建（IMPORT 阶段锁窗口 < 1s，业务请求 SQLITE_BUSY 自动重试 + busy_timeout=30s）
- ✅ uploads 切换走 mount 内部 entry 级 mv，nginx 无需 stop
- ✅ 失败 stage + errorMessage 立即写库，前端立即可见（不再等 5-30s 回填）
- ✅ IMPORT 后自动 UPSERT admin/123456，确保操作者能重新登入

### 5.3 恢复失败回退

每次恢复在 IMPORT 步骤前 SQLite Online Backup API **自动备份当前 db**（page-level snapshot），失败时 live db **保持原始内容不变**，无需手动回退。

uploads 切换中途失败时，已暂存到 `.restore-old.{ts}/` 的旧 entry 会被 best-effort 移回 top-level；新解出的 `.restore-staging.{ts}/` 直接删除。极端情况下可能留下一两个 `.restore-old.{ts}/` 残留目录，手动 `rm -rf` 即可（不影响 uploads 主功能）。

### 5.4 恢复后登录说明

恢复完 IMPORT 步骤会**自动执行 UPSERT**，强制把 `admin/123456` 写到 user 表：
- 如果备份里 admin 改过密码（如 prod 是 `xxx`），恢复后 admin 密码会**被覆盖为 123456**（destructive，但与"操作者能确定性重新登入"的设计意图一致）
- 如果备份里 admin 已经是 123456，无变化
- 如果备份里没有 admin 用户，插入新 admin 用户（id=1, role=ADMIN）

**会话行为**：恢复后旧 JWT 必然失效（DB 里用户记录已替换），前端会自动跳登录页。这是预期的——恢复操作本来就应让所有旧会话作废。用 admin/123456 重新登入即可。

## 6. 备份同步（新机器迁移 / 备份记录丢失场景）

**场景**：
- 迁移到新服务器，本地 `backup_record` 表为空，从 admin UI 看不到历史备份，无法选择恢复
- 误删了某条 `backup_record` db 行，但 GitHub Release 还在

**解决**：admin 后台 → 数据备份页 → **「备份同步」** 按钮（与「立即备份」并列）。

机制：
1. 后端调 `gh release list --repo $GITHUB_BACKUP_REPO -L 3 --json tagName,publishedAt,assets`（5s 超时）
2. 拉最近 3 条 release，按 tag 在本地查 `selectByTag`，**已存在则跳过**（天然幂等）
3. 不存在的反向 INSERT 一条 `status=SUCCESS` 的 backup_record（字段映射：tag / startedAt = finishedAt = publishedAt / assetCount / assetUrls / operator…）
4. 若 release 内有 `manifest.json` asset，curl 拉取并解析 `db.size_bytes` / `uploads.size_bytes` 填入；拉取失败则填 0（不阻断）
5. UI 列表立即刷新，新同步的记录可立即用于恢复流程

> **注意**：备份同步仅拉**元数据**回填，不下载 `.enc` 文件本身——恢复时才下载。所以同步本身是秒级动作。

> **依赖**：备份同步走 `gh` CLI（与备份链路一致）。如果服务器没装 `gh`，会失败。详见 §8.5。

## 7. 应急恢复（v5.0 同进程恢复不可用时的兜底）

> v5.0 把恢复移进 JVM 后，唯一兜底场景是 **myblog 进程整个起不来**（如部署文件损坏、JDK 没装）。这时需要在 shell 直接用 `sqlite-import.sh` 把 db 恢复出来，让 myblog 能起得来，再走 v5.0 流程恢复 uploads（如需要）。

### 7.1 前置

- 你有 GitHub 备份仓库的访问权限 + 知道 `BACKUP_ENCRYPTION_PASSWORD`
- 服务器装了 `gh`（或 `curl`）+ `openssl` + `sqlite3` + `tar`

### 7.2 应急恢复 DB（让 myblog 能起来）

```bash
# 1. 加载 env
set -a; source /etc/myblog/myblog.env; set +a

# 2. 准备临时目录
mkdir -p /tmp/restore && cd /tmp/restore

# 3. 列出可用的备份 tag
gh release list --repo "$GITHUB_BACKUP_REPO" --limit 10
# 假设选 backup-20260620-153012

TAG=backup-20260620-153012

# 4. 下载备份产物
gh release download "$TAG" --repo "$GITHUB_BACKUP_REPO" --dir .
# 或 curl 兜底:
# curl -L -H "Authorization: token $BACKUP_GITHUB_TOKEN" \
#   "https://github.com/$GITHUB_BACKUP_REPO/releases/download/$TAG/manifest.json" -o manifest.json
# ... 同样下载 *.enc / SHA256SUMS

# 5. 校验完整性
sha256sum -c SHA256SUMS
# 期望: ... OK ... OK ... OK

# 6. 备份当前 db (防万一)
sudo cp /opt/myblog/blog.db "/tmp/blog.db.bak.$(date +%Y%m%d-%H%M%S)" 2>/dev/null || true

# 7. 停服 (若 myblog 还在跑)
sudo systemctl stop myblog 2>/dev/null || true

# 8. 解密 + 导入 db
DB_FILE=$(jq -r '.db.encrypted_file' manifest.json)
sudo -E bash /opt/myblog/scripts/sqlite-import.sh /opt/myblog/blog.db "/tmp/restore/$DB_FILE"
# (交互式输入密码; 或 export DB_DECRYPT_PASSWORD=$BACKUP_ENCRYPTION_PASSWORD + FORCE_IMPORT=1 跳过确认)

# 9. 修属主
sudo chown myblog:myblog /opt/myblog/blog.db

# 10. 启服
sudo systemctl start myblog
```

### 7.3 应急恢复 uploads（很少用，通常走 UI 的 DB_UPLOADS scope）

```bash
UPLOADS_FILE=$(jq -r '.uploads.encrypted_file' /tmp/restore/manifest.json)
sudo openssl enc -d -aes-256-cbc -pbkdf2 -iter 10 \
    -pass env:BACKUP_ENCRYPTION_PASSWORD \
    -in "/tmp/restore/$UPLOADS_FILE" \
  | sudo tar xzf - -C /opt/myblog/
sudo chown -R myblog:myblog /opt/myblog/uploads
```

### 7.4 场景：只想看 db 内容，不想覆盖

```bash
sudo bash /opt/myblog/scripts/sqlite-import.sh /tmp/inspect.db /tmp/restore/blog-XXX.sql.gz.enc
sqlite3 /tmp/inspect.db "SELECT id,title FROM article LIMIT 10;"
# /opt/myblog/blog.db 不受影响
```

## 8. 常见问题

### 8.1 备份失败：errorStage = UPLOAD，"gh release create failed: 401"

**原因**：`BACKUP_GITHUB_TOKEN` 失效（过期 / 被 revoke）。

**修法**：
1. GitHub → 重新生成 token（推荐 Fine-grained PAT，限定 my-blog-backup 仓库）
2. 替换 `/etc/myblog/myblog.env` 的 `BACKUP_GITHUB_TOKEN=...`
3. `sudo systemctl restart myblog`
4. admin 后台重试「立即备份」

### 8.2 备份失败：errorStage = UPLOAD，"404 Not Found"

**原因**：`GITHUB_BACKUP_REPO` 填错。

**修法**：浏览器打开 `https://github.com/<repo>` 确认能访问 → 修正 env → 重启 + 重试。

### 8.3 备份失败：errorStage = UPLOAD，"asset > 2GB"

**原因**：uploads 单文件超 2GB（GitHub Release 单 asset 上限）。

**修法**：`SKIP_UPLOADS=1` 只备份 db；或考虑接对象存储（OSS/S3），不在本手册范围。

### 8.4 备份失败：errorStage = DUMP

**排查**：
```bash
# 1. db 健康检查
sqlite3 /opt/myblog/blog.db "PRAGMA integrity_check;"
# 期望: ok

# 2. 磁盘空间
df -h /opt/myblog/

# 3. 手动跑一次看完整日志
sudo -E bash /opt/myblog/scripts/blog-backup.sh 2>&1 | tee /tmp/backup-debug.log
```

### 8.5 备份同步失败：gh CLI 未安装

**症状**：admin → 数据备份 → 点「备份同步」→ Toast 报 `gh release list 退出码 127: command not found`。

**修法**：
- Ubuntu/Debian：`sudo apt install gh`（或参考 https://github.com/cli/cli#installation）
- 或退而求其次：手动 SSH 用 `curl + GitHub API` 维护 `backup_record` 表（详见后端 `BackupService.syncFromGithub` 实现思路）

### 8.6 恢复失败：errorStage = DOWNLOAD

**原因**：网络拉 GitHub 失败（token 失效 / 网络封锁 / GitHub 抽风）。

**排查**：
```bash
# 服务器上手测 GitHub API
curl -fsS -H "Authorization: token $BACKUP_GITHUB_TOKEN" \
  "https://api.github.com/repos/$GITHUB_BACKUP_REPO/releases/tags/backup-20260620-153012"
```

返回 4xx 看 message，5xx 等几分钟重试。

### 8.7 恢复失败：errorStage = VERIFY

**原因**：SHA256SUMS 与 .enc 文件不一致（下载中途损坏 / GitHub Release 被人改过）。

**修法**：重新触发恢复，让它重下一次；连续失败需检查仓库内容是否被改。

### 8.8 恢复失败：errorStage = DECRYPT

**原因**：密码错（`BACKUP_ENCRYPTION_PASSWORD` 不是这条备份创建时的密码）。

**修法**：密码忘了的备份永久无法解密。详见 §9.

### 8.8.1 恢复失败：errorStage = UPLOADS, `Device or resource busy`

**症状**：Docker 容器内触发恢复 DB_UPLOADS scope，errorMessage 含 `FileSystemException ... Device or resource busy`。

**原因（已修复，v5.0.0 → v5.0.1）**：旧实现把整个 `uploads` 目录改名做原子切换，但 Docker volume 挂载点不能被 rename，内核拒绝。

**已修复**：v5.0.1 起 uploads 切换改为 mount 内部 entry 级 mv，与挂载关系无关。如果你看到这个报错说明跑的是 v5.0.0 代码，升级到包含本修复的版本即可。

### 8.8.2 恢复后 admin/123456 仍然登录不上

**症状**：恢复成功，但用 admin/123456 登录报"用户名或密码错误"。

**原因（已修复，v5.0.0 → v5.0.1）**：旧实现用 `INSERT OR IGNORE`，备份里如果有 admin 用户（非默认密码）会被保留，无法用 123456 登入。

**已修复**：v5.0.1 起改为 UPSERT，IMPORT 完成后强制把 admin 密码覆盖为 bcrypt("123456")。

**若仍登录失败**：
- 确认你用的 v5.0.1+ 代码（grep `ensureAdminUser` 看到 `ON CONFLICT(username) DO UPDATE` 即对）
- 看 backend 日志 `[Restore-IMPORT] ensureAdminUser` 行的 rows 数：>0 表示已执行
- 如果 rows=0 → user 表结构异常，schema-sqlite.sql 兜底建表后再试

### 8.9 恢复失败：errorStage = IMPORT

**原因**：staged sqlite 构建失败 / Online Backup API 异常。

**排查**：
```bash
# 看 backend 日志
journalctl -u myblog --since "10 minutes ago" | grep -E "Restore-IMPORT|RestoreExecutor"

# 检查 /tmp/blog-restore/{recordId}/ 目录 (失败后 finally 块会清, 可能已无内容)
ls -la /tmp/blog-restore/ 2>/dev/null
```

### 8.10 恢复后状态 UNKNOWN

**原因**：JVM 在 RUNNING 中途被强杀（OOM / kill -9 / 容器 OOM-killer / 宿主机断电）。

**机制**：v5.0 `RestoreStartupReconciler` 在 JVM 重启后扫所有 RUNNING > 30min 的 restore_record，标 UNKNOWN + errorStage=ORPHAN。

**修法**：手动检查 live db 是否完整（`PRAGMA integrity_check`），完整则可重新触发一次恢复；不完整需走 §7 应急恢复。

### 8.11 恢复过程中前端断线

v5.0 不停服。如果前端断线说明 myblog **不是因为恢复**而挂了（独立问题，查 `journalctl -u myblog`）。

### 8.12 备份 / 恢复过程中 SSH 断了

没关系，全程在 JVM 异步执行，不依赖 SSH 连接。SSH 重连后看进度：

```bash
# 备份进度
sqlite3 /opt/myblog/blog.db \
  "SELECT id,status,started_at,finished_at,error_stage,error_message
   FROM backup_record ORDER BY id DESC LIMIT 3;"

# 恢复进度
sqlite3 /opt/myblog/blog.db \
  "SELECT id,status,started_at,finished_at,error_stage,error_message,verify_diff
   FROM restore_record ORDER BY id DESC LIMIT 3;"
```

### 8.13 多久备份一次？要不要 cron？

当前版本不内置 cron。建议：
- **活跃期**（天天发文）→ 一周一次
- **稳定期** → 一个月一次
- **改重要数据前**（批量删评论 / 改配置）→ 手动触发一次

> 后续版本计划加 systemd timer 凌晨 3 点自动跑 + 自动清旧 Release（当前靠 `BACKUP_KEEP_RECORDS=30` 维持滑动窗口）。

### 8.14 怎么删除旧备份？

**三条路**：
- **UI 删除（推荐）**：admin → 数据备份 → 列表行末「删除」
  - **SUCCESS** → 弹窗要求输入 `DELETE` 字样 → 同时删 GitHub Release tag 和 db 行（GitHub 删失败仅 WARN，db 行仍删）
  - **FAILED** → 普通二次确认 → 仅删 db 行
  - **PENDING / RUNNING** → 按钮禁用
- **自动**：`BACKUP_KEEP_RECORDS=30` 每次新备份成功后 `trimOldRecords` 保留最近 30 条
- **手动兜底**：GitHub 网页 → Releases → Delete（只删 GitHub，db 留痕）

### 8.15 加密密码忘了怎么办

**结论**：**所有备份永久失效**。AES-256-CBC + PBKDF2 + 每文件随机 salt，没有密码就解不出来。

**预防**：
- 必须用 1Password / Bitwarden / Keychain 等密码管理器存
- 至少在两个不同地方存（如 1Password + 写在纸上锁抽屉 / 写在另一台机器的 env 里）
- 改密码后**所有旧备份也失效**（新旧密码不会兼容）→ 改完立即触发一次新备份重新加密

> 备份采用 **强密码假设**（v4.2.0 OPT-001 起 PBKDF2 iter=10 + 强密码）。如果用了弱密码（字典词、生日、6 位数字），即使是 AES-256 也会被暴力破解；密码必须用 `openssl rand -base64 24` 这种 24 字节随机串。

### 8.16 GitHub 备份仓库被不小心设成 public 了

**立即**：
1. GitHub → 仓库 → Settings → Danger Zone → **Change visibility → Private**
2. `.enc` 文件加密的，但 `manifest.json` 和 `SHA256SUMS` 是**明文**——会暴露 db 行数、uploads 文件数、备份时间规律
3. 建议轮换一次密码 + 删除所有历史 Release + 重新备份

### 8.17 备份和恢复能同时进行吗？

**不能**。后端做了双向并发互斥：
- `BackupService.triggerBackup` 查 `backup_record` + `restore_record` 两表是否有 RUNNING
- `RestoreService.triggerRestore` 同上
- DB 唯一索引 `uk_backup_record_running` / `uk_restore_record_running` 兜底 TOCTOU 窗口

并发触发会得到错误码 `3001 BACKUP_CONFLICT`：「已有正在执行的任务 (备份或恢复),请等待完成后再试」。

## 9. 安全红线

| ❌ 不能做 | 原因 |
|---|---|
| 把 `BACKUP_ENCRYPTION_PASSWORD` / `BACKUP_GITHUB_TOKEN` commit 到 git | 泄漏后攻击者能解密所有历史备份 + 冒充身份发 release |
| GitHub 备份仓库设成 public | 加密产物本身安全，但 manifest 暴露业务规模 |
| 把密码写到日志 / 截图 / 文档 | 任何落盘文本可能被搜索引擎抓到 |
| 改完密码不重新备份 | 旧备份永久无法解密 |
| 在 admin 后台 UI 输入密码 | UI 不接 password 字段（架构硬保证，密码只走 env） |
| 把 `BACKUP_GITHUB_TOKEN` 跟发布用的 `GITHUB_TOKEN` 混用 | 一次泄漏同时影响备份和发布；Fine-grained PAT 精确授权失效 |
| 用弱密码 + iter=10 | iter=10 是基于强密码假设；弱密码会被暴力破解 |

| ✅ 应该做 | 频率 |
|---|---|
| 轮换 `BACKUP_GITHUB_TOKEN` | 90 天 |
| 验证最近一次备份能恢复 | 每季度（建议非生产 db 跑一遍恢复，对比 manifest） |
| 检查 `BACKUP_KEEP_RECORDS` 配额 | 备份频率变高时 |
| 监控 `/opt/myblog/logs/blog-warn.log` 里 `备份` / `恢复` 关键字 | 持续 |

## 10. 状态机参考

### 10.1 backup_record 状态

```
PENDING → RUNNING → SUCCESS
                 → FAILED (errorStage = DUMP / PACK / UPLOAD / SCRIPT)
                 → FAILED (errorStage = ORPHAN, JVM 在 RUNNING 中崩溃, 由 BackupStartupReconciler 兜底)
```

### 10.2 restore_record 状态

```
PENDING → RUNNING → SUCCESS (含 verifyDiff 如有)
                 → FAILED (errorStage = DOWNLOAD / VERIFY / DECRYPT / IMPORT / UPLOADS / INTERNAL)
                 → UNKNOWN (errorStage = ORPHAN, JVM 在 RUNNING 中崩溃, 由 RestoreStartupReconciler 30min 后兜底)
```
