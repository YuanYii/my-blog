## 1. 一分钟理解：这套备份解决什么问题

**痛点**：你生产服务器（Vultr ECS）的数据有两类：
1. **SQLite 数据库**（文章/评论/分类/标签/设备/IP 封禁记录）—— 整库就 1 个文件
2. **uploads 上传文件**（文章封面/评论头像/附件图片）—— 一个目录

**风险**：硬盘挂了、被恶意 rm、手贱删库、迁移机房……任何一种都会丢东西。

**解法**：admin 后台点一下「立即备份」→ 后端把 db + uploads **加密打包** → 上传到**独立 GitHub 备份仓库**的 Release → 任何时候从那个 Release 拉回来就能恢复。

**关键不变量**：
- 上传到 GitHub 的 `.enc` 文件 **是加密的**，没有密码你拿到也解密不出来
- 加密密码 **只在服务器本地** `/etc/myblog/myblog.env` 里，**不写到日志、不进 db、不返回前端**
- 备份期间后端 **正常服务**（SQLite 走 WAL online backup，uploads 走 tar 流式加密）

## 2. 前置配置（首次部署必做，一次性）

### 2.1 创建独立的 GitHub 备份仓库

**不要**用你发布代码的 `my-blog-prov` 仓库，**单独建一个** `my-blog-backup`（建议 private）：

1. GitHub 网页 → New repository
2. 名字：`my-blog-backup`（或随便起，叫 `xxx-blog-backup` 也行）
3. **Private**（必须，否则别人能下载到你的 db + uploads 加密包）
4. **不要**勾 Add README / .gitignore（空仓库就行，gh CLI 需要 default branch）

### 2.2 生成 GitHub Personal Access Token（PAT）

1. GitHub → Settings → Developer settings → Personal access tokens → Tokens (classic) → **Generate new token**
2. **Expiration**：建议 90 天或自定义（过期前重新生成）
3. **Scopes**：只勾 `repo`（完整仓库访问）
4. **不要**勾任何 admin / delete_repo 权限
5. 复制生成的 token（`ghp_xxx...`）—— **只显示一次**

### 2.3 生成备份加密密码

SSH 到服务器，跑：

```bash
openssl rand -base64 24
# 输出类似：b3JyaGVwZUNyaXN0aW5QYXJyb3QgMjAyNg==
```

**复制这个值**。

### 2.4 写入服务器环境变量文件

服务器上的 env 文件路径：`/etc/myblog/myblog.env`（`chmod 600`，只有 root 能读）。

**首次部署**：deploy-server.sh 会自动生成一个模板，你只需要：

```bash
sudo vim /etc/myblog/myblog.env
```

加 3 行（或改 3 个 `REPLACE_ME_...` 的占位）：

```bash
# === 数据备份（v4.2.0）===
BACKUP_ENCRYPTION_PASSWORD=12345678   # ← 2.3 生成的密码
GITHUB_BACKUP_REPO=YuanYii/my-blog-backup                    # ← 2.1 的仓库名
BACKUP_GITHUB_TOKEN=      # ← 2.2 的 token
```

> ⚠️ token 变量叫 `BACKUP_GITHUB_TOKEN`（**不**叫 `GITHUB_TOKEN`）。发布用的 `GITHUB_TOKEN` 走 deploy.env / CI 临时注入，**不**进这个 env。两个 token 完全隔离、可以独立轮换。

保存后：

```bash
sudo chmod 600 /etc/myblog/myblog.env
sudo systemctl restart myblog   # 重启后端让 env 生效
```

### 2.5 验证配置生效

浏览器登录 admin 后台 → 左侧菜单 **系统 → 数据备份**。

**如果配置不对**，点「立即备份」会立刻在弹窗里报具体错：
- "BACKUP_ENCRYPTION_PASSWORD 未配置" → 检查 env 第 1 行
- "BACKUP_GITHUB_TOKEN 未配置" → 检查 env 第 3 行
- "GITHUB_BACKUP_REPO 未配置,例 owner/my-blog-backup" → 检查 env 第 2 行

**如果三项都配了**，点「立即备份」→ 状态从 PENDING → RUNNING → SUCCESS 即可（耗时 30s-10min，取决于 uploads 体积）。

## 3. 日常使用：触发一次备份

### 3.1 UI 触发（推荐）

1. 登录 admin → **系统 → 数据备份**
2. 顶部点 **「立即备份」** 按钮
3. 二次确认弹窗（防误触）→ **确认**
4. 页面顶部出现 **当前任务卡片**：
   - `PENDING` → 已加入队列，等脚本启动
   - `RUNNING` → 正在打包/加密/上传，**不要刷新页面**
   - `SUCCESS` → ✅ 显示 tag（如 `backup-20260620-153012`）和资产链接
   - `FAILED` → ❌ 显示失败阶段（DUMP/PACK/UPLOAD/SCRIPT）+ 错误信息
5. 状态变更会**自动**通过 Toast 通知

**轮询机制**：前端每 2s 拉一次 `/admin/backup/{id}`，状态到终态（SUCCESS/FAILED）后自动停。

### 3.2 手动 SSH 触发（应急）

服务器本地应急备份（比如 UI 坏了、想跳过 UI 鉴权）：

```bash
# 加载 env
set -a; source /etc/myblog/myblog.env; set +a

# 跑脚本（DRY_RUN=1 不上传，只产本地 stage 目录产物）
DRY_RUN=1 sudo -E bash /opt/myblog/scripts/blog-backup.sh

# 真跑（加密 + 上传 GitHub）
sudo -E bash /opt/myblog/scripts/blog-backup.sh
```

`-E` 是 `sudo` 保留当前 shell 的 env（**必须**，否则 env 文件里那 3 个变量在 `sudo` 子进程里全没了）。

### 3.3 可选环境变量（按需）

跑 `blog-backup.sh` 时可覆盖默认值：

| 变量 | 默认 | 用途 |
|---|---|---|
| `SKIP_UPLOADS=1` | 不跳过 | 只备份 db（uploads 太大时） |
| `SKIP_DB=1` | 不跳过 | 只备份 uploads（很少用） |
| `BACKUP_STAGE_DIR=/tmp/blog-backup-stage` | 默认值 | 明文中转目录（脚本退出 trap 自动清） |
| `SQLITE_PATH=/opt/myblog/blog.db` | 默认值 | db 路径 |
| `UPLOAD_DIR=/opt/myblog/uploads` | 默认值 | 上传目录 |
| `BACKUP_KEEP_RECORDS=30` | 30 | db 保留最近 N 条 SUCCESS（超出自动删 GitHub Release + db 行） |
| `DRY_RUN=1` | 0 | 只产本地产物，不上传 GitHub |

## 4. 备份内容是什么：每次上传到 GitHub 的 4 个文件

| 文件 | 类型 | 大小 | 加密？ | 作用 |
|---|---|---|---|---|
| `blog-20260620-153012.sql.gz.enc` | 数据库加密包 | db 体积的 ~50% | ✅ AES-256-CBC | 完整 SQLite 库 |
| `uploads-20260620-153012.tar.gz.enc` | 上传文件加密包 | 压缩后 ~60% | ✅ AES-256-CBC | 全部图片/附件 |
| `manifest.json` | 元数据 | ~5 KB | ❌ 明文 | db 行数/uploads 文件数/时间/SHA256 |
| `SHA256SUMS` | 校验和 | <1 KB | ❌ 明文 | 前 3 个文件的 SHA256 |

**Release 命名**：`backup-YYYYMMDD-HHMMSS`（北京时间）。

**GitHub 上看到的样子**：
```
https://github.com/yourname/my-blog-backup/releases/tag/backup-20260620-153012
├─ blog-20260620-153012.sql.gz.enc
├─ uploads-20260620-153012.tar.gz.enc
├─ manifest.json
└─ SHA256SUMS
```

## 5. 怎么从备份恢复（灾难恢复流程）

### 5.1 场景：服务器硬盘挂了，重新买了一台

**前置**：你还有那个 GitHub 备份仓库的访问权限 + 知道 `BACKUP_ENCRYPTION_PASSWORD`。

**步骤**：

1. 在新服务器上跑标准部署：`bash deploy-server.sh v4.2.0`（先把基础设施装起来）
2. 部署完后服务跑起来了，但 db 是空的 admin/123456 占位数据
3. SSH 上去，下载最新一次 backup 的 assets：

```bash
mkdir -p /tmp/restore && cd /tmp/restore

# 用 gh CLI 下载（推荐）
GITHUB_BACKUP_REPO=yourname/my-blog-backup
gh release download backup-20260620-153012 --repo $GITHUB_BACKUP_REPO --dir .

# 或用 curl 兜底
# curl -L -o blog-20260620-153012.sql.gz.enc \
#   https://github.com/yourname/my-blog-backup/releases/download/backup-20260620-153012/blog-20260620-153012.sql.gz.enc
# ... 重复 3 次
```

4. **校验**（防下载中途损坏）：

```bash
sha256sum -c SHA256SUMS
# 期望：blog-XXX...enc: OK / uploads-XXX...enc: OK / manifest.json: OK
```

5. **先停服务再覆盖 db**（避免锁竞争）：

```bash
sudo systemctl stop myblog
```

6. **解密 + 导入 db**（复用 `sqlite-import.sh`）：

```bash
set -a; source /etc/myblog/myblog.env; set +a   # 把密码 load 进来

# 备份原 db（防万一）
sudo cp /opt/myblog/blog.db /opt/myblog/db/backups/blog-pre-restore-$(date +%Y%m%d-%H%M%S).db

# 解密 + 导入
sudo bash /opt/myblog/scripts/sqlite-import.sh /opt/myblog/blog.db /tmp/restore/blog-20260620-153012.sql.gz.enc
```

7. **解密 uploads**（手动解）：

```bash
sudo mkdir -p /opt/myblog/uploads
sudo openssl enc -d -aes-256-cbc -pbkdf2 -iter 100000 \
    -pass env:BACKUP_ENCRYPTION_PASSWORD \
    -in /tmp/restore/uploads-20260620-153012.tar.gz.enc | sudo tar xzf - -C /opt/myblog/

# 修权限（解出来可能是 root 拥有）
sudo chown -R myblog:myblog /opt/myblog/uploads
```

8. **重启服务**：

```bash
sudo systemctl start myblog
```

9. **验证**：
- 浏览器打开 `https://yourname.com` → 文章/图片都在 → 登录 admin → 看仪表盘统计数对得上
- `sqlite3 /opt/myblog/blog.db "SELECT COUNT(*) FROM article;"` 跟恢复前的 manifest.json 里 `table_stats_exact.article` 一致

### 5.2 场景：只丢了 uploads（图片 404）

跳过第 6 步（不动 db），只跑第 7 步解密 uploads。

### 5.3 场景：只想看 db 内容，不想覆盖

```bash
# 解密到临时 db
bash sqlite-import.sh /tmp/inspect.db /tmp/restore/blog-XXX.sql.gz.enc
sqlite3 /tmp/inspect.db "SELECT id,title FROM article LIMIT 10;"
# 不影响 /opt/myblog/blog.db
```

## 6. 常见问题

### 6.1 备份失败，errorStage = UPLOAD，错误是 "gh release create failed: 401"

**原因**：`BACKUP_GITHUB_TOKEN` 失效（过期或被 revoke）。

**修法**：
1. GitHub → Settings → Developer settings → Personal access tokens → 重新生成 token（**Fine-grained PAT，限定到 my-blog-backup 仓库**）
2. 替换 `/etc/myblog/myblog.env` 的 `BACKUP_GITHUB_TOKEN=...`
3. `sudo systemctl restart myblog`
4. 在 admin 后台重试「立即备份」

### 6.2 备份失败，errorStage = UPLOAD，错误是 "404 Not Found"

**原因**：`GITHUB_BACKUP_REPO` 填错（仓库不存在 / 拼错 / 是别人的）。

**修法**：
1. 浏览器打开 `https://github.com/yourname/my-blog-backup` 确认能访问
2. 修正 `/etc/myblog/myblog.env` 的 `GITHUB_BACKUP_REPO=你的用户名/你的仓库名`
3. 重启 + 重试

### 6.3 备份失败，errorStage = UPLOAD，错误是 "asset > 2GB"

**原因**：uploads 总和超过 2GB，GitHub Release 单 asset 上限 2GB。

**修法**（3 选 1）：
- `SKIP_UPLOADS=1` 只备份 db（**最快**）
- 加 `DB_EXCLUDE_TABLES=uploads_log` 之类的——**没有意义**，这表不存在
- 用 `BACKUP_KEEP_RECORDS=10` 清理历史 Release 腾空间

**根本解法**：uploads 太大考虑接对象存储（OSS/S3），不在本手册范围。

### 6.4 备份失败，errorStage = DUMP，错误是 "sqlite-export.sh 失败"

**原因**：db 文件可能损坏、磁盘满、或 sqlite3 CLI 不一致。

**排查**：
```bash
# 1. db 健康检查
sqlite3 /opt/myblog/blog.db "PRAGMA integrity_check;"
# 期望：ok

# 2. 磁盘空间
df -h /opt/myblog/

# 3. 手动跑一次看完整日志
sudo -E bash /opt/myblog/scripts/blog-backup.sh 2>&1 | tee /tmp/backup-debug.log
```

### 6.5 备份过程中 SSH 断了

**没关系**。脚本在后台异步跑，不依赖 SSH 连接。SSH 重连上去：

```bash
# 看进度
sqlite3 /opt/myblog/blog.db "SELECT id,status,started_at,error_stage,error_message FROM backup_record ORDER BY id DESC LIMIT 3;"

# 看脚本日志（Java 侧 process 写到 java.io.tmpdir）
ls -lt /tmp/blog-backup-*.log | head -3
tail -50 /tmp/blog-backup-XX.log
```

### 6.6 多久备份一次？要不要 cron？

**当前 v4.2.0 不内置 cron**。建议手动节奏：
- **活跃期**（你天天发文/改站）→ 一周一次
- **稳定期** → 一个月一次
- **改重要数据前**（大量删评论/批量改配置）→ 手动触发一次

后续 v4.3.0+ 计划加 systemd timer 自动每天凌晨 3 点跑 + 自动删 30 天前的旧 Release（`BACKUP_KEEP_RECORDS=30` 现在是手动管理）。

### 6.7 怎么删除旧备份？

**三条路**（2026-06-21 v4.2.1 polish 增加 UI 入口）：
- **UI 删除（推荐）**：admin 后台 → 系统 → 数据备份 → 列表行末"删除"按钮
  - **SUCCESS 记录**：点删除 → 弹窗要求输入 `DELETE` 字样 → 同时删除 GitHub Release tag 和 db 行（GitHub 删除失败仅 WARN，仍删 db 行）
  - **FAILED 记录**：点删除 → 普通二次确认 → 仅删 db 行（GitHub 上没建 release）
  - **PENDING / RUNNING 记录**：按钮禁用，无法删（备份在进行中）
- **自动**：`BACKUP_KEEP_RECORDS=30` 每次新备份成功后，trimOldRecords 保留最近 30 条 SUCCESS，超出自动删 GitHub Release + db 行
- **手动兜底**：到 GitHub 备份仓库网页 → Releases → 找到旧 tag → Delete（只删 GitHub，db 留痕）

### 6.8 加密密码忘了怎么办？

**结论**：**所有备份永久失效**。

AES-256-CBC + PBKDF2 100k 是工业级加密，暴力破解不现实（密码不弱的话）。所以**密码管理很关键**：
- 推荐用 1Password / Bitwarden 存
- 至少在两个不同地方存（比如 1Password + 写在纸上锁抽屉）
- 改密码后**所有旧备份也失效**（PBKDF2 每次加密自带随机 salt），需要用新密码重新备份

### 6.9 GitHub 备份仓库被不小心设成 public 了

**立即**：
1. GitHub 网页 → 仓库 → Settings → Danger Zone → **Change visibility → Private**
2. 虽然 `.enc` 文件是加密的，但 `manifest.json` 和 `SHA256SUMS` 是**明文**，里面会暴露你的 db 行数、uploads 文件数、备份时间规律——**建议轮换一次密码** + 删除历史 Release

## 7. 安全红线

| 不能做 | 原因 |
|---|---|
| ❌ 把 `BACKUP_ENCRYPTION_PASSWORD` / `BACKUP_GITHUB_TOKEN` commit 到 git | 一旦泄漏，攻击者能解密你**所有**历史备份 + 冒充你发 release |
| ❌ 把 GitHub 备份仓库设成 public | 虽然加密，但 manifest 暴露业务规模 |
| ❌ 把 `BACKUP_ENCRYPTION_PASSWORD` 写到日志 / 截图 / 文档 | 任何落盘文本都可能被搜索引擎抓到 |
| ❌ 改完密码不重新备份 | 旧备份全部用旧密码加密，密码忘了一样解不开 |
| ❌ 在 admin 后台 UI 输入密码 | UI 永远不接 password 字段（架构硬保证） |
| ❌ 把 `BACKUP_GITHUB_TOKEN` 跟发布用的 `GITHUB_TOKEN` 混用 | 一次泄漏同时影响备份和发布；Fine-grained PAT 精确授权失效 |

| 应该做 | 频率 |
|---|---|
| ✅ 定期轮换 `BACKUP_GITHUB_TOKEN` | 90 天 |
| ✅ 验证最近一次备份可以恢复 | 每季度（找个测试 db 跑一遍 §5.3） |
| ✅ 检查 `BACKUP_KEEP_RECORDS` 配额是否要调 | 备份频率变高时 |
| ✅ 监控 `/opt/myblog/logs/blog-warn.log` 里的 `备份` 关键字 | 持续 |
