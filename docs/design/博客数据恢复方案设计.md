## 1. 目标与约束

**目标**：复用现有 admin "数据备份" 页面（`frontend/pages/admin/backup.vue`），新增 "数据恢复" 能力 —— 用户在本地备份记录列表里**单选**一条 → 点击「数据恢复」按钮 → 后端从该条记录对应的 GitHub Release 拉回加密 dump → 解密 → 覆盖本地 db（可选恢复 uploads）→ 启动后端验证。

**不新增独立恢复页面**（用户原话：单页承担备份 + 恢复两个职能）。

**约束**：

1. **加密链路复用**：复用 v4.0.0 加密数据迁移的 AES-256-CBC + PBKDF2 100k 链路（`sqlite-import.sh`），不引入新加密算法
2. **GitHub Release 数据源**：复用 `blog-backup.sh` 推送到 `GITHUB_BACKUP_REPO` 的 Release 资产
3. **必须停服**：恢复是覆盖式（删原 db 全量重建），恢复期间 Spring Boot 必须停
4. **必须先备当前 db**：恢复前自动 `cp blog.db blog.db.bak.YYYYMMDD-HHMMSS`，失败可手动回退
5. **恢复范围可勾选**：默认 `DB_ONLY`，可选 `DB_UPLOADS`（前端 Dialog 勾选框）
6. **密码不进前端**：从服务器 `/etc/myblog/myblog.env` 的 `BACKUP_ENCRYPTION_PASSWORD` 读，前端只传 tag + scope
7. **并发控制（双向）**：恢复期间拒绝触发新备份；备份期间拒绝触发新恢复（共享一个"任务占用"互斥锁，跨两个表查）
8. **不引入新后台任务框架**：复用 `BackupService` 已有的 `@Async + ProcessBuilder` 模式
9. **admin 鉴权 + 操作日志**：按 AGENTS.md §4.8 P0 安全类，恢复成功/失败/无权限都打 INFO/WARN，禁打密码/secret
10. **进程模型必须能扛住"自我重启"**（详见 §6.1）：脚本脱离 cgroup + 磁盘状态兜底 + 新 JVM 启动时回填
> 关联 changelog: 待新建 `docs/changelogs/2026-06-20-vX.Y.Z-restore-feature.md`

## 2. 数据来源与流程

### 2.1 数据源：现有 `backup_record` 表

```
backup_record (本地记录)
├─ id, status, tag, asset_urls, ...
└─ tag = GitHub Release tag (如 backup-20260620-153022)
        └─ 通过 tag → gh release download → 拉到 dump + manifest + SHA256SUMS
```

**为什么不直接查 GitHub Releases API 列远程 release？**

- 本地 `backup_record` 已有现成的"该备份存在哪些 asset、是谁触发的、当时耗时多少"等元信息
- 一次页面加载里同时拉 GitHub API 容易触发限流（60/h 匿名、5000/h 认证），且当前 ECS 出 ECS 拉 GitHub 偶尔有 1-3s 延迟
- 用户已经看本地列表，能直接选 → 直接恢复，无需切换"本地/远程"两套数据源

### 2.2 完整流程

```
┌──────────────────────────────────────────────────────────────────┐
│ 1. 用户在 backup.vue 单选一条 SUCCESS 的 backup_record           │
│ 2. 点 [数据恢复] 按钮（未选中时 disabled）                       │
│ 3. 弹 Dialog：勾选范围 [DB_ONLY] / [DB_UPLOADS]，确认            │
│ 4. POST /api/v1/admin/restore/run { recordId, scope }           │
│ 5. 后端建 restore_record (PENDING) + systemd-run --scope 启脚本 │
│ 6. JVM 立刻 return（不 waitFor），前端启动退避轮询 2s→4s→...→30s│
│ 7. 脚本完成 → 写 .result.json；下次 JVM 启动 + 每 5min 巡检回填 │
│ 8. 前端轮询拉到 SUCCESS/FAILED/UNKNOWN → 弹对应 Toast           │
└──────────────────────────────────────────────────────────────────┘
```

## 3. 架构（v3 核心：systemd-run --scope + 磁盘状态兜底 + 定时巡检）

### 3.1 进程模型（v0.1/v2 死结 → v3 解法）

```
[ v0.1 死结 ] — 备份脚本 waitFor 同步等
JVM → ProcessBuilder → blog-restore.sh
       └─ 脚本第 2 步: systemctl stop myblog ← 杀掉整个 cgroup, 包括脚本自己
                            ├─ Restart=always: 5s 后新 JVM 起来
                            ├─ 原 @Async 线程已死, waitFor 没人收尸
                            └─ .result.json 成孤儿, restore_record 永远 RUNNING

[ v2 假解 ] — setsid 替换 waitFor, 但 setsid 不脱 cgroup
JVM → ProcessBuilder → setsid bash -c "... &"  blog-restore.sh
       └─ setsid 只改 session/process-group, 不迁移 cgroup
              └─ 脚本还是在 myblog.service cgroup 里
                     └─ systemctl stop myblog 照样杀整个 cgroup ← 死结原封不动

[ v3 真解 ] — systemd-run --scope 进独立 cgroup
JVM (myblog.service cgroup)
  └─ sudo systemd-run --scope --slice=myblog-restore --unit=blog-restore-<id> bash script
                          │
                          ▼
                  新 cgroup: myblog-restore.slice/blog-restore-<id>.scope
                  (跟 myblog.service 不在同一 cgroup)
                          │
                          └─ blog-restore.sh 在独立 cgroup 里跑:
                                ├─ sudo systemctl stop myblog  ← 只杀 myblog.service cgroup, 杀不到这里
                                ├─ 恢复 db + uploads
                                ├─ sudo chown -R myblog:myblog
                                ├─ sudo systemctl start myblog ← 新 JVM 起来
                                ├─ 健康检查 + 数据校验
                                └─ 写 .result.json 到固定路径
                                                              │
新 JVM 启动时 ─── ApplicationReadyEvent ───────────────────┐ │
                                                              ▼ │
                  + @Scheduled(5min) 定时巡检 ──► 扫 restore_record   │
                                                       ├─ RUNNING + 有 .result.json → 按它标 SUCCESS/FAILED
                                                       ├─ RUNNING + 没 .result.json + 超 30min → 标 UNKNOWN (孤儿)
                                                       └─ RUNNING + 没 .result.json + 时间不到 → 还在跑, 跳过
```

**v3 关键不变量**：

1. **脚本必须进独立 cgroup**：`sudo systemd-run --scope --slice=myblog-restore --unit=blog-restore-<id>`（不是 setsid）
2. **JVM 即发即忘**：`pb.start()` 后**不 waitFor**，立刻返回 record id
3. **结果走磁盘**：脚本写到 `$RESTORE_RESULT_DIR/.blog-restore-result.$recordId.json`（**固定路径，不进 stage**）
4. **状态回填双轨**：JVM 启动时 + 每 5 分钟定时扫表，**不只靠启动事件**（新-4 修复）
5. **回填逻辑必须无条件扫**：先看磁盘 result.json，再看时间阈值（不能反过来，新-2 修复）

### 3.2 为什么 systemd-run --scope 能成而 setsid 不行

| 维度 | setsid | systemd-run --scope |
|---|---|---|
| 改 session | ✅ | ✅（自动） |
| 改 process-group | ✅ | ✅（自动） |
| 改 cgroup | ❌ | ✅（创建独立 scope cgroup） |
| 能否逃过 `systemctl stop myblog` | ❌（仍在同一 cgroup） | ✅（独立 cgroup，杀不到） |
| 适用场景 | 跟终端脱钩就行（如 cron） | 需要扛住 systemd KillMode=control-group |
| v3 选择 | ❌（致命漏洞） | ✅ |

**权威依据**（systemd 文档）：

> `KillMode=control-group`（默认值）表示**杀死该单元的 cgroup 内的所有进程**。
> `systemd-run --scope` 会创建一个临时 scope 单位，**进程直接映射到独立的 cgroup 路径**。

→ **只有 systemd-run --scope（或修改 unit 的 KillMode=process）能让脚本逃出 cgroup 杀伤范围**。前者不动 unit，符合"不动 deploy-server.sh"的约束，是 v3 的唯一选择。

## 4. 数据库：新增 `restore_record` 表

**不复用 `backup_record` 表**（语义不同：备份是"长期审计"，恢复是"瞬时任务"；混表后"恢复成功"会被误读为"备份成功"）。

```sql
CREATE TABLE restore_record (
  id                INTEGER PRIMARY KEY AUTOINCREMENT,
  status            VARCHAR(16)  NOT NULL,              -- PENDING / RUNNING / SUCCESS / FAILED / UNKNOWN
  source_record_id  BIGINT,                            -- 关联 backup_record.id
  source_tag        VARCHAR(64),                       -- 备份的 GitHub Release tag
  scope             VARCHAR(16)  NOT NULL,              -- DB_ONLY / DB_UPLOADS
  started_at        DATETIME     NOT NULL,
  finished_at       DATETIME,
  error_stage       VARCHAR(32),                       -- DOWNLOAD / SHA256 / DECRYPT / IMPORT / START / HEALTH / VERIFY
  error_message     TEXT,                              -- 截断到 500 字符
  verify_diff       TEXT,                              -- v2 新增: 数据校验差异 (manifest vs 实际)
  operator_id       BIGINT,
  operator_name     VARCHAR(64)
);
CREATE INDEX idx_restore_started ON restore_record(started_at DESC);
```

**`status` 多了 `UNKNOWN`** —— 给"启动时回填发现孤儿但磁盘上没 result.json"的情况用。v0.1 没有这个状态，会让死掉的 RUNNING 永远卡住。

DDL 写入 `docs/sql/schema-sqlite.sql`（v2.6.0 整合后单一 schema 文件）。

```java
@Async
public void runRestoreAsync(Long recordId) {
    // 1. PENDING → RUNNING
    // 2. ProcessBuilder("sudo", "-n", "systemd-run",
    //      "--scope", "--slice=myblog-restore", "--unit=blog-restore-" + recordId,
    //      "--uid=myblog", "--gid=myblog",
```

**v4 vs v2 关键变化**：

| 维度 | v2 (setsid) | v4 (systemd-run --scope) |
|---|---|---|
| `pb.start()` 命令 | `setsid bash -c "exec bash ... &"` | `sudo systemd-run --scope --slice=myblog-restore --uid=myblog --gid=myblog /bin/bash <script>` |
| 进独立 cgroup | ❌ setsid 不脱 cgroup | ✅ systemd-run --scope 创建独立 scope cgroup |

| `pb.start()` 后 | 立刻 return | 立刻 return（不变） |
| 状态回填 | v2 只有 ApplicationReadyEvent | §5.4 双轨回填（含 @Scheduled 定时巡检） |

### 5.4 `RestoreStartupReconciler`（v3 核心：双轨回填）

```java
@Component
public class RestoreStartupReconciler {

    private final RestoreRecordMapper mapper;
    private final ObjectMapper json;

    /** 结果文件目录（= /var/lib/myblog/restore-results，固定路径，不进 stage） */
    @Value("${blog.restore.result.dir:/var/lib/myblog/restore-results}")
    private String resultDir;

    /** orphan 阈值（默认 30 分钟：正常恢复 1-5 分钟，30min 兜底慢 IO / 慢网络） */
    @Value("${blog.restore.orphan.threshold.min:30}")
    private int orphanThresholdMin;

    // ===== 入口 1：JVM 启动时跑一次 =====
    @EventListener(ApplicationReadyEvent.class)
    public void reconcileOnStartup() {
        log.info("[RestoreReconciler] JVM 启动, 开始回填 RUNNING 记录");
        reconcile();
    }

    // ===== 入口 2：每 5 分钟定时巡检（兜住"脚本启动即失败服务没重启"的窗口）=====
    // v3 新增（修复严重新-4）
    @Scheduled(fixedDelay = 5 * 60 * 1000, initialDelay = 5 * 60 * 1000)
    public void reconcileOnSchedule() {
        reconcile();
    }

    private void reconcile() {
        // v3 关键：无条件扫所有 RUNNING（不带时间阈值）
        // 修复致命新-2 — 旧版"started_at > 30min 才捞"会让正常完成的 RUNNING 永远捞不到
        List<RestoreRecord> running = mapper.findAllRunning();
        if (running.isEmpty()) return;

        LocalDateTime now = LocalDateTime.now();
        for (RestoreRecord r : running) {
            Path resultPath = Paths.get(resultDir,
                ".blog-restore-result." + r.getId() + ".json");

            if (Files.exists(resultPath)) {
                // 情况 1：有 result.json → 按它标 SUCCESS/FAILED
                try {
                    ResultJson result = json.readValue(resultPath.toFile(), ResultJson.class);
                    applyResult(r, result);
                    Files.deleteIfExists(resultPath);  // 一次性, 读完即删
                    log.info("[RestoreReconciler] 回填 record {} → {} (从 result.json)",
                        r.getId(), result.getStatus());
                } catch (Exception e) {
                    log.warn("[RestoreReconciler] 读 result.json 失败: record={} err={}",
                        r.getId(), e.getMessage());
                    // 解析失败 → 不动, 下次再试 (避免 result 文件被误删后丢信息)
                }
            } else if (r.getStartedAt().isBefore(now.minusMinutes(orphanThresholdMin))) {
                // 情况 2：没 result + 超 30 分钟 → 孤儿, 标 UNKNOWN
                r.setStatus("UNKNOWN");
                r.setErrorStage("ORPHAN");
                r.setErrorMessage("脚本未在 " + orphanThresholdMin + " 分钟内产出 .result.json, 判定为孤儿");
                r.setFinishedAt(now);
                mapper.updateById(r);
                log.warn("[RestoreReconciler] 孤儿 record {} → UNKNOWN (started={})",
                    r.getId(), r.getStartedAt());
            } else {
                // 情况 3：没 result + 时间不到 30 分钟 → 还在跑, 跳过
                log.debug("[RestoreReconciler] record {} 还在跑, 跳过 (started={})",
                    r.getId(), r.getStartedAt());
            }
        }
    }
}
```

**v3 关键变化 vs v2**：

| 维度 | v2 | v3 |
|---|---|---|
| 触发时机 | 只在 JVM 启动时（一次性） | JVM 启动时 + 每 5 分钟定时 |
| 扫描条件 | `started_at < now - 30min`（致命漏洞） | 无条件扫所有 RUNNING |
| 孤儿判定 | 捞不到 = 不处理（永远卡） | 没 result + 超 30min → UNKNOWN |
| 修复了 | — | 致命新-2 + 严重新-4 |

**需要开启 `@EnableScheduling`**：在 Application 类加 `@EnableScheduling`（或某个 @Configuration 上加）。Spring Boot 默认不开启定时任务。

**结果文件路径必须固定**：用 `RESTORE_RESULT_DIR=/var/lib/myblog/restore-results`，**永不被 trap 清**（trap 只清 `RESTORE_STAGE_DIR`）。

## 6. 脚本设计：`blog-restore.sh`

### 6.1 进程脱离（v3 第 1 步必修：systemd-run --scope）

**Java 侧**（在 RestoreService.runRestoreAsync 里）：

```java
// v4 关键: 必须加 --uid=myblog --gid=myblog
// systemd-run 是 root 跑的工具 (sudo 提权), scope 内命令默认以 root 身份跑
// 如果不加 --uid, sqlite-import.sh 写出的 db / tar 解出的 uploads 全是 root 属主,
// 靠 step 11 chown 兜底 (顺序勉强对但有遗漏风险, 比如 WAL 临时文件)
// 加 --uid=myblog 后脚本内本进程即 myblog, §6.5 step 9/10 "不需要 sudo" 注释才成立

ProcessBuilder pb = new ProcessBuilder(
    "sudo", "-n", "systemd-run",
    "--scope",                                          // 创建临时 scope 单元
    "--slice=myblog-restore",                           // 独立 slice, 跟 myblog.service 平级
    "--unit=blog-restore-" + recordId,                  // 单元名 (systemd-cgls 可见)
    "--uid=myblog", "--gid=myblog",                     // v4 必加: scope 内进程以 myblog 身份跑
    "/bin/bash", blogRestoreScriptPath                  // v4 精确路径, 跟 sudoers 对齐
);
pb.environment().putAll(envVars);
Process p = pb.start();
return; // 不 waitFor, 不读 stdout, 立刻 return
```

**v4 sudoers 第 5 条**（详细见 §12.1）：

```
myblog ALL=(root) NOPASSWD: /usr/bin/systemd-run --scope --slice=myblog-restore --unit=blog-restore-* --uid=myblog --gid=myblog /bin/bash /opt/myblog/scripts/blog-restore.sh
```

末尾精确到 `/bin/bash /opt/myblog/scripts/blog-restore.sh`，**不留任何通配符**（v3 末尾的 `*` 是提权后门，已删除）。

**为什么必须 `sudo systemd-run`**：

- `systemd-run` 是给 root 用的工具（创建 systemd 单元需要特权）
- myblog 用户跑不了 → 必须 sudo
- `--scope` 是关键（不是 `--unit` 起 service，scope 是临时同步的，符合"脚本跑完就回收"的语义）
- 脚本跑完后，scope cgroup 自动随进程退出被 systemd 清理

**v4 vs v3 关键变化**（致命新-2）：

| 维度 | v3 | v4 |
|---|---|---|
| ProcessBuilder 命令 | `sudo systemd-run ... bash script` | 加 `--uid=myblog --gid=myblog` |
| scope 内进程身份 | root（默认） | myblog（强制） |
| step 9/10 注释前提 | "本进程即 myblog" 是**错的** | "本进程即 myblog" 才成立 |
| step 11 chown 必要性 | 必须做（root 写的 db） | 仍必须做（恢复前的旧 db 可能是其他属主）|

### 6.2 必读环境变量（全部由 Java ProcessBuilder 透传）

|---|---|---|
| `BACKUP_ENCRYPTION_PASSWORD` | `/etc/myblog/myblog.env` | 加密密码（8+ 位） |

| `RESTORE_RESULT_DIR` | `@Value` 默认 `/var/lib/myblog/restore-results` | .result.json 落点（**永不被 trap 清**） |

### 6.3 退出码（与 backup 对齐语义）

| 退出码 | 含义 | Java 侧 errorStage 映射 |
|---|---|---|
| 0 | 成功 | — |
| 20 | 预检失败（env 缺失 / 文件不存在 / sudoers 没配） | `PRECHECK` |
| 21 | `gh release download` 失败 | `DOWNLOAD` |
| 22 | SHA256SUMS 校验失败 | `SHA256` |
| 23 | 解密失败（openssl 报错） | `DECRYPT` |
| 24 | `sqlite-import.sh` 导入失败 | `IMPORT` |
| 25 | `systemctl start` 失败 / 启服超时 | `START` |
| 26 | 健康检查 `curl /api/v1/health` 失败 | `HEALTH` |
| 27 | uploads 解压失败（scope=DB_UPLOADS 时） | `UPLOADS` |
| 28 | 数据完整性校验失败（manifest 行数 vs 实际行数差异超阈值） | `VERIFY` |

### 6.4 关键不变量

1. **明文不落 stage 之外**：解密后的 .sql / .tar 临时文件全部在 `RESTORE_STAGE_DIR` 内，trap 退出时 shred
2. **.result.json 写到 stage 外**：`RESTORE_RESULT_DIR=/var/lib/myblog/restore-results`（独立目录，不进 stage 不被 trap 删）
3. **失败信息只保留最后 500 字符**：避免 db 撑爆
4. **环境变量走 env 不进命令行**：ProcessBuilder 注入（密码/token 不进 `ps`）
5. **sudoers 严格白名单**（§12.1）：`myblog` 用户只能 `sudo -n` 几条精确命令
6. **.bak 保留最近 N 份**（v2 新增）：避免多次恢复撑爆磁盘

### 6.5 脚本伪代码（v3）

```bash
set -euo pipefail

# ---------- 0. 默认值（脚本可独立调试时用, Java 透传时会被覆盖）----------
RESTORE_HEALTH_URL="${RESTORE_HEALTH_URL:-http://localhost:8080/api/v1/health}"
RESTORE_KEEP_BAKS="${RESTORE_KEEP_BAKS:-5}"
RESTORE_RESULT_DIR="${RESTORE_RESULT_DIR:-/var/lib/myblog/restore-results}"

# ---------- 1. 预检 ----------
[[ -n "$BACKUP_ENCRYPTION_PASSWORD" ]] || { err "BACKUP_ENCRYPTION_PASSWORD 未配置"; exit 20; }
[[ -n "$BACKUP_GITHUB_TOKEN" ]] || { err "BACKUP_GITHUB_TOKEN 未配置"; exit 20; }
[[ -n "$GITHUB_BACKUP_REPO" ]] || { err "GITHUB_BACKUP_REPO 未配置"; exit 20; }
[[ -n "$RESTORE_SOURCE_TAG" ]] || { err "RESTORE_SOURCE_TAG 未配置"; exit 20; }
[[ -f "$SQLITE_PATH" ]] || { err "SQLITE_PATH 不存在: $SQLITE_PATH"; exit 20; }
# v5 改: 验证 sudoers 已配 (用白名单内的 systemctl is-active 命令, 不再试 systemd-run)
# 历史: v3 写成 `sudo -n systemd-run ... --unit=test-$$ /bin/true` 做自检,
#   但 v4 把 sudoers 第 5 条收窄成 `--unit=blog-restore-* --uid=myblog --gid=myblog /bin/bash <script>`
#   test-$$ 不以 blog-restore- 开头 + 没有 --uid/--gid + /bin/true 不是 blog-restore.sh
#   → 自检必被拒 → exit 20 → 恢复根本起不来
# v5 自检用 `sudo -n systemctl is-active myblog`:
#   1) 在白名单内 (systemctl is-active 是第 3 条)
#   2) 退出码区分: sudo 拒绝 → exit 1 (NOPASSWD 失败);
#                    服务 inactive → exit 3 (systemd 标准退出码);
#                    服务 active → exit 0
#   3) 服务停着也正常, 不阻断 (inactive 也算 sudoers 配通)
sudo -n systemctl is-active myblog >/dev/null 2>&1
SUDO_RC=$?
# sudo 被拒 (exit 1) → 预检失败
# sudo 通过但服务 inactive (exit 3) → OK, 正常情况
# sudo 通过且服务 active (exit 0) → 也 OK
if [[ $SUDO_RC -eq 1 ]]; then
    err "sudoers 未配置 systemctl, 见设计文档 §12.1"
    exit 20
fi
info "sudoers 验证通过 (is-active exit=$SUDO_RC, 0=active / 3=inactive / 1=rejected)"

# ---------- 2. 清理旧 .bak (保留最近 N 份) ----------
if compgen -G "${SQLITE_PATH}.bak.*" > /dev/null; then
    ls -1t "${SQLITE_PATH}.bak."* | tail -n +$((RESTORE_KEEP_BAKS + 1)) | xargs -r rm -f
    info "保留最近 $RESTORE_KEEP_BAKS 份 .bak, 已清理旧的"
fi

# ---------- 3. 备份当前 db (恢复前快照) ----------
if [[ -f "$SQLITE_PATH" ]]; then
    cp "$SQLITE_PATH" "${SQLITE_PATH}.bak.$(date +%Y%m%d-%H%M%S)"
    info "当前 db 已备份为 .bak"
fi

# ---------- 4. 准备 stage 目录 + result 目录 + trap ----------
mkdir -p "$RESTORE_STAGE_DIR" "$RESTORE_RESULT_DIR"
chmod 700 "$RESTORE_RESULT_DIR"

# 写 result 函数 (trap 和正常退出共用)
write_result() {
    local status="$1"
    local stage="$2"
    local message="$3"
    cat > "$RESULT_FILE" <<EOF
{
  "status": "$status",
  "stage": "$stage",
  "message": "${message:0:500}",
  "tag": "$RESTORE_SOURCE_TAG",
  "scope": "$RESTORE_SCOPE",
  "finished_at": "$(date -Iseconds)"
}
EOF
    chmod 600 "$RESULT_FILE"
}

RESULT_FILE="$RESTORE_RESULT_DIR/.blog-restore-result.$RESTORE_RECORD_ID.json"

# v3 trap 补 write_result (修复中-1)
cleanup_on_exit() {
    local rc=$?
    # 关键: 还没写过 result 的话补一个 FAILED, 让 onAppReady / 定时巡检能正确回填
    if [[ ! -f "$RESULT_FILE" ]]; then
        write_result FAILED "TRAP" "脚本异常退出 (exit code $rc)"
    fi
    # 清 stage 明文
    if [[ -d "$RESTORE_STAGE_DIR" ]]; then
        find "$RESTORE_STAGE_DIR" -type f 2>/dev/null | while read -r f; do
            command -v shred >/dev/null 2>&1 && shred -u -z "$f" 2>/dev/null || rm -f "$f"
        done
        rm -rf "$RESTORE_STAGE_DIR"
    fi
    exit $rc
}
trap cleanup_on_exit EXIT
trap 'cleanup_on_exit 1' INT TERM

# ---------- 5. 停服 (脚本在 myblog-restore.slice 独立 cgroup, myblog.service cgroup 杀不到) ----------
log_step "STOP"
if sudo -n systemctl is-active --quiet myblog 2>/dev/null; then
    sudo -n systemctl stop myblog \
        || { err "systemctl stop myblog 失败"; write_result FAILED STOP "..."; exit 25; }
    info "myblog 已停止"
else
    info "myblog 已是 inactive 状态, 跳过 stop"
fi

# ---------- 6. 拉 release assets (gh 优先, curl fallback) ----------
log_step "DOWNLOAD"
mkdir -p "$RESTORE_STAGE_DIR"
cd "$RESTORE_STAGE_DIR"

if command -v gh >/dev/null 2>&1; then
    USE_GH=1
else
    USE_GH=0
    info "gh CLI 未安装, fallback 到 curl"
fi

if [[ "$USE_GH" == "1" ]]; then
    GH_TOKEN="$BACKUP_GITHUB_TOKEN" gh release download "$RESTORE_SOURCE_TAG" \
        --repo "$GITHUB_BACKUP_REPO" \
        --dir "$RESTORE_STAGE_DIR" \
        --pattern "*.enc" --pattern "manifest.json" --pattern "SHA256SUMS" \
        || { err "gh release download 失败"; write_result FAILED DOWNLOAD "..."; exit 21; }
else
    # curl + REST API 拉每个 asset (跟 backup 脚本同样的兜底模式, 见 blog-backup.sh line 469-503)
    RELEASE_JSON=$(curl -fsS \
        -H "Authorization: token $BACKUP_GITHUB_TOKEN" \
        "https://api.github.com/repos/$GITHUB_BACKUP_REPO/releases/tags/$RESTORE_SOURCE_TAG")
    [[ -n "$RELEASE_JSON" ]] || { err "curl 拉 release 元信息失败"; write_result FAILED DOWNLOAD "..."; exit 21; }
    # 解析 asset 列表 (用 jq)
    echo "$RELEASE_JSON" | jq -r '.assets[] | select(.name | endswith(".enc") or . == "manifest.json" or . == "SHA256SUMS") | .name + " " + .browser_download_url' \
        | while read -r name url; do
            curl -fsSL -H "Authorization: token $BACKUP_GITHUB_TOKEN" "$url" -o "$name" \
                || { err "curl 下载 $name 失败"; write_result FAILED DOWNLOAD "..."; exit 21; }
        done
fi

# ---------- 7. SHA256 校验 ----------
log_step "SHA256"
sha256sum -c SHA256SUMS || { err "SHA256SUMS 校验失败"; write_result FAILED SHA256 "..."; exit 22; }

# ---------- 8. 读 manifest 拿 db 文件名 + 数据校验基线 ----------
log_step "MANIFEST"
DB_FILE=$(jq -r '.db.encrypted_file' manifest.json)
EXPECTED_TABLE_COUNTS=$(jq -r '.db.table_stats_exact // {}' manifest.json)

# ---------- 9. 调 sqlite-import.sh (本进程即 myblog, 直接调不需要 sudo) ----------
log_step "IMPORT"
FORCE_IMPORT=1 \
DB_DECRYPT_PASSWORD="$BACKUP_ENCRYPTION_PASSWORD" \
    bash /opt/myblog/scripts/sqlite-import.sh "$SQLITE_PATH" "$RESTORE_STAGE_DIR/$DB_FILE" \
    || { err "sqlite-import.sh 失败"; write_result FAILED IMPORT "..."; exit 24; }

# ---------- 10. (可选) 恢复 uploads (本进程即 myblog, 直接调) ----------
if [[ "$RESTORE_SCOPE" == "DB_UPLOADS" ]]; then
    log_step "UPLOADS"
    UPLOADS_FILE=$(jq -r '.uploads.encrypted_file' manifest.json)
    openssl enc -d -aes-256-cbc -pbkdf2 -iter 100000 \
        -pass env:BACKUP_ENCRYPTION_PASSWORD \
        -in "$RESTORE_STAGE_DIR/$UPLOADS_FILE" \
        | tar xzf - -C "$INSTALL_DIR" \
        || { err "uploads 解压失败"; write_result FAILED UPLOADS "..."; exit 27; }
fi

# ---------- 11. 改权限 (sudo chown, 需要 root) ----------
sudo -n chown -R myblog:myblog "$SQLITE_PATH" "$UPLOAD_DIR" \
    || { err "chown 失败"; write_result FAILED START "..."; exit 25; }

# ---------- 12. 启服 + 健康检查 + 数据校验 ----------
log_step "START"
sudo -n systemctl start myblog \
    || { err "systemctl start myblog 失败"; write_result FAILED START "..."; exit 25; }

# 健康检查 (30s 等待新 JVM 起来, URL 从 env 注入避免硬编码端口)
HEALTH_OK=0
for i in {1..30}; do
    if curl -fsS "$RESTORE_HEALTH_URL" >/dev/null 2>&1; then
        HEALTH_OK=1
        break
    fi
    sleep 1
done
[[ $HEALTH_OK == 1 ]] || { err "健康检查失败 (30s 超时, url=$RESTORE_HEALTH_URL)"; write_result FAILED HEALTH "..."; exit 26; }

# 数据完整性校验 (对比 manifest.table_stats_exact vs 实际行数)
log_step "VERIFY"
ACTUAL_COUNTS=$(sqlite3 "$SQLITE_PATH" "
    SELECT name FROM sqlite_master
    WHERE type='table' AND name NOT LIKE 'sqlite_%'
    ORDER BY name
" 2>/dev/null | while IFS= read -r t; do
    [[ -z "$t" ]] && continue
    cnt=$(sqlite3 "$SQLITE_PATH" "SELECT count(*) FROM \"$t\"" 2>/dev/null || echo 0)
    printf '%s\n' "\"$t\":$cnt"
done | paste -sd ',' - | { echo -n '{'; cat; echo '}'; })

DIFF=$(diff <(echo "$EXPECTED_TABLE_COUNTS" | jq -S .) <(echo "$ACTUAL_COUNTS" | jq -S .) || true)
if [[ -n "$DIFF" ]]; then
    warn "数据校验有差异 (仅警告, 不阻断): $DIFF"
    VERIFY_DIFF="$DIFF"
else
    info "数据校验通过"
    VERIFY_DIFF=""
fi

# ---------- 13. 写 .result.json (SUCCESS) ----------
write_result SUCCESS "" "$VERIFY_DIFF"
exit 0
```

**v3 vs v2 关键变化**：

- ✅ step 1 预检：sudo 验证改成 `systemd-run ... /bin/true`（v2 是 `sudo -n true`，不在白名单里）
- ✅ step 9/10/12：去掉所有 `sudo -n -u myblog`（本进程就是 myblog）
- ✅ step 11：保留 `sudo chown`（需要 root）
- ✅ step 4 trap：补 `write_result FAILED`（修复中-1）
- ✅ step 12：健康检查 URL 用 `$RESTORE_HEALTH_URL` 不用硬编码（修复中-4）
- ✅ step 10：openssl 解 uploads 不再 `sudo tar`（本进程就是 myblog，tar 写到属主是 myblog 的目录不需要 sudo）

```typescript
}

// v2 新写: 容错轮询, 处理"后端停服 1-5 分钟"窗口
const startRestorePolling = (id: number) => {
    stopRestorePolling()
    restorePollingId.value = id
    let backoffMs = 2000  // 起始 2s
    const tick = async () => {
        try {
            const res = await get<any>(`/admin/restore/${id}`)
            const item = res?.data
            if (!item) return
            restoreConsecutiveFailures.value = 0
            backoffMs = 2000  // 成功后重置退避
            if (item.status === 'SUCCESS' || item.status === 'FAILED' || item.status === 'UNKNOWN') {
                stopRestorePolling()
                if (item.status === 'SUCCESS') {
                    $toast.success(`恢复成功: ${item.sourceTag}`)
                } else if (item.status === 'UNKNOWN') {
                    $toast.warning(`恢复状态未知, 请检查服务端日志: ${item.errorStage || ''}`)
                } else {
                    $toast.error(`恢复失败: ${item.errorStage || '未知阶段'}`)
                }
                await fetchList()  // 刷新备份列表
            }
        } catch (e: any) {
            // 后端可能因停服连不上 (connection refused / timeout)
            // 退避重试: 2s → 4s → 8s → 16s, 上限 30s
            restoreConsecutiveFailures.value++
            backoffMs = Math.min(backoffMs * 2, 30000)
            // 持续失败超过 5 分钟 → 放弃轮询, 让用户手动刷新页面
            if (restoreConsecutiveFailures.value > 60) {
                stopRestorePolling()
                $toast.warning('轮询超时, 请手动刷新页面查看最终状态')
            }
        }
    }
    tick()
    // setInterval 用动态周期有点别扭, 改成 setTimeout 自调度
    const schedule = () => {
        restoreTimer.value = setTimeout(async () => {
            await tick()
            if (restorePollingId.value !== null) schedule()
        }, backoffMs)
    }
    schedule()
}

const stopRestorePolling = () => {
    if (restoreTimer.value) {
        clearTimeout(restoreTimer.value)
        restoreTimer.value = null
    }
    restorePollingId.value = null
}

onBeforeUnmount(() => {
    stopRestorePolling()
})
```

**v2 关键变化**：

- 不复用 `startPolling(id)` —— 路径 / 语义都对不上（v0.1 问题 #5）
- 退避重试 —— 容忍后端停服 1-5 分钟的 connection refused
- `UNKNOWN` 状态显式提示用户去看服务端日志

### 7.6 浏览器断线重连后的用户体验

恢复期间后端是 down 的，用户浏览器在 admin 页面可能：

1. **停留在原地不动**：等待轮询 reconnect，5 分钟后看到 SUCCESS/FAILED Toast
2. **手动刷新页面**：admin-auth.ts 检查 token → token 还在（JWT 没失效）→ 直接进页面，调 `GET /admin/restore/{id}` 拿到终态

不需要额外的"恢复完成后跳转"逻辑。

> **不新增 `restore` 列表页**。恢复记录是"瞬时任务"，不需要列历史 —— 当前轮询响应里已经带了 status / errorStage / errorMessage / verifyDiff，够用户判断。失败信息也不会丢，存在 `restore_record` 表里供将来查询。

## 12. 部署补充（v3 修订）

### 12.1 sudoers 白名单（v4 收窄到 5 条精确路径，无通配符）

新增 `/etc/sudoers.d/myblog-restore`（参考 `docs/scripts/sudoers-myblog-restore.example`）：

```
# my-blog 数据恢复专用 sudoers 白名单
# 精确授权 5 条命令, 其他一概拒绝
# 部署: sudo install -m 0440 sudoers-myblog-restore.example /etc/sudoers.d/myblog-restore
#       sudo visudo -c -f /etc/sudoers.d/myblog-restore

# 停/启/查 myblog 服务
myblog ALL=(root) NOPASSWD: /usr/bin/systemctl stop myblog
myblog ALL=(root) NOPASSWD: /usr/bin/systemctl start myblog
myblog ALL=(root) NOPASSWD: /usr/bin/systemctl is-active myblog

# 改文件属主（恢复后 Spring Boot 要能写 db / uploads）
myblog ALL=(root) NOPASSWD: /usr/bin/chown -R myblog\:myblog /opt/myblog/*

# v4 新增: systemd-run 创建独立 cgroup, 跑恢复脚本
# v4 关键: **不能末尾用 * 通配符**! 之前 v3 写成
#   /usr/bin/systemd-run --scope --slice=myblog-restore *
#   → myblog 可以 sudo ... bash -i 拿 root shell, 等于 NOPASSWD: ALL
# v4 改成精确到脚本路径: 只能跑这一个 bash 调这一个脚本
myblog ALL=(root) NOPASSWD: /usr/bin/systemd-run --scope --slice=myblog-restore --unit=blog-restore-* --uid=myblog --gid=myblog /bin/bash /opt/myblog/scripts/blog-restore.sh
```

**v4 vs v3 关键变化**（致命新-1）：

- ❌ v3: `/usr/bin/systemd-run --scope --slice=myblog-restore *`（末尾 `*` 通配符任意匹配 → 提权后门）
- ✅ v4: `/usr/bin/systemd-run --scope --slice=myblog-restore --unit=blog-restore-* --uid=myblog --gid=myblog /bin/bash /opt/myblog/scripts/blog-restore.sh`（精确到 `/bin/bash /opt/myblog/scripts/blog-restore.sh`）
- `--unit=blog-restore-*`：通配符**仅允许 unit 名以 `blog-restore-` 开头**，不能传别的
- 加 `--uid=myblog --gid=myblog`：跟 §6.1 ProcessBuilder 对齐，scope 内进程强制以 myblog 身份跑
- 末尾精确到脚本路径：myblog 想 `bash -i` 进不去（只能跑这一个脚本）

**v4 sudoers 安全性自检**：

```bash
# 验证 myblog 不能滥用 systemd-run 提权
sudo -u myblog sudo -n /usr/bin/systemd-run --scope --slice=myblog-restore /bin/bash -i
# 期望: 报 "Sorry, user myblog is not allowed to execute ..."
# 因为白名单末尾必须是 /bin/bash /opt/myblog/scripts/blog-restore.sh, -i 进不去

sudo -u myblog sudo -n /usr/bin/systemd-run --scope --slice=other-slice /bin/bash
# 期望: 拒绝 (--slice=other-slice 不在白名单)

sudo -u myblog sudo -n /usr/bin/systemctl restart myblog
# 期望: 拒绝 (没有 restart 白名单, 只有 stop/start/is-active)
```

**精确路径、精确子命令**，避免被滥用。`NOPASSWD` 是因为 myblog 服务运行无终端，不能交互输入密码。

部署时一次性 `install -m 0440` 进去，**本仓库不直接修改生产 /etc/sudoers.d/**。

### 12.2 一次性部署步骤（v3 第一次上线）

1. 部署 jar（deploy-server.sh，DEPLOY_MODE=code）
