# 博客数据恢复方案设计（v5.0 · 同进程不停服）

> 版本：v5.0
> 更新日期：2026-06-24
> 状态：现行方案（取代 v4.3.0 的脚本 + 双轨回填模型）
> 前置文档：`docs/design/博客数据备份方案设计.md`（备份产物结构、加密协议、manifest 格式）

---

## 1. 设计目标

把数据恢复从「外部脚本 + 重启 JVM + 跨进程回填」简化为「同 JVM 进程内执行 + SQLite Online Backup API 原子替换」，消除整套时序复杂度，并让 Docker 与宿主机走完全相同的代码路径。

| 维度 | v4.3.0（旧） | v5.0（新） |
|------|-------------|------------|
| 执行方式 | `ProcessBuilder("sudo", "systemd-run", "--scope", ...)` 启动 `blog-restore.sh`，pb.start() 后立刻 return | `@Async` 直接在 JVM 内执行 7 步流水线，全程同进程 |
| myblog 服务 | 全程停服 1-5 分钟（脚本 systemctl/supervisorctl stop → restart） | **全程不停服**，HikariCP 连接不重建 |
| DB 替换方式 | `rm -f blog.db` + `sqlite3 blog.db < dump.sql` 重建 | `SQLiteConnection.restore()`（SQLite Online Backup API） |
| 进程隔离 | 宿主机靠 `myblog-restore.slice` 独立 cgroup、Docker 靠 `supervisorctl` 守护 | 无外部进程，无需 cgroup / supervisorctl |
| 状态回填 | result.json 协议 + 双轨 Reconciler（ApplicationReadyEvent + 5s 二次 + 60s scheduled） + meta 文件 + 孤儿重建 | record 直接走 PENDING → RUNNING → SUCCESS/FAILED，全程同 JVM 内 update |
| Docker 兼容 | Docker 分支需 `supervisorctl stop/start myblog` + `wait_port_freed` + exit 29 | 与宿主机走完全相同路径，无 Docker 特殊分支 |
| 依赖 | `gh` / `jq` / `openssl` / `tar` / `sha256sum` / `sqlite3` / `sudo` / `systemd-run` / `supervisorctl` / `curl` | 仅 JDK + `org.xerial:sqlite-jdbc`（已有）+ `commons-compress`（新增） |
| 失败模式 | ~10 种（RESULT_PARSE_FAILED / RESULT_INVALID / ORPHAN / START / STOP / SHA256 / IMPORT / UPLOADS / HEALTH / TRAP） | 6 种（DOWNLOAD / VERIFY / DECRYPT / IMPORT / UPLOADS / POSTCHECK） |
| 失败可见性 | 最长 ~5s（启动 5s 二次触发）到 ~2min（scheduled） | 实时（同 JVM update，request 链路立即返回） |
| 代码量 | ~1200 行（service + reconciler + 600 行 shell） | ~400 行 Java + 0 行 shell |

## 2. 核心原理：SQLite Online Backup API

xerial sqlite-jdbc 暴露 `org.sqlite.SQLiteConnection.restore(dbName, sourceFile, observer)`，底层是 SQLite C API `sqlite3_backup_*`。语义：

- 用 EXCLUSIVE 锁短暂锁住目标 db，按 page 复制 source → destination
- 复制窗口内其他连接读写返回 `SQLITE_BUSY`，由 `busy_timeout` 自动重试
- 个人博客 db 量级（几 MB）锁窗口次秒级（实测 < 1s）
- HikariCP 连接无需重建，下次事务自动看到新数据
- 即使目标 db 当前打开也能正常工作（这正是 API 的设计目的）

**WAL 兼容性**：restore 后 SQLite 的 `journal_mode` 会被重置为 rollback journal，需要执行 `PRAGMA journal_mode=WAL;` 重新打开 WAL。

**MySQL profile**：v5.0 不支持 MySQL profile 下的数据恢复（旧版本也只支持 SQLite）。源码注释里留 TODO，待 v5.x 后续版本评估实现思路（dump/restore via mysqldump 或 logical backup 等）。

## 3. 流程总览

```
POST /api/v1/admin/restore/run
   │
   ▼
RestoreService.triggerRestore (同步)
   │ 1. 预检 env（BACKUP_ENCRYPTION_PASSWORD / BACKUP_GITHUB_TOKEN / GITHUB_BACKUP_REPO）
   │ 2. 预检 scope（DB_ONLY / DB_UPLOADS）
   │ 3. 预检 source backup（status=SUCCESS + tag 非空）
   │ 4. 并发互斥（countRunning + uk_restore_record_running）
   │ 5. INSERT restore_record (status=PENDING)
   │ 6. self.runRestoreAsync(id)  ← @Async, 同 JVM
   │
   ▼ return id

RestoreService.runRestoreAsync (异步, 同 JVM)
   │ status: PENDING → RUNNING
   │
   ▼ RestoreExecutor.execute(record):
   │   ┌─────────────────────────────────────────────────────────────────┐
   │   │ Step 1 · DOWNLOAD                                              │
   │   │   GithubReleaseClient.downloadAssets(tag, stageDir, assets)    │
   │   │   - GET /repos/{repo}/releases/tags/{tag} 拿 asset 元信息       │
   │   │   - 逐个下载 manifest.json / SHA256SUMS / *.enc                 │
   │   │   - HttpURLConnection + Authorization: token $TOKEN            │
   │   │                                                                 │
   │   │ Step 2 · VERIFY                                                │
   │   │   - 解析 SHA256SUMS, 用 MessageDigest 校验每个 .enc 文件        │
   │   │   - 解析 manifest.json 拿 .db.encrypted_file 和 table_stats     │
   │   │                                                                 │
   │   │ Step 3 · DECRYPT                                               │
   │   │   EncryptedDumpCodec.decryptAndDecompressToSql(encFile, pwd)   │
   │   │   - openssl 兼容格式: Salted__{8 字节 salt}{密文}              │
   │   │   - PBKDF2WithHmacSHA256 推 key + iv (iter=10)                 │
   │   │   - Cipher AES/CBC/PKCS5Padding decrypt                        │
   │   │   - GZIPInputStream → sql 临时文件                              │
   │   │                                                                 │
   │   │ Step 4 · IMPORT (核心)                                          │
   │   │   - 用临时 sqlite 文件（jdbc:sqlite:/tmp/.../staged.sqlite）   │
   │   │     执行 dump.sql 构建一个全新的 db                             │
   │   │   - SqliteOnlineBackup.copyOver(stagedPath, livePath)           │
   │   │     用 dest connection 的 restore API 从 stagedPath 覆盖        │
   │   │   - 完成后执行 PRAGMA journal_mode=WAL 重启 WAL                 │
   │   │                                                                 │
   │   │ Step 5 · UPLOADS (scope=DB_UPLOADS 时执行)                      │
   │   │   - Decrypt uploads.tar.gz.enc → /tmp/.../uploads.tar.gz        │
   │   │   - commons-compress TarArchiveInputStream 解到 $UPLOAD_DIR.new │
   │   │   - 校验每个 entry path 必须以 $UPLOAD_DIR.new 为前缀 (Zip Slip)│
   │   │   - 原子切换: mv $UPLOAD_DIR → $UPLOAD_DIR.old.{ts} +           │
   │   │              mv $UPLOAD_DIR.new → $UPLOAD_DIR                   │
   │   │                                                                 │
   │   │ Step 6 · POSTCHECK                                             │
   │   │   - 用 JdbcTemplate 跑 SELECT COUNT(*) FROM 各表                │
   │   │   - 对比 manifest.db.table_stats_exact (仅记录 verifyDiff)      │
   │   └─────────────────────────────────────────────────────────────────┘
   │
   ▼ 成功: status=SUCCESS + verifyDiff (如有)
   ▼ 失败: status=FAILED + errorStage + errorMessage
   ▼ finally: 清理 /tmp/blog-restore-{id}/* + 临时 staged.sqlite
```

## 5. 关键决策与依据

### 5.1 为什么用 SQLite Online Backup API 而不是 ATTACH/transaction

| 方案 | 优点 | 缺点 |
|------|------|------|
| **Online Backup API**（采用） | 锁窗口次秒级；HikariCP 连接复用；WAL 自动处理；专为 live restore 设计 | restore 后需手动重启 WAL |
| schema-drop + import 全 SQL | 不引入新 API | 长事务阻塞全应用；中途失败 DB 损坏 |
| 新 DB 文件 + 重命名 | 原子切换 | open file handle 仍指向旧 inode；必须重建连接池 ≈ 软重启 |

### 5.2 为什么删 result.json 协议

旧设计是「跨进程通信」：脚本写 result.json，JVM 读 result.json 回填状态。同 JVM 后这层协议完全冗余——直接 `mapper.updateById(record)` 即可。

附带消除的失败模式：
- result.json 半写（脚本崩溃 → status 字段缺失 → RESULT_INVALID）
- result.json 解析异常（JSON 损坏 → RESULT_PARSE_FAILED）
- result.json 丢失（脚本写之前被 kill → 30min 后 ORPHAN）
- result.json 落在 stage_dir 内（被 trap 清理）→ 设计上必须挪到 result_dir

### 5.3 为什么删 meta 文件 + 孤儿重建

旧设计的 meta 文件是为了在「sqlite-import.sh wipe DB 后 restore_record 丢失」时反向重建。新方案不 wipe（Online Backup API 是原地替换），restore_record 全程在 DB 里，无需重建。

### 5.4 uploads 切换（v5.0.1 改写：mount 内部 entry 级 swap）

**初版（v5.0.0）**：解压到 `$UPLOAD_DIR.new`，然后 `mv $UPLOAD_DIR → $UPLOAD_DIR.old.{ts}` + `mv $UPLOAD_DIR.new → $UPLOAD_DIR` 做整目录原子切换。

**翻车场景**：Docker 容器内 `/opt/myblog/uploads` 是 volume mount 挂载点（`-v myblog-sim-uploads:/opt/myblog/uploads`）。Linux 内核**拒绝**对挂载点本身执行 rename，无论是否停 nginx 都触发 `FileSystemException: Device or resource busy`。停 nginx 没用——nginx 持有的是挂载里的具体文件 fd，挂载关系本身是被内核锁住的。

**v5.0.1 修正**：永远不触碰挂载点，所有操作只在 mount 内部完成：

```
1. mkdir $UPLOAD_DIR/.restore-staging.{ts}/        ← 在挂载内
2. decrypt → tar 解到 $UPLOAD_DIR/.restore-staging.{ts}/
   每个 entry path 必须 canonical 在 staging 下（Zip Slip 防御）
3. mkdir $UPLOAD_DIR/.restore-old.{ts}/
4. for entry in $UPLOAD_DIR/* (排除 .restore-staging.* / .restore-old.*):
       mv entry → $UPLOAD_DIR/.restore-old.{ts}/entry        ← entry 级 mv
5. for entry in $UPLOAD_DIR/.restore-staging.{ts}/*:
       mv entry → $UPLOAD_DIR/entry                          ← entry 级 mv
6. rmdir $UPLOAD_DIR/.restore-staging.{ts}/                   ← 已空
7. 异步删 $UPLOAD_DIR/.restore-old.{ts}/                      ← 后台清理
8. 失败时 best-effort 回滚：把 .restore-old.{ts}/ 内 entry 移回 top-level
```

**关键差异**：
- 每个 `mv` 是单文件 / 单子目录的 entry-level rename，与 mount 关系无关，不触发 EBUSY
- 整体**不是严格 atomic**（步骤 4-5 之间挂载内容短暂混合，几秒钟），对个人博客可接受
- **nginx 不需要 stop**：nginx 持有已 open 文件的 fd 通过 inode 引用，entry 级 mv 不影响 inode，新请求 resolve 到新 entry
- 失败时回滚是 best-effort，只把 oldHoldDir 内 entry 移回未被新 entry 占用的位置，避免覆盖已切换的新数据

### 5.5 删除 Reconciler 双轨触发

旧设计 5s 二次触发 + 60s scheduled 是为了覆盖「脚本写 result.json 在 myblog start 之后」的时序窗口。新方案 JVM 全程同步推进状态，触发场景不存在，删除。

新 Reconciler 仅保留：JVM 启动时扫一次 RUNNING 状态、按 `startedAt < now - 30min` 阈值标 UNKNOWN（仅处理「JVM 在恢复中崩溃，新 JVM 起来后状态机滞留 RUNNING」场景）。

## 6. 错误分级与 stage 命名

| stage | 触发条件 | exit code（v4 对应） |
|-------|---------|---------------------|
| `DOWNLOAD` | GitHub 拉取 release 元信息 / asset 文件失败 | 21 |
| `VERIFY` | SHA256 校验失败 / manifest.json 解析失败 | 22 |
| `DECRYPT` | 密码错误 / 加密文件损坏 / gunzip 失败 | 23 |
| `IMPORT` | 临时 sqlite 构建失败 / Online Backup 失败 | 24 |
| `UPLOADS` | tar 解压失败 / Zip Slip 检测命中 | 27 |
| `POSTCHECK` | 数据完整性校验异常（仅记录 verifyDiff，不阻断） | - |

前端 `restoreStatusType` / `restoreStatusLabel` 现有色值映射与 stage 名称完全兼容，无需改动。

## 7. 安全防护

| 风险 | 防护 |
|------|------|
| GitHub token / 解密密码泄露 | 全程 `@Value` 注入 + 静态字段，不出现在异常 message / 日志 |
| 临时文件残留（敏感数据） | try-with-resources + finally 清理；启动时扫 `/tmp/blog-restore-*` 兜底 |
| Zip Slip / Path Traversal | 解压 entry 必须 canonical path 以 `$UPLOAD_DIR.new` 为前缀，否则跳过该 entry + WARN |
| tar bomb（解压炸弹） | 单 entry 大小上限 100 MB；总解压大小上限 1 GB；entry 总数上限 100,000 |
| 并发恢复 | `countRunning() == 0` 应用层 + `uk_restore_record_running` DB 唯一索引双重防护 |
| 备份/恢复同时跑 | restore trigger 查 backup + restore 两表 RUNNING；backup trigger 同理（已有逻辑保留） |
| HTTP MITM | HTTPS only（`https://api.github.com/...`），HttpURLConnection 默认走 JVM truststore |
| MySQL profile 误触发 | 暂不检测；恢复操作本就只支持 SQLite，代码注释 TODO 留作 v5.x 处理 |

## 11. 数据模型（不变）

```sql
CREATE TABLE IF NOT EXISTS restore_record (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  source_record_id INTEGER NOT NULL,       -- backup_record.id
  source_tag      TEXT NOT NULL,           -- 冗余 backup_record.tag (反查)
  scope           TEXT NOT NULL,           -- DB_ONLY / DB_UPLOADS
  status          TEXT NOT NULL,           -- PENDING / RUNNING / SUCCESS / FAILED / UNKNOWN
  started_at      DATETIME NOT NULL,
  finished_at     DATETIME,
  error_stage     TEXT,                    -- DOWNLOAD / VERIFY / DECRYPT / IMPORT / UPLOADS / POSTCHECK
  error_message   TEXT,                    -- 失败信息 (截断 500)
  verify_diff     TEXT,                    -- 数据校验差异 (截断 500)
  operator_id     INTEGER,
  operator_name   TEXT
);

-- 唯一索引: 同一时刻只能有一条 RUNNING (DB 兜底 TOCTOU)
CREATE UNIQUE INDEX IF NOT EXISTS uk_restore_record_running
  ON restore_record(status) WHERE status='RUNNING';
```

## 13. 迁移与回滚

### 迁移
本次为一次性切换（Phase 1 == Phase 2 合并），无双跑过渡期：

### 回滚
如发现 Online Backup API 在生产 db 大小下出现意外行为（如锁窗口过长），回滚步骤：
1. 通过 git revert 还原相关 commit
2. 重装 `sudo` / `gh` / `jq` / `supervisorctl` / 配 sudoers
3. 重启 myblog

由于改动是「单向收敛」（删除 > 新增），git revert 即可，无需特殊数据迁移。
