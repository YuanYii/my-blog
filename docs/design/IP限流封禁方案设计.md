# IP 限流与封禁方案设计

> 状态：**已实现**（2026-06-18）
> 落地组合：10 次/秒 / 30 分钟封禁 / 全站请求 / Redis 热路径 + DB 持久化

## 背景

用户提出的原始需求是"防重放机制：某 IP 1 秒内访问超过 N 次就封禁"。这描述的实际上是**频率型攻击防护**（暴力刷接口 / 爬虫 / CC 攻击），
与 `防重放攻击方案设计.md` 里"防重放"（同一个被截获的合法请求被原样重发）是**两个不同维度的安全问题**，因此本方案单独命名、单独落地，文末有专门的对比章节。

## 方案：Redis 计数 + DB 持久化封禁

### 核心设计

| 层 | 机制 |
|---|------|
| **计数** | `IpRateLimitFilter` 按 `IP + 自然秒` 分桶，Redis `INCR`，TTL=2s |
| **封禁判定** | 同一桶内计数 `> 10`（第 11 次请求触发）→ 调 `IpBanService.ban()` |
| **封禁标记（热路径）** | Redis `ip_ban:{ip}`，`SETNX` 占坑 + TTL=封禁时长，请求进来先查这个 key（O(1)） |
| **封禁记录（审计）** | DB `ip_ban` 表，只在"触发封禁那一刻"写一行，供 admin 后台查看/手动解封 |
| **范围** | 全站所有请求（含 admin 接口、公开接口），OPTIONS 预检豁免 |
| **降级** | Redis 不可用 → fail-open（放行 + WARN 日志），与登录限流、PageViewFilter 一致的可用性优先原则 |
| **重启恢复** | `@PostConstruct warmUpFromDb()`：应用启动时把 DB 里"未手动解封 + 未过期"的封禁记录回灌进 Redis |

### 关键决策记录

| 决策点 | 选择 | 备选 |
|------|------|------|
| 阈值 N | 10 次/秒 | 5 次（严）/ 20 次（宽） |
| 封禁时长 | 30 分钟 | 5 分钟（短）/ 永久（需人工解封） |
| 防护范围 | 全站所有请求 | 仅 admin / 仅写请求 |
| 计数存储 | Redis（固定窗口，按自然秒分桶） | in-memory（单实例够用，但重启丢状态、不支持多实例） |
| 封禁名单持久化 | **DB 持久化**（用户明确选择，非默认推荐项） | 纯内存（重启自动清空，更简单，但 admin 后台无法查看/解封历史） |

### 请求流程

1. 请求进入 `IpRateLimitFilter`（filter 链最前面）
2. 查 Redis `ip_ban:{ip}` 是否存在 → 存在则直接 429，不再计数
3. 不存在 → `INCR rate_limit:{ip}:{epochSecond}`
4. 计数 `> 10` → 写 Redis 封禁标记（SETNX 防并发重复封禁）+ 异步落 DB 一行 → 429
5. 计数 `≤ 10` → 放行到下一个 filter / controller

### 验收用例

1. **正常请求**：同一 IP 1 秒内 ≤10 次 → 全部通过
2. **超限触发**：第 11 次 → 429，且该 IP 立即进入封禁状态
3. **封禁期间**：任意路径、任意请求 → 429，不再参与计数
4. **到期自动解封**：30 分钟后该 IP 恢复正常计数
5. **手动解封**：admin 调 `PUT /admin/ip-bans/{id}/unban` → 立即生效，不用等 TTL
6. **Redis 故障**：限流检查异常 → 全部放行（fail-open + WARN 日志）
7. **应用重启**：DB 中未过期的封禁记录在启动时回灌进 Redis，不出现"重启后封禁失效的空窗期"

### 风险与权衡

- **共享 IP 误杀**：NAT / 公司网 / 校园网下多用户共享同一出口 IP，一人触发阈值会牵连同 IP 下所有人被封 30 分钟。当前未做按用户/会话维度的精细化限流，是 IP 维度方案的固有局限。
- **固定窗口边界**：按自然秒分桶（非滑动窗口），理论上跨秒边界的请求可能在极短时间内达到接近 2N 次而不触发封禁。为实现简单和性能选择固定窗口，可接受。
- **代理池绕过**：攻击者使用代理池轮换 IP 可绕过封禁——这是任何 IP 维度限流的天然局限，需要时应叠加验证码/行为验证等更高层防御，不在本方案范围内。
- **Redis 单点**：与登录限流、站点设置缓存共用同一 Redis 实例，故障域已存在，未引入新的单点风险。

## 与《防重放攻击方案设计》（**文档未建**，对比仅作设计意图参考）的对比

两个方案防御的**不是同一类攻击**，不能互相替代：

| 维度 | 防重放攻击方案（待实现） | 本方案：IP 限流封禁（已实现） |
|---|---|---|
| 防御目标 | 阻止"同一个被截获的合法请求"被原样重发（语义级重放） | 阻止"单 IP 短时间内发起大量请求"（频率级刷量/爬虫/CC） |
| 防护范围 | 仅 admin 写请求（POST/PUT/DELETE） | 全站所有请求，含公开端点和 GET |
| 客户端改造 | 需要前端主动加 `X-Timestamp` / `X-Nonce`，未升级的客户端（含第三方脚本、Postman）会被 400 拒绝 | 无需任何客户端改造，纯服务端识别 IP + 频率 |
| 误杀维度 | 请求级（nonce 唯一），不会误伤同 IP 下其他正常请求 | IP 级，共享出口 IP 时存在误杀风险 |
| 持久化 / 可观测 | 仅 Redis nonce（TTL 120s），无 DB 落库，事后无法追溯历史 | DB `ip_ban` 表持久化 + admin 后台查看/手动解封，有审计能力 |
| 应用重启后状态 | 无影响（nonce 本就设计为短期一次性，重启清空符合预期） | 有专门的回灌机制，封禁状态跨重启不丢失 |
| 精确重放单次请求（只重发 1 次，未超频率阈值） | ✅ 能拦截（nonce 命中即拒） | ❌ 拦不住——这正是本方案的盲区 |
| 高频暴力刷量 / 爬虫 / CC 攻击 | ❌ 不防（仅限 admin 写请求，且换个 nonce 就能绕过） | ✅ 能拦截——这正是防重放方案的盲区 |
| 实现状态 | 设计稿，未落地 | 已落地 |

**本方案相对的工程优势**：覆盖面更广（全站而非仅 admin 写请求）、零客户端改造成本、有 DB 审计与人工解封入口、应用重启状态不丢失。

**但必须诚实指出**：如果攻击者截获一个合法请求只重放一次（没有触发 1 秒 10 次的频率阈值），本方案完全无效——这恰恰是防重放方案要解决的核心场景。两者是**正交、互补**关系而非替代关系：本方案是频率层的前置防线，防重放方案是语义层的精确防线。后续如果要补齐 admin 写请求被截获后精确重放的风险，仍需要按《防重放攻击方案设计》落地 timestamp + nonce 校验。
