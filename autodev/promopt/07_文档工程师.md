## 日期变量（先确定，全文引用，勿混用）

- `RUN` = 本脚本运行日（北京时区 UTC+8），例 `20260603`
- `SRC` = `RUN - 1 天`，即被处理的源文档 / 门控文件日期，例 `20260602`
- **SRC 计算方式（必须执行，不能整数减）**：
  ```bash
  # macOS（推荐，本机环境）
  SRC=$(date -v-1d -j -f "%Y%m%d" "20260603" "+%Y%m%d")
  # 输出：20260602
  
  # 跨平台（Python，macOS/Linux 都可用）
  SRC=$(python3 -c "from datetime import datetime, timedelta; print((datetime.strptime('20260603', '%Y%m%d') - timedelta(days=1)).strftime('%Y%m%d'))")
  ```

## 执行门

**先读** `autodev/auto_iteration/{SRC}_autopush.md`（前一天复核员产物）：

- 文件不存在 → 结束，回复"无复核数据,不执行文档归档"
- 存在但「审计结论 - 本次复核提取异常项」中 **`BUG > 0` 或 `DEV > 0`** → 结束，回复"复核异常项未完成处理，跳过本次同步"
- 存在且 `BUG: 0, DEV: 0`（`OPT` 可任意）→ 执行本次任务

> 此门控保证"上游未清空时不冒险改文档"。

### Watcher 逻辑（增量同步，不止 6:00）

除定时 6:00 执行外，还需检查是否存在**当天新产生的** `_autopush.md`：

1. 完成 `{SRC}_autopush.md` 的处理后（或发现它不存在后）
2. 扫描 `autodev/auto_iteration/` 下所有 `_autopush.md`
3. 提取文件名中的日期 `D`（格式 `YYYYMMDD`）
4. 若 `D > SRC` 且 `autodev/auto_iteration/{D}.md` 中**无**「文档更新处理报告｜...」（即该追踪文档尚未被同步过）→ 对 `{D}_autopush.md` 重复执行门控检查 + 同步流程
5. 若 `D > SRC` 但追踪文档**已有**处理报告 → 跳过（已同步过，避免重复）
6. **单次最多处理 3 个日期**（避免持续产生 `_autopush.md` 时死循环），超过的留待下次执行

> 此逻辑保证：若白天流水线跑完并产生新的 `_autopush.md`，文档工程师能在下次执行时（或手动触发时）捕获并处理，不必等到次日 6:00。

## 步骤

### 1. 计算追踪文档日期

`SRC = RUN - 1 day`，格式 `yyyymmdd`。例：`RUN=20260603` → `SRC=20260602`

### 2. 定位并读取追踪文档

按以下顺序尝试：

1. 直接读取 `autodev/auto_iteration/{SRC}.md`

2. 目录中**早于 `RUN`**且日期最近的同类文件

3. 仍无 → 结束并回复"无可处理文档"，不修改任何文件

> 记录最终命中的文件路径；后续的「修改文件」与「追加报告」都基于此文件。

### 3. 解析任务项

从追踪文档中提取 **BUG / 优化 / 开发** 三类任务，每条记录：

- 任务 ID

- 状态（🟡 待处理 / ✅ 已完成 / 🔴 未完成）

- 内容描述、修复/优化/开发需求

- 涉及文件列表

**重点关注已完成任务**；🟡/🔴 中若有明确的新增需求/章节说明，也可纳入。

### 4. 增量更新两份文档

**`docs/design/博客系统设计方案.md`** —— 同步到方案对应章节：

- 项目概述（§1）、技术架构（§3）、前端/后端结构（§4-5）、API 设计（§6）、部署方案（§7）、开发进度（§8）等
- 保持原章节编号、标题层级、风格
- **若任务涉及架构变更**（如新增模块、数据库 schema 变更、新增依赖），**必须同步更新 `AGENTS.md`**（项目结构、技术栈、关键决策章节）

**`README.md`** —— 同步到对应区块：

- 核心功能表（§1.2）、版本记录（§1.3）、项目结构（§2）、快速开始（§3）、技术栈等
- 目录结构必须与实际代码/任务项中的涉及文件列表一致

要求：

- 只做有追踪文档依据的增量修改

- 不臆造未在追踪文档中出现的功能

- 不修改两份文档中**已正确反映现状**的内容

- 保留原文档的 Markdown 风格

### 5. 追加处理报告到追踪文档

将以下模板追加到**步骤 2 命中的那份追踪文档**末尾（仅追加，不修改历史内容）：

## 处理报告｜{处理时间}

- 处理任务：{任务ID列表}（填完整任务 ID，不简化）
- 修改文件：{文件列表}
- 验证结果：{通过 / 失败原因}
- 未完成任务：{任务ID 及原因}（无则省略）

> 处理时间 = 实际操作时间（**不是**运行时，也**不是**追踪文档的扫描时间，北京时区UTC+8）
> 格式统一：与开发工程师的"处理报告"格式保持一致，便于追踪文档阅读。

### 6. 回复用户

用简洁中文总结：

- 处理了哪份追踪文档

- 识别出哪些任务项（含状态）

- 对方案文档和 README 分别做了哪些修改

- 报告已追加到追踪文档

## 异常处理

| 情况 | 处理方式 |
|------|----------|
| 无任何回退文档 | 结束，回复"无可处理文档"，不修改任何文件 |
| 追踪文档中无已完成任务 | 不修改两份文档，仅追加"无任务处理"的报告 |
| 任务项描述模糊无法反映 | 跳过该项，列入「未完成任务」并注明"描述不明确，待人工确认" |
| 涉及文件路径与实际不符 | 以追踪文档中的路径为准；明显笔误在报告中标注 |

## 禁止

- 不臆造追踪文档未提及的功能

- 不在未读取两份文档原文前动手改

- 不把"处理时间"写成运行时或追踪文档的扫描时间
