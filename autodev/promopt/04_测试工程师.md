## 日期变量（全文引用，勿混用）

- `RUN` = 本脚本运行日（审计当天，北京时区 UTC+8），例 `20260603`
- `SRC` = `RUN - 1 天`，即被审计的源文档日期，例 `20260602`
- **SRC 计算方式（必须执行，不能整数减）**：
  ```bash
  # macOS（推荐，本机环境）
  SRC=$(date -v-1d -j -f "%Y%m%d" "20260603" "+%Y%m%d")
  # 输出：20260602
  
  # 跨平台（Python，macOS/Linux 都可用）
  SRC=$(python3 -c "from datetime import datetime, timedelta; print((datetime.strptime('20260603', '%Y%m%d') - timedelta(days=1)).strftime('%Y%m%d'))")
  ```

> 约定：**审计文件按 `RUN` 命名**（审计当天）；**源文档按 `SRC`**。

## 执行模式（每次启动前先判断）

### 模式 A：首次执行（全量审计）
当 `auto_audit/{RUN}/{RUN}-stage4.md` 不存在时：
- 走原有"审计流程"全量审计源文档中所有 `✅ 已完成` 任务
- 输出文件：`auto_audit/{RUN}/{RUN}-stage4.md`

### 模式 B：重复执行（增量审计）
当 `auto_audit/{RUN}/{RUN}-stage4.md` 存在时，**严格按下面 4 步走**：

#### 第 1 步：扫描源文档当前状态（必做）
- `grep -nE "^### 20[0-9]{6}-(BUG|OPT|DEV)-[0-9]+" autodev/auto_iteration/{SRC}.md`
- 提取每条任务的**当前状态**（`✅ 已完成` / `🟡 待处理` / `🟠 执行中` / `❌ 执行失败`）和**完整编号**
- 输出形如：`{SRC} 当前有 N 项 ✅ 任务：[BUG-001, BUG-002, OPT-001, ...]`

#### 第 2 步：扫描历史报告的遗留项
- 扫描 `{RUN}-stage4.md`
- 提取两类遗留项：
  1. **偏差项**：状态为 ⚠️ / ❌ 的任务（含具体偏差描述与文件:行号出处）
  2. **未确认项**：需人工确认清单中**未勾选**的 `- [ ]` 条目
- **注意**：历史报告里"已 ✅ 通过"的任务**不构成遗留项**，但**不意味着本次可以不审**——见第 3 步

#### 第 3 步：计算本次审计范围（关键，不能跳过）
本次审计范围 = **以下三类并集**：
- (a) 历史报告遗留项中的所有任务 → 必须复核
- (b) **源文档当前 ✅ 但历史报告从未审计过的任务** → 视为新增范围，必须审计
- (c) **源文档状态相对历史报告有变化的任务**（如 🟡→✅、✅→🟡/❌） → 必须审计

> 计算步骤（明确，不可使用模糊的"diff 算法"措辞）：
> 1. 提取历史报告审计过的任务编号集合：`grep -hE "^### 20[0-9]{6}-(BUG|OPT|DEV)-[0-9]+" auto_audit/{RUN}/{RUN}-stage4.md | sort -u`
> 2. 提取源文档当前 ✅ 任务编号集合：`grep -nE "^### 20[0-9]{6}-(BUG|OPT|DEV)-[0-9]+" autodev/auto_iteration/{SRC}.md | grep "✅ 已完成" | 提取编号 | sort -u`
> 3. 差集 (b) = 步骤 2 结果 - 步骤 1 结果
> 4. 差集 (c) = 源文档中状态变化的任务（对比历史报告中的状态记录）
> 5. 本次范围 = (a) + (b) + (c)

#### 第 4 步：核对并输出
- 对第 3 步算出的所有任务，逐一执行"审计流程"（静态核对 + 判定）
- 已修复/已对齐：标记为 ✅，从遗留项中移除，给出证据（git diff / 文件:行号）
- 仍存在/未修复：保留 ⚠️/❌ 状态，注明"本次复核仍存在"
- 新发现的问题：作为新增项加入报告
- **对所有本次审过的 ✅ 任务，检查"人工验证结果"字段**：含"存在bug"/"不通过"等关键词的，写入报告
- 输出文件：`auto_audit/{RUN}/{RUN}-stage4.md`

## 审计流程

### 1. 加载任务清单
读取指定日期的 markdown，列出所有 `✅ 已完成` 的任务（标题含 BUG/OPT/DEV 编号）。
对每条任务提取：需求/描述/优化描述、验证清单、解决方案、涉及文件列表、人工验证结果。

**autopush 卡片特殊处理**：
- autopush 卡片（编号格式 `autopush-{SRC}-<BUG|OPT|DEV>-NNN`）可能无"验证清单"字段（来自审计报告的异常提取）
- 审计依据：按卡片的「描述/优化描述/开发内容」字段（原始异常描述）+ 「涉及文件列表」（文件:行号）
- 验证清单处理：若卡片无验证清单，则根据「描述」字段自行拆解验证项，在报告中注明"验证清单由审计员根据异常描述拆解"

### 2. 静态核对
对每条任务的"验证清单"逐项 grep 涉及文件，确认功能点有对应代码、关键字段/参数/行为与描述一致。

> 找不到 ≠ 不符，先换关键词搜，再标"未找到实现"。

### 3. 判定

| 状态 | 含义 |
|------|------|
| ✅ 通过 | 验证清单全部命中，人工验证结果为"通过"或空且无矛盾 |
| ⚠️ 部分通过 | 核心实现但验证清单有遗漏/偏差，或人工验证标"不通过" |
| ❌ 未实现 | 涉及文件无对应改动，或关键功能完全找不到 |
| 🔍 需运行确认 | 涉及 UI 交互、视觉效果、LLM 输出、时区/时间显示等无法静态判定的项 | 必须写明【需要什么类型的运行验证】（如：需启动本地服务器访问 /admin/login 验证重定向），禁止只写"需人工确认" |
