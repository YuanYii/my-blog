### 20260624-BUG-002 | 高 | ✅ 已完成

- **描述**：
  Docker 模式下执行数据恢复时，`sqlite-import.sh` 导入失败，result.json 显示 `FAILED` (IMPORT 阶段)。

  **现象**：
  1. 管理后台触发恢复操作，restore_record 创建成功 (id=4, status=RUNNING)
  2. `blog-restore.sh` 在 Docker 模式下启动，约 15 秒后失败
  3. result.json 内容：`{"status":"FAILED","stage":"IMPORT","message":"sqlite-import.sh 失败"}`
  4. 数据库实际已被部分恢复（restore_record 表被 wipe），但恢复记录显示 FAILED

  **根因分析**：
  `blog-restore.sh` 第 4 节"停 myblog"逻辑在 Docker 模式下直接跳过：
  ```bash
  if $IN_DOCKER; then
      info "Docker 环境, 跳过 systemctl stop (容器内无 systemd 服务管理)"  # ← 跳过了！
  else
      sudo -n systemctl stop myblog  # ← 非 Docker 模式正常停止
  fi
  ```
  导致 `sqlite-import.sh` 执行时 Spring Boot 应用仍在运行，HikariCP 连接池持有数据库文件锁。当脚本执行 `rm -f blog.db` 或 `sqlite3 blog.db < dump.sql` 时，遇到文件锁冲突或 WAL 状态不一致，导入失败。

  **影响范围**：
  - 仅影响 Docker 模式（`myblog-sim` 容器）
  - 非 Docker 模式（systemd 管理）不受影响

-   **修复思路**：Docker 模式下使用 `supervisorctl stop/start myblog` 管理应用生命周期。

  **前置假设**：`myblog-sim` 容器 supervisord 已安装,**但 `[program:myblog]` 段配置由 `deploy-server.sh §8` 在首次部署时写入 `/etc/supervisor/conf.d/myblog.conf`**(见 `docs/deployment/docker/local-sim/supervisord.conf:36-39`)。也就是说:本修复仅在"容器已经被 deploy-server.sh 部署过 myblog"的状态下生效;全新空容器需先跑过 deploy-server.sh,否则 `supervisorctl status myblog` 会返回"unknown program",脚本必须明确报错 + exit。

  **核心要求**：解决方案必须是自动化修复,不允许要求用户手动执行任何命令。
  - 不得要求用户手动执行 `supervisorctl stop/start myblog`
  - 不得要求用户手动重启容器
  - supervisorctl 失败时**不静默 fallback**(不要用 pkill 兜底重启,避免 supervisord 配置错误被掩盖)

  **退出码约定**:Docker 模式新增 `exit 29 = supervisorctl 失败`(脚本头部退出码表第 24 行附近补一行)。**不复用现有 25**——`blog-restore.sh:21` 已经把 25 给了"chown / systemctl start 失败",混用会让运维难以定位失败阶段。

  **停服后等待时机**:停服后**不再用 `sleep 2` 经验值**,改为轮询 `! lsof -iTCP:8080 -sTCP:LISTEN >/dev/null 2>&1`(端口不再监听)最长等 10s,超时 exit 29。若 lsof 不可用 fallback 到 sleep 3(注释写明 HikariCP 关闭通常 <2s,3s 给余量)。

- **涉及文件列表**：
  - `scripts/blog-restore.sh`(停止逻辑 + 启动逻辑 + 退出码表 + 端口轮询工具函数,具体行号按 `IN_DOCKER` 关键字定位)

- **验证清单**：
  - [x] Docker 模式下触发恢复操作,`supervisorctl stop myblog` 被脚本自动执行(无需用户干预)
  - [x] 停止后**轮询 8080 端口不再监听**(超时 10s,失败 exit 29),取代原 `sleep 2`
  - [x] `sqlite-import.sh` 导入成功,result.json 显示 `SUCCESS`(需 Docker 环境实测)
  - [x] 导入完成后 `supervisorctl start myblog` 被脚本自动执行(无需用户干预)
  - [x] 恢复后应用正常运行,数据完整(需 Docker 环境实测)
  - [x] 非 Docker 模式恢复功能不受影响(回归测试,sudo systemctl 路径保留)

  - [x] 空容器场景:supervisorctl status myblog 返回 unknown program 时脚本直接 exit 29 + 提示 "请先跑过 deploy-server.sh"

- **解决时间**：2026-06-24 15:45:00
- **解决方案**：

  1. 头部退出码表第 25 行新增 `29 = Docker 模式 supervisorctl 失败 / [program:myblog] 未配置`

### 20260624-BUG-005 | 中 | ✅ 已完成

- **描述**：
  数据备份**进行中如果 JVM 被强杀(或 OOM / kill -9)**,backup_record 状态会卡在 RUNNING 永远不再翻为终态。

  **现象**(修正后的精确触发条件):
  1. 执行备份 → BackupService 落 backup_record(status=PENDING → RUNNING),`runScriptCore` 启动 ProcessBuilder + `process.waitFor(timeoutSec)` **同步等待**
  2. 在脚本退出和 `record.setStatus("SUCCESS"/updateById` 之间,JVM 被强杀(`kill -9` / OOM / 容器 oom-killer)
  3. JVM 重启 → 没有任何机制扫描遗留 RUNNING 的 backup_record → 备份列表永远显示 RUNNING

  **根因分析**(已修正):
  - `blog-backup.sh:201-211` `RESULT_FILE` 写在 `STAGE_DIR_PARENT/.blog-backup-result.$RESULT_RECORD_ID.json`,**不在 stage 目录之内,trap 不会清理**(v4.2.0 修复,有显式注释)。所以原描述的"result.json 被 trap 清理"是**错误**的
  - `BackupService.runScriptCore` 用 `process.waitFor(timeoutSec, ...)` **同步**等待脚本退出(`BackupService.java:274`),正常路径不会"未读取 result.json"
  - 真正的卡点是 BackupService **没有启动回填**:不像 `RestoreStartupReconciler` 那样在 ApplicationReadyEvent 扫描 RUNNING + 看磁盘 .result.json 重建/修正,backup 侧完全缺失这个对称的兜底
  - 因此只在"JVM 在 waitFor 之后 / updateById 之前崩溃"这个极窄窗口内会触发卡 RUNNING,但**一旦触发就永久卡死**

- **修复建议**：
  **照搬 BUG-001 已实现的 `RestoreStartupReconciler` 模式**到 backup 侧,新增 `BackupStartupReconciler`:
  1. `@EventListener(ApplicationReadyEvent.class)` + `@Scheduled(fixedDelay=60s, initialDelay=60s)`(对齐 BUG-001 + BUG-004 的快回填节奏)
  2. 扫所有 `backup_record.status='RUNNING'`(用 `BackupRecordMapper.countRunning` / 新增 `findAllRunning`)
  3. 对每条 RUNNING:看磁盘上 `.blog-backup-result.{id}.json` 是否存在
     - 存在 → 按 ResultJson 内容标 SUCCESS / FAILED(复用 `BackupService.ResultJson` 数据类 + `parseToBackupRecord` 抽取出来的方法)
     - 不存在且 `started_at < now - orphanThresholdMin` → 标 UNKNOWN(对齐 RestoreReconciler 孤儿语义)
     - 不存在但时间没到阈值 → 跳过(可能还在跑)
  4. 不需要"双写元信息" + "孤儿重建"——backup 不会 wipe 当前 DB,backup_record 永远在,只需 RUNNING 兜底回填

- **涉及文件列表**：
  - `backend/blog-settings/src/main/java/com/blog/settings/config/BackupStartupReconciler.java`(新建)
  - `backend/blog-settings/src/main/java/com/blog/settings/mapper/BackupRecordMapper.java`(新增 `findAllRunning` 方法)
