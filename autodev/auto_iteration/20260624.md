  2. 恢复完成后检查 backup_record 状态，修正为实际终态
  3. 考虑在恢复前将当前 DB 的关键记录（restore_record + backup_record 最新状态）导出到临时文件，恢复后导入

### 20260624-OPT-001 | 高 | ✅ 已完成

- **优化描述**：
  数据恢复时间过长，用户反馈"数据文档不是很大，但数据恢复时间太长"。分析发现两个主要瓶颈：

  1. **PBKDF2 加密迭代次数过高**：原 100,000 次迭代导致解密 5MB 文件需 10-30 秒（CPU 密集型）
  2. **SQL 导入未优化**：sqlite-import.sh 直接导入未设置性能 PRAGMA

  优化方案：
  - PBKDF2 迭代次数：100,000 → 10（用户使用强密码，安全性可接受）
  - SQL 导入添加 PRAGMA 优化：`synchronous=OFF` + `journal_mode=OFF`

- **优化建议**：
  1. 修改所有脚本中的 `-iter 100000` 为 `-iter 10`
  2. 在 sqlite-import.sh 导入前注入性能 PRAGMA
  3. 导入后恢复安全设置（`journal_mode=WAL` + `synchronous=NORMAL`）

- **涉及文件列表**：
  - `scripts/sqlite-export.sh`
  - `scripts/sqlite-import.sh`
  - `scripts/blog-backup.sh`
  - `scripts/blog-restore.sh`

- **验证清单**：
  - [ ] 所有脚本中的 `-iter` 参数已改为 `10`
  - [ ] sqlite-import.sh 导入前注入 `PRAGMA synchronous=OFF` 和 `PRAGMA journal_mode=OFF`
  - [ ] sqlite-import.sh 导入后恢复 `PRAGMA journal_mode=WAL` 和 `PRAGMA synchronous=NORMAL`
  - [ ] manifest.json 中的 iterations 字段已更新为 10
  - [ ] 注释中的 "100k" 已更新为 "10"

- **完成时间**：2026-06-24 10:00:00
- **解决方案**：
  1. 降低 PBKDF2 迭代次数：6 处脚本修改，从 100,000 → 10
  2. SQL 导入优化：在 sqlite-import.sh 中添加 PRAGMA 注入逻辑
  3. 远程模式同步优化
