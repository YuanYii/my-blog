7 个关键决策点 DECISION

v2.5.0 引入 PV 体系 → v2.6.0 跨方言改造 → 2026-06-18 异步化 + 多 BUG 修复

性能 · 写入路径
D-1 · 同步 SELECT+INSERT → 异步 INSERT + UK 约束去重
原"先 COUNT 再 INSERT"两步 TOCTOU 模式：两请求并发都过 COUNT=0，第二个 INSERT 撞 UK 抛异常未 catch。改异步后 INSERT + catch UK 冲突（少 1 次 round-trip，并发幂等）。业务响应不阻塞——SQLite 单连接池下首页不再等每个公开 GET 的 SELECT+INSERT。
2026-06-22 v4.x polish
跨方言
D-2 · UK 冲突三层 catch（Spring DIV / SQLite 原生 / SQLSTATE）
MySQL driver → Spring 翻成 DataIntegrityViolationException → catch 1 收。SQLite driver → 抛原生 SQLiteException（error code 19）→ Spring 因 SQLite 错误码不在内置 mapping 里包成 UncategorizedSQLException → catch 1 漏接，日志刷屏。BIG 修：三层 catch。isUniqueConstraintDup() 检查 message 含 SQLITE_CONSTRAINT / Duplicate entry / SQLSTATE 23xxx，再递归查 cause 链。
2026-06-22 v4.x BUG fix
语义
D-3 · 登录用户不算访客（带 Authorization 即跳过）
admin 改完文章后预览、admin 调试公开 API、admin 自己的"阅读"行为都不应污染 PV/UV。当前项目只有 admin 一种登录用户 → 有 token = admin。未来若有"普通登录用户"功能也合理（访客 = 匿名访问）。用户感知：PV 是真实"路人访问量"。
2026-06-16 调整
性能 · 缓存
D-4 · SLUG_CACHE 正/负双 TTL + -1L 哨兵值
文章详情每次都要 slug → articleId。原本对不存在的 slug（findArticleIdBySlug 返回 null）执行 ConcurrentHashMap.put(k, null) → NPE，被外层 try/catch 吞。改：-1L 哨兵值标识"slug 不存在"，正缓存 TTL=5min，负缓存 TTL=1min。防爬虫狂打随机 slug 导致 map 无界增长 + DB 反复查。
2026-06-18 修复
性能 · 内存
D-5 · SLUG_CACHE @Scheduled 周期清理防内存泄漏
缓存"逻辑过期"——过期 entry 仍在 map 里占位。一个爬虫遍历几万随机 slug，map 外层 key 永久积累，每条 ~200B 也能吃几百 MB。修法：@Scheduled 5min 扫一遍，删掉内层 bucket 已过期的外层 slug。低开销——SLUG_CACHE 是 CHM 静态，进程生命周期内只一份。
2026-06-22 v4.x polish
跨方言
D-6 · referer 域名提取走 Java 端聚合
topReferrers() 不写 SQL substr() 函数（SQLite vs MySQL 字符串函数差异）——拉所有 referer 到 Java 聚合。page_view 表数量级几千行可控。extractDomain：无协议/空/-/相对路径 → direct；去 www. 前缀；截到第一个 /?#` ；端口丢弃。
2026-06-24 DEV-001
建表
D-7 · visit_date DATE 字段 + Java 端截断 created_at
UK (visitor, path, visit_date, created_at) 用于按天去重（每秒一次刷新不算多次 PV）。Java 端把 created_at 设为 visit_date 00:00:00 让 UK 真正按天命中。原 UK (visitor, path, created_at) 只能精确到秒——一秒内多次刷新会全部成功。visit_date 同时用于统计 WHERE visit_date = today 走 DATE 类型 index 快。
2026-06-16 v2.5.0-fix
