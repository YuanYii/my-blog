7 个关键决策点 DECISION

v4.0.0 三件套之一 —— 每一个决策都源自一次具体 BUG 或压测发现

Filter 链排序
D-1 · IpRateLimitFilter 放 HIGHEST+1
TraceIdFilter 占 HIGHEST_PRECEDENCE（保证被限流的拒绝请求日志也带 traceId）；IpRateLimitFilter 退一格但仍是业务 filter 链最前——比 AdminAuthFilter / PageViewFilter 都先跑。被封的 IP 应最早拦截，避免把压力传到后面 DB 或鉴权计算。
FR-5.5 日志体系
存储分层
D-2 · Redis 热路径 + SQLite 仅持久化
限流计数 + 封禁查询走Redis（O(1)），IP ban 的 DB 仅在触发那一刻写一行。生产 SQLite 单连接，全站每请求一次 DB 会直接拖垮站点（压测场景）。Redis 同时天然适合多实例 / 集群部署。额外好处：Redis 故障可 fail-open 降级放行，不会拖垮全站。
2026-06-18 REQ-IPBAN
计数原子性
D-3 · SETNX EX + INCR 原子组合
原"INCR + EXPIRE"两步非原子，INCR 后 EXPIRE 前崩溃会留下永久 counter key持续累积，理论 OOM。新方案：SETNX EX 2s 把"首次创建"和"设过期"合成一步原子；后续 INCR 复用同 TTL。2s TTL 大于 1s 分桶时间，留出秒切换安全余量。
2026-06-22 v4.x polish
并发去重
D-4 · ban() Redis SETNX 抢坑
1 秒内可能多个并发请求都触发阈值判断 → 都想写 DB → 同一封禁事件插入多条记录。修法：Redis SETNX 占坑，只抢到坑位的线程才写 DB，并发场景幂等。已并发的请求直接 return。代价：同一秒只有第一次写 DB，但 Redis 标记仍生效。
2026-06-18 REQ-IPBAN
启动回灌
D-5 · warmUpFromDb() @PostConstruct
Redis 重启或应用重启时封禁缓存丢失 → 短窗口"封禁名单真空"。修法：@PostConstruct 在应用启动时把 DB 里"未手动解封 + 未过期"的封禁重新 SET 进 Redis，TTL 取剩余封禁时长。回灌失败 WARN 不影响启动，最坏只是这些 IP 在 Redis 重建前短暂被放行。
2026-06-18 REQ-IPBAN
故障兜底
D-6 · Redis 故障 fail-open 降级放行
isBanned() Redis 异常 catch + 返回 false；ban() Redis SETNX 异常 → acquired=true 强写 DB（这次 Redis 没生效，下次启动能回灌）；IpRateLimitFilter doFilter catch (Exception e) → WARN + 放行。限流层抖动绝不能拖垮主站——比"严格遵守限流但站挂了"重要。
2026-06-18 REQ-IPBAN
运维手动
D-7 · 手动解封 = DB update + Redis DEL
IpBanService.unban(id)：DB UPDATE unbanned=true + unbanned_at=now（留审计），然后 Redis DEL key 让其立即生效不等 TTL。Redis DEL 异常 WARN "DB 已标记，Redis key 自然过期"——不阻断，给 admin 一个接口 + 一条记录就够用。
2026-06-18 REQ-IPBAN

9 种边界场景 BOUNDARY

覆盖限流热路径 + 封禁异步路径 + 运维手动路径的全部分支

场景 触发条件 后端处理 HTTP / code 决策来源
enabled=false 总开关 运维临时关闭限流（出问题时） shouldNotFilter 直接 true → 跳过滤流逻辑 放行 IpRateLimitFilter L70
OPTIONS 预检 浏览器 CORS 预检 shouldNotFilter 早 return true 放行 IpRateLimitFilter L72
已封禁 IP 请求 Redis ip_ban:{ip} 存在 isBanned() → true → 写 429 429 已封禁 IpRateLimitFilter L82
1 秒内 ≤ 10 次 正常流量 count ≤ maxRequestsPerSecond → 放行 200 放行 主路径
1 秒内 > 10 次 扫描器 / 恶意请求 触发 ban() + 写 429 429 触发封禁 IpRateLimitFilter L109
并发同 1 秒多次触发 同 IP 同时多次越过阈值 Redis SETNX 抢坑：首发写 DB，其余 return 429（DB 仅 1 条） D-4 并发去重
Redis 整体故障 Redis 连接失败 / 超时 catch (Exception e) → WARN + 放行 限流层降级放行 D-6 fail-open
应用重启 / Redis 重启 封禁名单真空期 warmUpFromDb() 回灌剩余 TTL 的封禁 回灌到 Redis D-5 启动回灌
admin 手动解封 DELETE /admin/ip-bans/{id} DB UPDATE unbanned=true + Redis DEL 200 立即解封 D-7

backend/blog-auth/.../auth/entity/IpBan.java
DB entity 字段：id / ip / requestCount / reason / bannedAt / expireAt / unbanned / unbannedAt；status 隐含在 unbanned + expireAt 组合（active = !unbanned && expireAt > now）
Redis schema 约定
两个 prefix：rate_limit:{ip}:{epochSecond}（计数 key，TTL 2s） + ip_ban:{ip}（封禁标记 key，TTL = banDurationMinutes 默认 30min）。两个 prefix 互不冲突，命名空间天然分桶
application.yml 配置项
blog.security.ip-rate-limit.enabled（总开关） + max-requests-per-second（默认 10） + ban-duration-minutes（默认 30）。三配置项都在 application-prod.yml，dev 默认同 prod
