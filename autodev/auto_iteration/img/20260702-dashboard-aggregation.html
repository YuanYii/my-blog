6 个关键决策点 DECISION

v2.5.0 真实数据化 + v2.6.0 跨方言改造 + v4.x polish 性能边界声明

架构
D-1 · 单端点聚合 12 字段（一次调用一次响应）
GET /admin/dashboard 单次调用串/并行查 12 个数据源 → 拼装 Map { kpi, categoryDistribution, tagDistribution, publishTrend, visitTrend, visitTrend7, topArticles, trafficSources, todos, lastBackup }。前端只发一次请求。代价：每次调用都有 ~12 个 SQL，dashboard 不能高频轮询；收益：前端瀑布流简单，render 一次到位。
v2.5.0 起
性能 · 敏感点
D-2 · 总字数：一次性 SELECT content_md → Java strip + 累加
当前 MVP 决定：一次性 query 所有已发布文章正文到 Java 堆，strip markdown 标记后按 codePoint 累加字符数（不做词分词，CJK=1字/ASCII=1字符）。显式迁移触发条件（任一即重构）：文章数 >200 / 平均 content_md >50KB / dashboard P99 >3s。迁移路径：article.word_count 字段 + write-time 算并写库。
2026-06-22 v4.x polish
跨方言
D-3 · MySQL DATE_SUB(NOW(), INTERVAL 30 DAY) → Java 传 LocalDateTime
原 SQL 写 MySQL 特有 DATE_SUB(NOW(), INTERVAL 30 DAY) 不可移植。修：java.time.LocalDateTime.now().minusDays(30) 算 fromTime，用占位符 ? 参数化绑定传 SQL。SQLite/MySQL 都支持，零字符串拼接。
2026-06-17 v2.6.0
故障兜底
D-4 · 各非 KPI 段独立 try/catch 不阻断整体
publishTrend / trafficSources / lastBackup 三段用独立 try { ... } catch (Exception e) {} 兜底——任一段异常降级为空数组/空 map，不影响 KPI / 分类分布等核心字段返回。例：backup_record 表还没初始化（如首次部署未跑备份）时，前端待办仍能正常显示。
2026-06-21 / 06-22
兼容
D-5 · 旧字段 totalViewCount 保留（不删 deleted 文章的 view_count）
KPI totalViewCount 走 SUM(article.view_count) WHERE deleted=0——保留兼容旧版逻辑。"不改过滤条件避免 KPI 大波动"是用户决策：用户已经习惯看见这个数字，删文章时阅读数突然下降会引起困惑。稳妥兼容胜过数学正确。
v2.5.0 兼容策略
数据结构
D-6 · 趋势缺日期由前端补 0（VIEW 层兜底）
visitTrend / publishTrend 只返回有数据的日期，缺失日期省略。前端 chart 渲染时按完整日期轴补 0（如 06-15 没访问 → (06-15, pv:0)）。后端聚合简单（一条 GROUP BY），前端负责补全。前后端职责分明。
v2.5.0 数据契约

8 种边界场景 BOUNDARY

覆盖空数据 / 异常兜底 / 性能边界 / 首次部署

场景 触发条件 后端处理 HTTP / 行为 决策来源
空博客（无文章） 首次部署，article 表为 0 KPI 全 0；列表空数组；总字数 0；趋势空数组 200 全 0 / 空 主路径
publishTrend 异常 SQL 语法错 / 表缺失 try/catch 兜底 → 空数组；KPI 字段照常返回 publishTrend=[]，其他 OK D-4
trafficSources 异常 page_view 引用列异常 try/catch 兜底 → 空数组 trafficSources=[] D-4
未跑过备份 backup_record 表为空 selectLatestSuccess 返 null → lastBackupAt=null 显示「未备份过」 前端 dashboard 待办
无分类 / 无标签 category / tag 表为空 LEFT JOIN 兜底，COUNT=0；前端展示「暂无分布」 200 空数组 主路径
无 PV 统计 page_view 表全空（如未发布访问） todayPV=0 / todayUV=0；趋势空数组；Top 空 200 全 0 主路径
文章量 >200（性能边界） 个人博客量级突破 computeTotalWordCount 卡 1-2s（仍可接受）；触发迁移条件 → 加 article.word_count 字段 P99 升到 1-2s D-2 性能边界
格式异常的 content_md 老文章无 front matter / 乱码 stripMarkdown 8 步正则 strip（不抛异常）；codePoint 累加兜底 数字仍合理 stripMarkdown L188

前端图表库 + 缺日期补 0
