7 个关键决策点 DECISION

2026-06-24 DEV-002 加的整套链路 —— 决策点都围绕"异步 + 解压安全 + 单篇容错"

执行架构
D-1 · self 注入走 @Async 代理
@Autowired @Lazy private ArticleImportService self —— Spring 同类内部方法调用不走代理（this.runImportAsync 失效）。注入 self 走代理才能让 @Async 生效。@Lazy 防循环依赖。本质是"自我注入"模式。
Spring 代理语义
异步线程池
D-2 · articleImportExecutor core/max=1 + AbortPolicy
专门给导入留的线程池：core/max=1 同时只跑一个导入任务（避免多 ZIP 并行解压抢内存）；队列 16（日常排队够用）；AbortPolicy（队列满直接抛异常给前端，让用户重试，不丢任务）。与 pageViewExecutor (DiscardPolicy) 对比：PV 是 best-effort 可丢，导入是用户主动行为不能丢。
AsyncConfig L46
解压安全
D-3 · Zip Slip 双重防护
第一道（parseZip 入口）：路径含 .. / 以 / 或 \\ 开头 → 直接抛 400。第二道（resolveZipPath → normalizeRelative）：解析 ./ 和 ../，跳出根目录的 ../ 静默忽略。双层防护防文件名绕过 + 嵌套 ../ 的特殊构造。
ArticleImportService L204, L435
解压安全
D-4 · 压缩炸弹防护（ZIP 5MB + 解压后 5MB 双上限）
MAX_ZIP_SIZE = 5MB（入口检查）+ MAX_EXTRACTED_SIZE = 5MB（解压累加检查 + 单文件检查）。第一道拦"压缩 100MB → 解压 10GB"的攻击，第二道拦"循环读单文件超 5MB"。双层独立检查——任一触发立即抛 400，避免解压到一半才发现爆。
ArticleImportService L86-89
单篇容错
D-5 · 部分失败仍 SUCCESS（fail_count 区分）
单篇解析失败（如某 md 内容格式错）→ catch + fail_count++ → continue 跑下一篇。整体任务仍 SUCCESS，但 error_message 收 500 字截断的失败清单。前端按 fail_count > 0 单独提示，让用户精准定位哪几篇失败。
ArticleImportService L155-160
图片处理
D-6 · 相对路径双层解析（md 目录为基准 + 文件名兜底）
resolveZipPath(mdPath, ref)：以 md 所在目录为基准解析 ./ 或 ../ 路径，得到 ZIP 内绝对路径。findImageBytes：精确匹配失败时按文件名兜底匹配（用户写错相对路径也尽量找到图），找不到才 WARN「跳过」并继续。图片保存到 uploadDir/yyyy/MM/yyyyMMdd-uuid.png（与 UploadController 路径对齐）。
ArticleImportService L426, L450
标题规范
D-7 · 标题以文件名为准（忽略 front matter title）
标题强制从文件名提取（去 .md + 去 YYYY-MM-DD- 前缀 + - 换空格），忽略 front matter 的 title 字段。原因：title 字段可能跟 md 文件名不一致，导入后用户搜"标题A"找不到对应文章（用户感知混乱）。front matter 只取 date / view_count / status / summary / cover / categories / tags 6 个业务字段。
ArticleImportService L257
