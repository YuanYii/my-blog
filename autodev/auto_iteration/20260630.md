### 20260630-BUG-001 | 高 | 🟡 待处理

- **BUG 描述**：
  博客首页（实际指 NavBar 全局搜索按钮，"首页"为用户口语化表述）搜索按钮"无法使用"——本地 docker (myblog-sim / 28000) 复现：用户输入关键词提交后，搜索结果页显示**所有文章**（不是按关键词过滤的子集）。

  **症状**：用户在 NavBar 搜索图标点开搜索弹窗 → 输入关键词 → 回车 → 跳到 `/search?q=xxx` → 显示"共 N 条结果"+ 全列表文章卡片。体验上等同于"没搜索"。

  **根因（多层叠加，按影响范围排序）**：
  1. **后端搜索召回率高**：`ArticleService.list` line 66 仅 `qw.like("title", keyword)`，对短关键词（< 2 字符）或通用词（"用"、"的"、单字符 "？"）召回全部 title，导致"结果 = 全部"。
  2. **后端缺少长度校验**：未对 keyword 做长度下限检查，1 字符也能搜（命中率高）。
  3. **前端无"结果过多"提示**：search.vue 没在 total 大于阈值时提示用户缩小关键词，用户感知不到搜索"是否生效"。
  4. **nginx `try_files` 触发 301（次要，部署 BUG）**：`scripts/deploy-server.sh:889` 生成的 nginx conf 用 `try_files $uri $uri/ /200.html`，直接访问 `/search`（不带 trailing slash）触发 301 redirect 到 `http://localhost/search/`（host 不带端口），浏览器跟随 redirect 后连接失败。SPA 客户端 router.push 不触发此问题，但刷新页面 / 直接访问 URL / 外部链接场景会失败。
  5. **`fetch-routes.js` 的 `STATIC_ROUTES` 漏 `/search`**（次要，一致性问题）：line 30 数组 `['/', '/about', '/archives', '/tags']` 缺 `/search`，虽然 Nuxt prerender 默认会兜底生成静态 HTML，但与 `docs/design/博客系统设计方案.md:393` 文档化"`/search` 是 prerender 路由之一"不一致。

- **修复建议**：
  1. **`backend/blog-article/src/main/java/com/blog/article/service/ArticleService.java`**：
     - `list()` 方法 line 60 后加 keyword 长度校验：`if (keyword != null && !keyword.isEmpty() && keyword.trim().length() < 2) throw new BusinessException(400, "关键词至少 2 个字符");`
     - line 66 扩展搜索范围：`qw.and(w -> w.like("title", keyword).or().like("summary", keyword).or().like("content_md", keyword))` —— MyBatis-Plus 的 `and(orLambda)` 模式组合三个 like
     - 注意：contentMd 字段可能很大，全表 like 会慢；本期先不加索引优化（用户博客数据量小），保留代码可读性
  2. **`backend/blog-article/src/main/java/com/blog/article/controller/ArticleController.java`**：
     - line 47-50 现有 `enableSearch=false` 403 校验保留不动
     - 无新增改动（关键词长度校验下沉到 Service 层）
  3. **`frontend/pages/search.vue`**：

     - 在 header 段加提示："找到 N 条结果，建议缩小关键词范围"（v-if="isResultTooMany"）
     - 不引入 watch（保持与 OPT-001 同风格的「逻辑下沉」原则）
  4. **`scripts/deploy-server.sh` line 889**：

     - 修复后：nginx 先试 `/search/index.html`（直接命中），跳过 `$uri/` 的 301 redirect 行为
     - 同时覆盖 `/about /archives /tags` 等所有"目录形"路由
  5. **`frontend/scripts/fetch-routes.js` line 30**：
     - `STATIC_ROUTES` 数组补 `/search`：`const STATIC_ROUTES = ['/', '/about', '/archives', '/tags', '/search']`

## Hotfix 2026-07-01 — BUG-001 前端段真闭环

> 触发：用户截图 `/search?q=刷量` 显示 6 条结果 + 无"建议缩小关键词范围"提示（`autodev/auto_iteration/20260630.md` BUG-001 修复后 24h 反馈「还是不行」）。
> 不走流水线：Mavis 排查 + 修 + 部署到 sim，不动 prod，等用户拍板。

### 排查链

| 步 | 工具 | 结论 |
|---|------|------|
| 1 | playwright 打开 `localhost:28000/search?q=刷量` | 页面：6 条结果 + 无阈值提示；网络：`?params={"keyword":"刷量",...}` |
| 2 | curl `/api/v1/articles?keyword=刷量` | 200 返 **1 条**（id 8231）—— 后端 BUG-001 修复完全正常 |
| 3 | curl `?keyword=AI` / `?keyword=S` | 1 条 / 400「关键词至少 2 个字符」—— 后端全过 |
| 4 | 容器内 grep `_nuxt/*.js` | 含 `建议缩小关键词范围` / `isResultTooMany` 编译进去 —— BUG-001 前端代码在的 |
| 5 | 容器内 grep `usePublicApi` 编译后 | `get: (a, l) => n(a, { method: "GET", params: l })` —— `l` 整个当 query params |
| 6 | 对比 `tags.vue` 调用 | `get('/articles', { tagId, size })` 直接展开 —— search.vue 是唯一 `{ params: {...} }` 包装的 |

### 真根因

`frontend/pages/search.vue:28-30` 的 `get` 调用**多包了一层 `params:`**：

```ts
// 错：query 对象被多包一层 params:，ofetch 把它序列化为
// ?params={"keyword":"刷量","page":1,"size":20}
// 后端拿不到 keyword → 走「无 keyword 列表」→ 返全表 6 条
const res = await get<any>('/articles', {
  params: { keyword: keyword.value, page: page.value, size }
})
```

**OPT-002 引入 search.vue 时就错了**（不是 BUG-001 引入），但 6 条全表的 BUG 症状与 4 条 AI 全命中让前端表现恰好"看着像 BUG-001 修复前"被掩盖了；后端 24h 前刚修后，前端 query string 拼错才显式暴露。

### 修复（1 行 diff）

```diff
-    const res = await get<any>('/articles', {
-      params: { keyword: keyword.value, page: page.value, size }
-    })
+    const res = await get<any>('/articles', {
+      keyword: keyword.value, page: page.value, size
+    })
```

只改 search.vue 一行，**不动** `usePublicApi` 公共组件（tags.vue 已用对的写法，公共组件不该为单页面屈就）。
