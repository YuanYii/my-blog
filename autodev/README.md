# 自动开发流水线（AutoDev）

> 九角色夜间自动迭代闭环，将需求→实现→代码审查→测试→集成测试→复核→文档归档→发布串联为一条自动化流水线。
> 所有的日期使用北京时间

## 目录结构

```
autodev/
├── README.md                    # 本文件
├── config.json                  # 项目配置（Stage 0 自动生成）
├── promopt/                     # 九个角色的提示词
│   ├── 00_项目检测员.md        # Stage 0 · 项目架构识别
│   ├── 01_产品经理.md          # Stage 1 · 需求拟定
│   ├── 02_开发工程师.md        # Stage 2 · 代码实现
│   ├── 03_代码质量审查员.md    # Stage 3 · 代码质量审查
│   ├── 04_测试工程师.md        # Stage 4 · 静态审计
│   ├── 05_集成测试员.md        # Stage 5 · 集成测试
│   ├── 06_项目经理.md          # Stage 6 · 审计复核与任务回种
│   ├── 07_文档工程师.md        # Stage 7 · 文档同步归档
│   └── 08_发布管理员.md        # Stage 8 · 版本发布
```

## 角色职责

### 00 项目检测员（Stage 0，新增）

- **触发时机**：项目初始化时手动触发，或项目结构发生重大变化时
- **核心职责**：扫描项目目录结构，自动识别技术栈和架构，生成 `autodev/config.json` 配置文件
- **不做**：不修改项目代码，只生成配置文件
- **识别能力**：
  - 后端：Java/Maven/Gradle、Spring Boot、MyBatis-Plus/JPA
  - 前端：Nuxt/Vue/React、TypeScript、Tailwind CSS
  - 数据库：SQLite/MySQL/PostgreSQL
  - 缓存：Redis
  - 容器化：Docker/Docker Compose
- **输出**：`autodev/config.json`（项目配置，供后续 Stage 读取）

### 01 产品经理（Stage 1）

- **触发时机**：用户随时手动触发
- **输入**：用户口语化需求简述
- **输出**：`auto_iteration/{RUN}.md`（BUG / 优化 / 开发 三区段结构化任务卡片）
- **产出路径**：`autodev/auto_iteration/{RUN}.md`
- **注意**：涉及文件列表为**预测性**（基于需求推断），最终以项目经理提取为准

### 02 开发工程师（Stage 2）

- **触发时机**：每天凌晨 03:00 自动执行
- **执行规则**：BUG → OPT → DEV 顺序，同级按优先级，单次上限 5 个任务，超 15 分钟/10 文件即停止
- **输入**：`auto_iteration/{SRC}.md`（`SRC = RUN - 1 天`）
- **输出**：代码改动 + 处理报告追加到源文档末尾
- **工作机制**：`RUN` = 运行日，`SRC` = `RUN - 1 天`

### 03 代码质量审查员（Stage 3，新增）

- **触发时机**：每天凌晨 03:30 自动执行
- **核心职责**：对开发工程师提交的代码进行质量审查（规范/性能/安全三个维度），输出审查报告，**不修改代码、不判断需求符合性**
- **审查维度**：
  - 代码规范：命名、注释、文件/方法长度、重复代码
  - 性能：N+1 查询、未分页大查询、资源未关闭、Redis N+1、前端大 bundle
  - 安全：SQL 注入、XSS、敏感信息泄露、JWT secret 硬编码、未鉴权接口、CORS 通配
- **输入**：`auto_iteration/{RUN}.md`（✅ 已完成任务的涉及文件列表）
- **输出**：`auto_audit/{RUN}/{RUN}-stage3.md`
- **结论分级**：🔴 严重（必须修复）/ 🟡 警告（建议修复）/ 🟢 建议（可选优化）
- **与流水线关系**：不阻塞后续 Stage（测试工程师仍按需求符合性独立判断）

### 04 测试工程师（Stage 4）

- **触发时机**：每天凌晨 04:00 自动执行
- **审计方法**：静态核对（grep 涉及文件，逐条验证清单），非运行时测试
- **判定标准**：✅ 通过 / ⚠️ 部分通过 / ❌ 未实现 / 🔍 需运行确认
- **🔍 项强制要求**：必须写明「建议验证方式」，不能只写"需人工确认"
- **输入**：`auto_iteration/{SRC}.md`（✅ 已完成任务）
- **输出**：`auto_audit/{RUN}/{RUN}-stage4.md`
- **支持模式**：模式 A（首次全量审计）/ 模式 B（增量审计：只审源文档当前 ✅ 但上次未审的任务）

### 05 集成测试员（Stage 5，新增）

- **触发时机**：每天凌晨 04:30 自动执行
- **核心职责**：对测试工程师审计报告中标记为 🔍 的遗留项进行**实际运行验证**，给出确定结论（✅/❌），**不修改代码、不重新做静态审计**
- **前置条件检查**：
  - 后端（localhost:8080）未启动 → 结束，跳过集成测试
  - 前端（localhost:3000）未启动 → 仅测试 API 项，UI 项标注跳过
  - Redis 未启动 → 相关验证跳过
- **验证类型**：
  - 类型 A（UI 交互）：按钮点击、表单提交、弹窗、路由跳转
  - 类型 B（API 调用）：接口返回格式、状态码、鉴权行为
  - 类型 C（视觉效果）：颜色、字体、间距、响应式断点
  - 类型 D（时区/时间）：时间格式化、时区转换
- **输入**：`auto_audit/{SRC}/{SRC}-stage4.md`（取当天的审计报告，提取所有 🔍 项）
- **输出 1**：`auto_audit/{RUN}/{RUN}-stage5.md`（集成测试报告）
- **不回写审计报告**（本版起）：审计报告保留 🔍 状态作为"待集成测试"标记，stage5 报告独立承载确定结论，项目经理（Stage 6）合并读取两份报告判断

### 06 项目经理（Stage 6）

- **触发时机**：每天凌晨 05:00 自动执行
- **核心职责**：**格式转换员**——将测试审计报告中的异常项（⚠️/❌）转换为标准任务卡片，**不做问题分析、不自行判断根因**（分析由测试工程师负责）
- **分类映射**：行为与需求不符 → BUG / 功能未实现 → DEV / UI 偏差 → OPT
- **涉及文件列表**：以审计报告引用的 `文件:行号` 为**最终版**（与产品经理的预测性列表可能不同，以本项为准）
- **输入**：审计报告（取版本号最大的一份）+ 源任务文档
- **输出 1**：门控文件 `auto_audit/{SRC}/{SRC}-stage6.md`（异常计数：BUG / DEV / OPT，供 Stage 7 门控）
- **输出 2**：autopush 卡片合并进 `auto_iteration/{RUN}.md`（次日被开发工程师接手）
- **幂等保证**：写入前检查同源卡片，存在则先删旧再重写

### 07 文档工程师（Stage 7）

- **触发时机**：每天凌晨 06:00 自动执行（支持 Watcher 增量同步）
- **前置条件（门控）**：读取 `{SRC}_autopush.md`，若 BUG > 0 或 DEV > 0 则跳过（保证上游清空后才同步）
- **Watcher 逻辑（新增）**：完成当日 `_autopush.md` 处理后，扫描是否有**更新日期**的 `_autopush.md`，有则增量同步（避免白天流水线跑完后等到次日 6:00 才同步文档）
- **输入**：`auto_iteration/{SRC}.md`（✅ 已完成任务）
- **输出 1**：增量更新 `README.md` + `docs/design/博客系统设计方案.md`
- **输出 2**：在追踪文档底部追加处理报告
- **输出 3**：从 `autodev/status.json` 渲染「## 流水线状态｜{SRC}」段到 `{SRC}.md` 末尾（整段覆盖，详见下文「流水线状态视图」）
- **同步范围**：
  - 设计方案（§1 概述 / §3 架构 / §4-5 前后端 / §6 API / §7 部署 / §8 进度）
  - README（功能表 / 版本记录 / 项目结构 / 快速开始 / 技术栈）
- **注意**：所有的 BUG/OPT/DEV 编号都应该完整展示，而非使用简化版本

### 08 发布管理员（Stage 8，新增，默认手动触发）

- **触发时机**：用户手动触发（说"发布新版本" / "生成本周 CHANGELOG" / "打 tag"）；可选每天 06:30 自动检查（需显式启用）
- **核心职责**：检查追踪文档中所有任务是否已完成，决定是否触发版本发布，生成 CHANGELOG，打 Git tag，**默认不自动执行 `publish-release.sh`**
- **版本号决策规则**：
  - 新增功能（DEV 类任务）→ minor +1（如 4.2.0 → 4.3.0）
  - Bug 修复（BUG 类任务）→ patch +1（如 4.2.0 → 4.2.1）
  - 破坏性变更（API 不兼容、数据库 schema 变更）→ major +1（如 4.2.0 → 5.0.0）
  - 仅优化（OPT 类，无新功能无 Bug 修复）→ patch +1（或跳过发布）
- **自动触发条件**（全部满足才执行）：
  1. 所有任务状态均为 ✅（无 🟡 / 🔴）
  2. 距离上次发布 ≥ 1 天
  3. 不在版本冻结期（`autodev/freeze.flag` 不存在）
  4. 用户未设置 `AUTO_RELEASE=off`
- **输入 1**：`autodev/auto_iteration/` 下所有 `{RUN}.md` 格式的文件（自上次发布以来的所有任务）
- **输入 2**：`autodev/auto_iteration/*_autopush.md`（确认无遗留 BUG/DEV）
- **输入 3**：`backend/pom.xml`（读取当前版本号 `${revision}`）
- **输出 1**：`CHANGELOG.md`（增量更新，追加新版本条目）
- **输出 2**：Git tag（`v{Major}.{Minor}.{Patch}`）
- **输出 3**（可选）：执行 `scripts/publish-release.sh` 的结果（需用户确认）
- **输出 4**：`autodev/auto_iteration/{RUN}_release.md`（发布报告）

## 关键约定

### 项目配置（config.json）

`autodev/config.json` 是项目的唯一配置源，由 Stage 0（项目检测员）自动生成。后续 Stage 读取此文件获取项目信息：

- `project.name` / `project.nameEn`：项目名称
- `modules.*`：后端模块结构
- `database.*`：数据库配置
- `techStack.*`：技术栈信息
- `ports.*`：服务端口
- `api.*`：API 前缀和健康检查端点
- `docs.*`：文档路径

### 日期变量

- `RUN`：运行日（今天），北京时区 UTC+8
- `SRC`：源文档日（`RUN - 1 天`），即被处理的文档日期
- 各角色输出文件命名规则：
  - Stage 1/1/3 输出按 `RUN`
  - Stage 3 输出按 `RUN`（与开发工程师同日）
  - Stage 4/2.5 输出按 `RUN`（与测试工程师同日）
  - Stage 7 读取按 `SRC`
  - Stage 8 读取自上次发布以来的所有文档

### 任务编号格式

- 手工任务：`{YYYYMMDD}-{BUG|OPT|DEV}-{NNN}`
- autopush 卡片：`autopush-{SRC}-{BUG|OPT|DEV}-{NNN}`（SRC = 源文档日期，不是当天）

### 报告单文件覆盖规则（本版起，无版本号）

各阶段输出的审计报告/代码审查报告/集成测试报告/门控文件，**统一不带版本号后缀**，重跑时**覆盖写入同一文件**：

| 报告类型 | 输出路径 | 单文件覆盖 |
|---------|---------|-----------|
| 代码质量审查报告 | `auto_audit/{RUN}/{RUN}-stage3.md` | ✅ 重跑直接覆盖 |
| 测试工程师审计报告 | `auto_audit/{RUN}/{RUN}-stage4.md` | ✅ 重跑直接覆盖 |
| 集成测试报告 | `auto_audit/{RUN}/{RUN}-stage5.md` | ✅ 重跑直接覆盖 |
| 项目经理门控文件 | `auto_audit/{SRC}/{SRC}-stage6.md` | ✅ 重跑直接覆盖 |

**重要规则**：
1. **每天独立**：不同 `RUN` 日期的 stage 文件相互独立（路径里 `{RUN}` 不同）
2. **重跑覆盖**：同一 `RUN` 下重跑直接覆盖旧报告，不再生成 `v2` / `v3`...
3. **模式判断简化**：04 测试工程师的"模式 A 首次 / 模式 B 增量"判断从"扫描 v* 文件"改为"检查 stage4.md 是否存在"
4. **历史归档（按需）**：如需保留旧版本，手动 `cp auto_audit/{RUN}/{RUN}-stage4.md auto_audit/{RUN}/archive/manual-save/2026-06-24T214500/`

> **设计动机**：避免一天内多次重跑产生 v1→v2→v3→v4 多个文件堆积；status.json + 流水线状态视图段（详见下文）保留阶段结果信息。
> **回退方式**：如确需恢复 v{N} 模式，将单文件覆盖改回 `v{N_max+1}` 即可（旧提示词模板在 git 历史 `autodev/promopt/04_测试工程师.md` 改造前版本可查）

### 任务状态

- 🟡 待处理 / 🟠 执行中 / ✅ 已完成 / 🔴 执行失败

### 处理顺序

BUG → OPT → DEV，同级按优先级（高 → 中 → 低）

### 流水线状态视图

`autodev/status.json` 是流水线状态的唯一真相源，由 Stage 7 文档工程师在更新 status.json 后**整段渲染**为 markdown 表格，追加到 `auto_iteration/{SRC}.md` 末尾的「## 流水线状态｜{SRC}」段。

- **状态字段映射**：`success` → ✅ / `failed` → ❌ / `skipped` → ⏭ / `pending` → ⏸ / `running` → 🟠
- **覆盖规则**：每次 Stage 7 执行都从 status.json 重新渲染整段，历史快照不保留（这是有意的设计——status.json 是唯一真相源，多份快照只会制造阅读负担）
- **8 个 stage 列**：Stage 1 需求拟定 / Stage 2 代码实现 / Stage 3 代码审查 / Stage 4 静态审计 / Stage 5 集成测试 / Stage 6 门控 / Stage 7 文档同步 / Stage 8 发布
- **效果**：打开 `{SRC}.md` 末尾就能一眼看完 8 个 stage 状态，不必翻 auto_audit/ 下的多份报告

## 注意事项

1. **零异常闭环**：项目经理在审计报告无 ⚠️/❌ 项时，只产出空门控文件，不生成任何卡片
2. **门控保证**：文档工程师仅在 `BUG=0 且 DEV=0` 时执行文档同步，防止未修复项污染正式文档
3. **单次上限**：开发工程师单次最多处理 5 个任务，避免超时；超出部分留待次日
4. **静态审计局限**：UI 交互、视觉效果、LLM 输出等无法静态判定的项，测试工程师统一标 🔍 需运行确认；由集成测试员在 Stage 5 给出确定结论
5. **幂等写入**：项目经理写入卡片前检查同 `SRC` 来源的 autopush 卡片是否已存在，防止重复执行导致重复卡片
6. **代码质量审查不阻塞**：Stage 3 的输出不影响 Stage 4 的审计范围（测试工程师仍按需求符合性独立判断）
7. **集成测试依赖环境**：后端/前端/Redis 未启动时，对应验证项标注跳过，不阻塞流水线
8. **发布管理员默认手动**：避免每天自动打 tag；启用自动模式需显式配置 `AUTO_RELEASE=on` 并确认无版本冻结
9. **项目检测员仅初始化时运行**：Stage 0 生成 config.json 后，后续 Stage 直接读取，无需重复执行
