## 一、规范维度（Standards）

- ✅ **类型与签名一致**：`[slug].vue` 的 `useAsyncData` 解构 `error/status/refresh` 为 Nuxt 3 官方返回形参，正确；`dashboard.vue` 的 `visitorIpSources` ref 类型标注 `{ ip, count, percentage }` 与后端返回结构一致。
- ✅ **跨方言 SQL 约定遵守**：`topVisitorIps` 使用 `visit_date >= ?` + `GROUP BY ip` + 参数化 `LIMIT ?`，与项目既有 `topReferrers`/`dailyStats` 同路（AGENTS.md §4.5 跨方言统一要求），未引入 `CURDATE()`/`DATE_SUB()` 等 MySQL 专有函数。
- ✅ **Java 8 兼容**：显式 `new java.util.ArrayList<>()` / `java.util.LinkedHashMap<>()`（避免钻石操作符在部分 javac 下的推断差异），与项目"环境降级不升 Java"红线（AGENTS.md §4.1）一致。
- ✅ **Vue 模板分支闭合正确**：`[slug].vue` 的 `v-if loading → v-else-if articleError → v-else-if article → v-else` 四级分支完整，无遗漏标签。
- ✅ **错误兜底落点明确**：`edit.vue` 的 `handlePreview` 对 `!form.id` 先 `await save(false)` 再判空，符合"保存后再预览"契约；`[slug].vue` 顶部 `preview-banner` 仅在 `v-else-if="article"` 内渲染，不与错误分支冲突。

## 二、性能维度（Performance）

- 🟡 **观察项 A（非阻断）**：`topVisitorIps` 按 `ip` 分组，但 `page_view` 现有索引为 `idx_page_view_visitor(visitor)`，**无 `ip` 单列索引**。当前博客访问量级（日 PV 通常 < 1e4）下全表扫描 + 内存 GROUP BY 开销可忽略；若未来 PV 进入百万级，建议补 `idx_page_view_ip(ip)`。暂不阻断。
- ✅ **百分比双查询可控**：`topVisitorIps` 仅 2 条 SQL（1 条 COUNT(*) 分母 + 1 条分组），`DashboardController.dashboard()` 整体 ~10 条查询均在单次看板请求内，仪表盘 QPS 极低（admin 人工刷新），无 N+1。
- ✅ **前端零额外渲染成本**：`decoratedVisitorIpSources` 仅做 `map` 映射（颜色/名称），无循环内异步；列表上限 5 行。

## 三、安全维度（Security）—— 红线 §4.9

- ✅ **无 SQL 注入**：`topVisitorIps` 全部使用 `?` 占位参数化（`fromDate`、`limit`），未拼接任何外部字符串。
- ✅ **无敏感字段日志**：改动范围（PageViewService 查询 / DashboardController put / 前端渲染）均未新增 `log.info/warn` 打印 password / token / secret 等字段。
- ✅ **IP 不泄露到公开端点**：`visitorIpSources` 仅由 `DashboardController.dashboard()` 返回，该接口命中 `AdminAuthFilter` 的 `/admin/` 白名单（需 Bearer + X-Device-Id），公开 `/api/v1/articles/**` 不返回 IP 维度。
- ✅ **空 IP 不泄露、不抛异常**：SQL `ip IS NOT NULL AND ip != ''` 过滤空值；分母为 0 时直接返回空列表（`if (total == 0L) return new ArrayList<>()`），无 `除以 0` 风险。
- 🟡 **观察项 B（非阻断）**：`PageViewService.topReferrers` 方法保留但已无调用方（前端 `trafficSources` 移除），属死代码。不影响安全/功能，建议后续清理（非本次范围）。
