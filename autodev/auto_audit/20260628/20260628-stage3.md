## 🟡 警告

### WARN-001：useModalKeyboard.ts immediate: true 重复 addEventListener 风险
- **文件**：`frontend/composables/useModalKeyboard.ts`，第 50-56 行
- **维度**：规范（生命周期）
- **描述**：watch 加 `immediate: true` 后，组件 setup 阶段如果 `open.value` 已经是 `true`（比如某个 admin 页面在挂载时 modal 已经打开的边界情况），会立即 addEventListener；后续 `onBeforeUnmount` 又 removeEventListener —— 看起来对称，但若 `open` 在组件挂载后才变化（正常流程），则 addEventListener 触发 1 次 + onBeforeUnmount 触发 1 次 = 0 净监听；**实际上无泄漏**。
- **真实风险点**：如果同一页面**多次**调用 `useModalKeyboard`（虽然现在 4 个页面都各 1 次），每个实例都注册自己的 onKeydown —— 用户按 Esc 时，**所有**还活着的监听器都会触发（但每个监听器内部用 `if (!open.value) return` 守卫，所以不会重复关 modal）。
- **审查结论**：当前设计安全（守卫齐全），不构成 bug，但**建议**在 `useModalKeyboard` 顶部加 `console.assert` 或注释明确"同一时刻只有 1 个 modal 打开"前提。
- **修复建议**（轻量，不阻塞）：
  ```ts
  // useModalKeyboard.ts 顶部加注释：
  // 假设：调用方在同一组件中只对单一 modal 启用，多个 modal 各自独立 useModalKeyboard 实例
  // 多个 modal 同时打开的边界情况：每个实例的 keydown 监听器都会触发，但只对 open=true 的实例执行 onCancel
  ```
  **审查中已补充该注释到代码**（详见下方"审查补充"段）。

### WARN-002 候选：GlobalDialog.vue onKeydown window 监听器永远挂着
- **文件**：`frontend/components/GlobalDialog.vue`，第 87-88 行
- **维度**：规范（资源）
- **描述**：GlobalDialog 实例一旦 mounted（`admin.vue` 顶层 `<ClientOnly>` 包裹），window keydown 监听器**永久**挂着（直到 layout 卸载），而 `props.open` 可能 99% 时间是 false。监听器只是 `if (!props.open) return` 直接返回，**性能上无影响**（每次 keydown 多一次 ref 属性读取）。
- **审查结论**：可接受 —— GlobalDialog 是 admin 全局单例，layout 不卸载 listener 就不卸载是合理设计；这与 useModalKeyboard 的"按需挂载"形成对比但各有合理性。
- **不需要修复**。

## 🟢 建议

### SUG-001：focus-visible 样式只覆盖了 dialog 内的 .btn，未覆盖内联 modal
- **文件**：`frontend/components/GlobalDialog.vue` 第 202-209 行
- **描述**：focus-visible 样式用 `<style scoped>` 包裹，只对 GlobalDialog 内部 button 起效；内联 modal（categories/tags/restore/backup）的「确定/保存/确认恢复」按钮没有对应的 focus-visible 样式，键盘用户的焦点环依赖全局 main.css 的通用 `.btn` focus 样式
- **建议**：如果全局 `.btn:focus-visible` 已有 outline 则无需额外处理；如没有，建议在 main.css 补：
  ```css
  .btn:focus-visible { outline: 2px solid var(--primary); outline-offset: 2px; }
  .btn-danger:focus-visible { outline-color: var(--danger); }
  ```
- **审查确认**：未访问 main.css 全局样式做最终判定（与本任务非强相关，留给后续 OPT 改进）

### SUG-002：e2e 测试中 Playwright `await expect(page.locator(...)).toHaveCount(0)` 的"防重"测试断言过宽
- **文件**：`frontend/tests/dialog-keyboard.spec.ts` 第 169-188 行（防重测试）
- **描述**：
  ```ts
  expect(confirmCount).toBeLessThanOrEqual(1)
  ```
  实际期望是 `=== 1`，用 `<= 1` 是为了"如果未来业务变化偶尔 0 次也通过"——但**会掩盖真实 bug**（如果某次重构后 confirm 不触发，count=0 仍能通过）
- **建议**：改为 `expect(confirmCount).toBe(1)`，让任何偏差立即失败

### SUG-003：e2e 测试的 "Enter 触发确认" 断言依赖 page.route mock，但生产代码不走 mock
- **文件**：`frontend/tests/dialog-keyboard.spec.ts` 第 167-189 行
- **描述**：mock 的 POST /admin/articles/categories 总是返回 200，可能掩盖了 "Enter 时正好 modal 已关闭 → 第二次 Enter 实际打了哪里的回车" 的真实场景
- **建议**：补充一个反向测试：先 mock 让第一次请求延迟 500ms 返回，期间快速按 Enter 3 次，验证 modal 关闭后第 2/3 次 Enter 不会打到背景上（如清空 input 焦点）
