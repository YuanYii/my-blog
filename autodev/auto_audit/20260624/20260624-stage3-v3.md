## 🟡 警告

### WARN-001：reconcileOnStartup 直接用 Thread.sleep(5_000) 阻塞 ApplicationReadyEvent
- **文件**：`backend/blog-settings/src/main/java/com/blog/settings/config/RestoreStartupReconciler.java`，第 73-79 行
- **维度**：性能/规范
- **描述**：`reconcileOnStartup` 是 `@EventListener(ApplicationReadyEvent.class)` 监听,跑在 Spring 启动线程。原实现已经是同步,本轮新增 `Thread.sleep(5_000)` 后又跑一次 reconcile,**会把 JVM 启动事件分发额外延迟 5 秒以上**。其他 `ApplicationReadyEvent` listener(如健康检查、缓存预热)也会被推后。
- **修复建议**：改为 `@Async` 或用 `TaskScheduler.schedule(this::reconcile, Duration.ofSeconds(5))` 异步触发。本期任务标 ✅,但建议后续改造为非阻塞。
- **风险评估**：dev 环境影响小（启动慢 5s 体感不强）；prod 启动后 health-check 可能延后,nginx upstream 可能短暂返回 502。

### WARN-002：BackupStartupReconciler.applySuccess 直接复用 BackupService.ResultJson 公有静态类
- **文件**：`backend/blog-settings/src/main/java/com/blog/settings/config/BackupStartupReconciler.java`，第 153-179 行
- **维度**：规范（耦合）
- **描述**：reconciler 直接引用 `BackupService.ResultJson` 静态内部类,且重复了一段几乎与 `BackupService.runScriptCore:328-369` 一致的 "result → record" 映射逻辑（asset_urls 拼接、manifest_json 读取）。两段代码独立演化时易漂移（一处加字段另一处忘加）。
- **修复建议**：把 `BackupService.runScriptCore` 内的"映射 result → record"段抽成 package-private 静态方法 `BackupService.applyResultToRecord(BackupRecord, ResultJson, Path stageDirParent, ObjectMapper)`,reconciler 直接调用。本期任务标 ✅,可入 backlog 一并清理。

## 🟢 建议

### SUG-001：wait_port_freed 默认 fallback 时长建议加注释更显眼
- **文件**：`scripts/blog-restore.sh`，第 60-75 行
- **描述**：`wait_port_freed` 函数注释里写了 "sleep 3 经验值,HikariCP 关闭通常 <2s",但函数体内 `sleep 3` 那一行只是单行 `sleep 3` 无内联注释。后续维护者改这 3 秒可能不知道为什么。建议在 `sleep 3` 行尾加 `# HikariCP shutdown typically <2s, 3s gives margin`。

### SUG-002：BackupStartupReconciler 的 ORPHAN 状态用 FAILED 标的语义偏差
- **文件**：`backend/blog-settings/src/main/java/com/blog/settings/config/BackupStartupReconciler.java`，第 125-133 行
- **描述**：BackupRecord 没有 UNKNOWN 状态,reconciler 把"30min 没 result.json"的孤儿直接标 FAILED + errorStage=ORPHAN。前端 backup.vue 可能会把 errorStage=ORPHAN 错误地当作脚本失败显示。建议后续在 backup_record schema 添加 UNKNOWN 状态或在前端区分 errorStage=ORPHAN 与 errorStage=SCRIPT/UPLOAD。

### SUG-003：refreshMeta 在批量删除并行 Promise.allSettled 完成后只调一次,期间侧栏可能短暂陈旧
- **文件**：`frontend/pages/admin/posts.vue`，handleBulkDelete 第 ~128 行
- **描述**：`Promise.allSettled` 等所有并发删除请求都 settle 才调 refreshMeta。如果 50 条并发删除中前几条 200ms 完成,但其余 5s 才返回,中间这 5s 侧栏数字仍是旧值。属轻微 UX 体验项,不影响功能。

### SUG-004：BackupStartupReconciler 没有 5min 兜底巡检,仅 60s scheduled
- **文件**：`backend/blog-settings/src/main/java/com/blog/settings/config/BackupStartupReconciler.java`，第 78 行
- **描述**：相比 BUG-001 之前 RestoreStartupReconciler 的 5min,本期 BackupReconciler 直接 60s。理论上单次开销小,但 prod 环境数月不重启时,每分钟一次轻量 SQL count 全年 ~520k 次。建议远期改回 5min(或读 prop)。当前可观测影响 ~ 0,留作 backlog。
